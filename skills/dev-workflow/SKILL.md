# Dev Workflow

用户只需用自然语言描述希望实现或修复的目标，不需要选择风险等级、阶段或流程。AI 在内部把需求按 small、medium、large 三档处理：先识别风险和影响面，再选择足够而不过度的流程；以可验证的功能结果结束，而不是以“代码已写完”结束。

## 1. 确认授权与当前事实

1. 读取适用的 `AGENTS.md`、仓库状态、相关代码、测试和项目命令，保护已有用户修改。
2. 区分用户意图：
   - 讨论、分析、评审或制定方案：保持只读。
   - 明确要求实现、修改或修复：授权范围内的本地修改与非破坏性验证。
3. 即使用户要求直接实现，medium 和 large 仍执行各自的方案批准门；small 不重复确认。
4. 未经明确要求，不提交、不推送、不创建 PR、不部署、不修改远程状态。

## 2. 按风险分级

由 AI 自动分级，不要求用户判断或记忆等级。优先检查 large 的硬触发条件，再判断是否满足 small；其余归为 medium。不要按文件数量机械分级。

### Large：任一条件成立

- 数据库、Schema、存量数据迁移、数据一致性或恢复问题。
- 公共 API、协议、持久化格式、兼容性契约或跨版本行为。
- 认证、授权、权限、密钥、隐私或其他安全边界。
- 跨服务、跨仓库、核心架构、关键基础设施或生产发布链路。
- 灰度、迁移、回滚、停机、数据损坏或明显难以逆转的风险。
- 大规模行为保持型重构，且需要证明关键语义没有变化。

### Small：以下条件全部成立

- 改动局部、可逆，根因与预期行为清楚。
- 不改变公共契约、数据模型、权限边界、生产配置或发布流程。
- 不引入新的依赖、架构模式或跨模块协作关系。
- 可用聚焦测试和少量相邻检查建立足够信心。

### Medium

不属于 large，也不能同时满足 small 的需求。常见情况包括跨文件或跨模块行为、共享组件、内部公共函数、新依赖、多条用户路径、明显方案取舍或需要完整回归评审的功能。

若信息不足，默认 medium。实施中发现风险升级时，立即重新分级并在新等级的下一个批准门暂停；不要静默降级。

用一句话告知用户：`判定为 <等级>：<关键原因>；将按 <流程摘要> 推进。`

## 3. 加载对应流程

先阅读 [references/impact-map.md](references/impact-map.md)，再只加载命中等级的文件：

- small：阅读 [references/small.md](references/small.md)。
- medium：阅读 [references/medium.md](references/medium.md)。
- large：阅读 [references/large.md](references/large.md)。

需要阶段交接、最终交付或跨会话状态时，再阅读 [references/handoff-and-artifacts.md](references/handoff-and-artifacts.md)。不要为了形式创建额外文档。

## 4. 遵守共享质量底线

- 先画影响面，再修改；搜索定义、调用方、消费者、配置、测试和相似实现。
- 把验收条件写成可观察、可验证的行为，并覆盖失败路径和边界条件。
- 解决根因，控制改动范围；不顺手修复无关问题，不用删测、弱化断言或硬编码绕过测试。
- 实施时记录重要方案偏差；偏差改变目标、契约、风险或范围时重新征求批准。
- 验证强度逐级增加：聚焦验证 → 相邻回归 → 完整检查。明确区分未运行、通过和被既有问题阻塞。
- Review 区分阻断项与可选改进。复审要去重、确认修复并检查新增回归；允许报告此前遗漏但与当前改动相关的严重问题。
- 自动修复与复审连续三轮仍无法收敛时停止循环，交付证据、剩余阻塞和建议决策。
- medium / large 仅在任务可清晰拆分、触达路径不重叠或需要独立视角时使用子代理；主代理保留整体上下文，challenge、review、acceptance 优先使用独立新视角。

## 5. 完成判定

仅在以下条件满足时宣布完成：验收条件有证据支持；相关阻断项已处理或明确由用户接受；验证结果与未验证项已说明；计划偏差、残余风险和后续操作已交接。
