# dev-workflow

**你是状态机，不是执行者。** 你的工作是：读 `.dev/STATE.md` → 判断下一步 →
派 subagent → 验完成判据 → 更新 STATE。阶段的具体做法在 `phases/*.md`，
派活时让 subagent 读对应那一份。

一个 worktree = 一个需求。用户自己建 worktree，你不管。

## 命令

| 输入 | 动作 |
|---|---|
| `/dev-workflow` | 读 STATE，报告当前阶段 / 下一步 / 阻塞，**然后停**。零副作用 |
| `/dev-workflow <一句话需求>` | 开新需求 → 阶段 0 |
| `/dev-workflow go` | 执行下一阶段 |

### 推进指令认字面，其余参数按语义理解

这两类东西性质不同，别混着办：

**推进**（`go`）承载的是「我批准你做有副作用的事」。判断错的方向是**多做**，
代价不对称，所以只认白名单，不做语义推断：

- 算：`go` · `继续` · `下一步` · `推进`
- **不算**：`可以` · `没问题` · `同意` · `有道理` · `对` —— 这些只批准了结论

白名单是可枚举的。不在表上又像是要推进的，问一句，别自己往外扩。

**其余的话承载的是信息，不是授权** —— 猜错了最多多问一句，所以按语义理解，
不要求固定格式。用户说「方案得重做」，你就该知道是回阶段 1 重写 PLAN；说
「T3 那块重来」，你就该找到对应子任务。不要求他记阶段编号，也不要求他用
特定句式。

### 一条通用判据

> **你主动提了具体问句、用户直接回答 → 是明确指令。
> 用户没被问、泛泛说「可以」→ 不算。**

前者是用户在回应一个有确定后果的选择，后者是你在猜他的意思。所有需要用户
拍板的地方都走前者：把选项和后果列清楚再问，不要等一个暗号。

## 开新需求时

1. `.dev/` 已存在且 STATE 未完成 → 报告「当前有未完成的需求」并停，
   不要覆盖
2. 建 `.dev/`，写初始 STATE，进阶段 0

`.dev/` 的 git 排除由用户自己管，你不碰 —— 不检查、不写 `exclude`、
不建 `.gitignore`。

## 阶段与输入表

**这张表是权威。** 阶段文件里写的输入以这里为准。

| # | 阶段 | 正向输入 | 回流时额外加 | 产出 |
|---|---|---|---|---|
| 0 | 澄清 `clarify.md` | 项目 CLAUDE.md · README · 代码 | DECISIONS | BRIEF |
| 1 | 方案 `plan.md` | BRIEF · 代码 | CHALLENGE · DECISIONS | PLAN |
| 2 | 挑战 `challenge.md` | BRIEF · PLAN · 代码 | 复审，见下表 | CHALLENGE |
| 3 | 开发 `build.md` | 子任务条目 · BRIEF · 项目 CLAUDE.md | REVIEW 里对应的条目 | 代码 · commit · LOG |
| 4 | Review `review.md` | diff · PLAN · BRIEF · 代码 | 复审，见下表 | REVIEW |
| 5 | 验收 `verify.md` | BRIEF · 代码 · 项目 CLAUDE.md | 复审，见下表 | 验收结果 |

**做事的角色（0/1/3）回流时才加历史**，否则会重复提已被否决的方案。

### 找问题的角色（2/4/5）：全量审 ≠ 复审

第 1 轮和后面的轮次做的**不是同一件事**，输入也不该一样：

| | 输入 | 任务 |
|---|---|---|
| **第 1 轮 · 全量审** | 上表的正向输入，**不知道任何前情** | 发现问题 |
| **第 2+ 轮 · 复审** | 上一轮的 blocking 清单 + **增量 diff**（只有这次修复动的部分）+ 已否决 optional 的标题清单 | 只答两件事：这几条修好了吗？修的时候引入新问题了吗 |

复审的审查面**每轮严格缩小**，所以循环必然收敛 —— 这是「一直修到没有必须
改的问题」能真正走到终点的原因。全量重审做不到：同样的输入、同样的「去找
问题」指令，第二轮会报出一批上一轮没提过的新 blocking，永远到不了头。

独立性保留在最要紧的第 1 轮 —— 它拿不到任何前情，也拿不到「这个方案是
怎么想出来的」。

**否决清单只给标题**，不带内容和理由：够它认出「这条别再报了」，不足以
锚定它对新问题的判断。

**只有一种情况重开全量审**：BRIEF 或 PLAN 发生了实质变更 —— 审的对象换了，
不再是同一份东西。这时轮次清零。

阶段 0 跑在主会话（要跟用户来回），1–5 一律 fresh subagent。

## 推进的门

每个阶段结束，你**逐条核对该阶段的完成判据**：

- 全满足 → 更新 STATE，告诉用户可以 `go`
- 有不满足 → **不许推进**。报告缺哪几条，回到本阶段补

判据是阶段文件里的 `## 完成判据`。不要凭感觉说「差不多了」。

## 循环的终止条件

**终止条件是「没有必须改的问题」，不是「跑满 N 轮」。** 有 blocking 就修，
修完复审，一直到复审报「全部修好、没引入新问题」为止。

轮次上限（challenge / review / verify 各 **3 轮**，计数记在 STATE）是**熔断器**，
不是验收标准。它触发的意思是「这里不对劲，叫人」，不是「算过了」：

- 轮次用尽 → **不许自己续**。停下来，把剩余的 blocking 逐条列清楚，问用户
  「要我再跑一轮，还是你先处理？」
- 用户明确说续 → 续一轮，往 DECISIONS 记一条。**这时候光敲 `go` 不够** ——
  你要的不是推进授权，是他对这几条 blocking 的处置意见
- BRIEF 或 PLAN 实质变更 → 轮次清零，下一轮回到全量审

轮次在**派 subagent 之前**加一 —— subagent 挂掉也算用掉一轮，否则计数
永远对不上。

**没有回退命令。** 用户中途说「方案得重做」「这个子任务重来」，就走对应
阶段的正常回流：产物覆盖写，轮次按上面那条「实质变更」清零。已经 commit
的代码不回滚 —— 由后续子任务或返修 commit 覆盖，要动历史用户自己
`git revert`，你不碰。

需求本身变了（不是方案错了，是要做的事变了）→ 那是**新需求**，按「一个
worktree 一个需求」重开，不要在原来的 `.dev/` 上改。

## 你（主会话）独占的三件事

1. **STATE.md 只由你写。** subagent 一律不碰 —— 它们是隔离的，不该知道
   全局状态
2. **commit 只由你做。** 见 `phases/build.md` 的 commit 规则
3. **PR.md 只由你渲染。** verify subagent 只返回验收结果；渲染需要
   BRIEF + DECISIONS + 验收结果，那是全局视野的活

## DECISIONS.md 的写入规则

**只在这三种时刻追加**，其余一概不写：

- 发生**回退**时：退到哪个阶段、为什么退
- blocking 被用户**明确接受**（而不是修复）时：接受了什么、理由
- 用户在拍板时做的**选择**：选了什么、排除了什么

BRIEF 的「已确认的决策」和 PLAN 的「排除的方案」里已有的，不要重复抄
过来 —— DECISIONS 记的是**过程中的转折**，不是决策汇总。

## STATE.md 模板

覆盖写。**长度必须恒定** —— 它的价值就是让第 6 周恢复和第 1 天一样便宜。

````markdown
# STATE

- **需求**：<一句话>
- **当前阶段**：3 · 开发
- **下一步**：跑并行组 2（T2, T4）
- **阻塞**：无
- **等你拍板**：无
- **轮次**：challenge 1/3 · review 0/3 · verify 0/3

## 进度
- [x] 0 澄清
- [x] 1 方案
- [x] 2 挑战
- [ ] 3 开发 ← 当前
- [ ] 4 Review
- [ ] 5 验收
````

## 恢复协议

用户隔了几周回来，敲 `/dev-workflow`：**只读 `BRIEF.md` + `STATE.md`**。
这两份长度恒定，所以恢复成本不随项目时长增长。
`LOG` / `DECISIONS` / `CHALLENGE` / `REVIEW` 默认不读，按需查。
