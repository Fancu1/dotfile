# 阶段 5 · 验收

跑 BRIEF 的验收清单，逐条拿出证据。回答「100% 满足需求了吗」。

## 谁跑

**fresh subagent**。输入：`.dev/BRIEF.md` + 代码库 + 项目 CLAUDE.md。

**不给 `LOG.md`、不给 `PLAN.md`、不给 diff。**

这不是为了省上下文 —— 是因为它的任务是**独立验证最终结果**，不是检查
开发过程。给了 LOG 它就会去抄里面「已通过」的记录。

## 铁律

1. **每条验收标准都要有这次跑出来的实际输出**，含 exit code。
2. **没有输出的记「未验证」，不许记「通过」**。
3. **不许用「应该可以」「逻辑上没问题」代替执行。**
4. 二元判定类（不是命令的）验收标准，必须写明**判断依据** —— 看了哪个
   文件的哪一行、做了什么操作、看到了什么。

## 两类检查

### 一、BRIEF 验收清单

逐条跑，逐条记录。每条给三个字段：命令 / 实际输出 / 结论。

### 二、回归 —— 旧的有没有被弄坏

BRIEF 的验收清单只覆盖新功能，不会写「别的别坏」。所以必须另跑：

- 项目完整测试套件 → 全绿
- lint / typecheck → 通过
- 能构建 / 能启动

具体命令从**项目 CLAUDE.md** 读。项目 CLAUDE.md 没写这些命令 → 停下来
告诉用户补上，不要自己猜一个跑。

## 结果分级

| 结论 | 含义 |
|---|---|
| **通过** | 有实际输出，且符合预期 |
| **未通过** | 有实际输出，不符合预期 |
| **需人工确认** | 无法自动验证（比如要人眼看效果）。**必须列出让用户怎么确认** |

「需人工确认」不算失败，但整个阶段**不能在还有未确认项时宣布完成** ——
要停下来等用户确认。

## 失败怎么办

- **验收不过 / 回归挂了** → 回阶段 3 修，修完重跑，**一直循环到每条都通过
  为止**。终止条件是「全过」，不是「跑满几轮」
- **发现是验收标准本身写错了** → **不许自己改 BRIEF**。停下来报告，由用户
  决定要不要 amend。BRIEF 是锚点，能被随手改的锚点等于没有
- 轮次用尽还不过 → 停下来让用户介入，不许自己续

重跑时只跑**上一轮未通过的那几条** + 回归三项，已经通过的不用重跑。
验收清单是固定的、不存在「重新发现」，所以这个循环天然收敛 —— 不需要像
阶段 2 / 4 那样区分全量审和复审。

## 收尾 —— 由主会话做，不是 verify subagent

verify subagent 只跑验收、返回结果。以下三件事由主会话完成
（它才有 BRIEF + DECISIONS + 验收结果的全部视野）：

1. 渲染 `.dev/PR.md`（模板见下）
2. 更新 `.dev/STATE.md` 为「已完成，待推送」
3. 告诉用户可以推送和开 PR ——
   **按全局 CLAUDE.md，推送和开 PR 要先问用户，不要自己执行**

## 完成判据

- [ ] BRIEF 每条验收标准都有这次的实际输出，且结论是「通过」
- [ ] 回归三项（测试 / lint / 构建）全绿，且有输出
- [ ] 没有遗留「需人工确认」项（或用户已确认）
- [ ] 主会话已渲染 `.dev/PR.md`
- [ ] 主会话已更新 `.dev/STATE.md`

## PR.md 模板

写到 `.dev/PR.md`。手动提 PR 时 `gh pr create --body-file .dev/PR.md`。

````markdown
## 需求
<BRIEF 的「意图」，一段话>

## 验收
| 标准 | 命令 | 结果 |
|---|---|---|
| <验收 1> | `pytest tests/x.py` | ✅ 12 passed, exit 0 |

**回归**：测试 ✅ / lint ✅ / 构建 ✅

## 决策
<DECISIONS.md 要点：选了什么、排除了什么、为什么>

## 不做什么
<BRIEF 的范围边界。防止后来的人以为是遗漏>
````
