# 阶段 2 · 挑战方案

在写任何代码之前，把 PLAN 往死里挑。方案阶段推翻的成本是几分钟，
代码写完再推翻是几小时。

## 谁跑

**fresh subagent**。输入**只有** `.dev/BRIEF.md` + `.dev/PLAN.md` + 代码库。

**绝对不要**把阶段 0、1 的对话上下文传给它 —— 它必须看不到「这个方案
是怎么想出来的」，只看结果。这是这个阶段唯一的隔离手段，破了就没有
独立视角了。

## 铁律

1. **任务是反驳，不是评审**。默认立场是「这个方案有问题」，要主动去找
   它在哪会崩，而不是逐条打勾。
2. **blocking 和 optional 必须分开**。
   - **blocking**：会导致 BRIEF 某条验收标准不满足 / 会引入正确性问题 /
     会破坏现有功能
   - **optional**：其他一切 —— 风格、「可以更好」、「将来可能有问题」

   混在一起报 = 用户会去追着修 optional，那就是过度设计。
3. **「没有 blocking」是合格结论**。方案确实没问题就直说，不要为了证明
   自己审过而硬凑几条。凑出来的 finding 比不审更糟。
4. **指出问题必须给替代方案**。说不出更好的做法，那条就降级成 optional
   或者干脆不报。

## 挑战清单（逐个视角过一遍）

| 视角 | 追问 |
|---|---|
| **覆盖** | BRIEF 每条验收标准，PLAN 真的覆盖到了吗？「覆盖检查」表有没有糊弄 |
| **正确性** | 哪个子任务的验证方式是假的（跑了也证明不了它完成）？边界情况漏了吗 |
| **简单性** | 有没有明显更简单的做法？「排除的方案」里排除得站得住脚吗 |
| **维护性** | 半年后接手的人会在哪里骂？巨型文件、错误抽象、隐式约定 |
| **依赖** | 引入的库是不是必要？采用度够吗？有没有更主流的选择 |
| **判据例外** | PLAN 里写了理由的每一条例外，理由成立吗 |
| **风险** | 这个方案最可能在哪一步翻车？翻了能不能回滚 |

**「判据例外」和「引入的依赖」两栏是重点靶子** —— 那是阶段 1 自己标出来
的可疑之处，优先打。

## 挑战之后

- **blocking** → 回阶段 1 改 PLAN，改完**复审**（见下），一直循环到无
  blocking 为止。终止条件是「没有必须改的问题」，不是「跑满几轮」
- **optional** → 交给用户决定，采纳的写进 PLAN
- **轮次用尽仍有 blocking** → 停下来让用户介入，不许自己续。到这一步说明
  BRIEF 本身可能有问题，也许要回阶段 0

## 复审（第 2 轮起）

输入换成：**上一轮的 blocking 清单** + **改动后的 PLAN**（标出改了哪几段）
+ 已否决 optional 的标题清单。**不重新全量审。**

只回答两件事：

1. 上一轮每条 blocking，改后真的解决了吗
2. 这次改动本身有没有引入新的 blocking

**不要去挖上一轮没提过的老问题** —— 那是第 1 轮全量审的活。你现在的任务
是收敛，不是再发现一批。否决清单上的 optional 一律不许再报。

## 完成判据

- [ ] 七个视角都过了（可以合并报告，但不能跳过）—— **仅第 1 轮全量审要求。
      复审改成逐条列上一轮 blocking 的处置**
- [ ] 每条 finding 都标了 blocking / optional
- [ ] 每条 blocking 都给了替代方案
- [ ] 所有 blocking 已解决，或用户明确接受
- [ ] **仅当**发生回退、或有 blocking 被用户明确接受时，才往
      `.dev/DECISIONS.md` 追加一条。全部修掉了就不用写 —— DECISIONS
      记的是转折，不是审查流水

## CHALLENGE.md 模板

写到 `.dev/CHALLENGE.md`（每轮覆盖写，历史进 `DECISIONS.md`）。

````markdown
# CHALLENGE: <需求名> · 第 N 轮 · <全量审 / 复审>

## 结论
<一句话：有 N 条 blocking / 无 blocking，可以进开发>

## Blocking

### B1 · <标题>
- **问题**：<具体会怎么崩>
- **影响**：<对应 BRIEF 的哪条验收 / 什么正确性问题>
- **替代方案**：<怎么改>

## Optional

### O1 · <标题>
- **问题**：
- **建议**：
- **不改的后果**：<让用户能判断值不值得改>

## 过了的视角
<七个视角里没发现问题的，一行带过，证明确实过了>
````
