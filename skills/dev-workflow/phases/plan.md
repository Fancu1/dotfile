# 阶段 1 · 方案

把 BRIEF 变成一份**可执行的 PLAN.md**：子任务、依赖、每步怎么验证。

## 谁跑

**fresh subagent**，输入只有 `.dev/BRIEF.md` + 代码库。
**不要带澄清阶段的对话上下文** —— 那里面全是被否决的方向和试探性想法，
带过来只会干扰。subagent 直接写 `.dev/PLAN.md`，主会话读文件给用户看。

## 铁律

1. **这一阶段不写任何代码**，产物只有 PLAN.md。
2. **先读再写**。动笔前把要改的地方、既有的同类实现、能复用的东西读完。
   凭空出的方案在阶段 2 一挑就碎。
3. **每个子任务必须能独立验证**。说不清「怎么验证它完成了」= 拆得太大，
   继续拆。

## 设计判据（双向 —— 不是越少越好）

用户要的是「架构清晰、易维护、不过度设计」。**过度设计和设计不足是
两个反方向的失败，判据两边都要卡。**

### 抽象 —— Rule of Three

- 相同逻辑重复 < 3 处 → **不要**抽象。临时的重复比错误的抽象便宜
- 重复 ≥ 3 处 → **必须**抽象，不许继续复制
- 只有 1 个调用点就建接口 / 基类 / 配置项 = 不合格
- 「将来可能会用到」不构成抽象的理由

### 第三方库 —— 默认应该用，不要造轮子

- 成熟库能解决的优先用库。自己写的每一行都是将来要维护的
- 满足**任一**条才自己实现：
  - 需要的功能 < 50 行能写完，而库会带进一整套用不上的东西
  - 库不过质量线
- 质量线（全满足）：最近 12 个月有提交或发布 · 有 CI 和测试 · 许可证兼容
- **在 PLAN 里写出这个库的下载量 / star 数和最近发布时间**，让阶段 2
  能判断采用度够不够。存疑时跑 OpenSSF Scorecard，≥ 6 分再用

### 文件与函数 —— 防巨型文件

- 单文件 > 500 行 → 拆。不拆要写理由（项目 CLAUDE.md 可以覆盖这个数字）
- 一个文件只服务一个主题。什么都往里塞比多开几个文件难维护得多
- **新建文件不需要理由 —— 需要理由的是「不拆」**

### 防御性代码

- 不为不可能发生的情况写处理。写了就要说明它什么时候会触发

---

违反以上任何一条不是绝对禁止，但**必须在 PLAN 里写明理由** —— 那是写给
阶段 2 挑战者看的靶子。判据只负责挡住高频错误，具体的设计判断交给
阶段 2 的跨模型挑战，不要指望用判据穷举所有质量维度。

## 流程

1. **读 BRIEF**，逐条列出验收标准
2. **读代码**，找到要改的地方和可复用的实现
3. 需要引入新库 / 新模式时，按全局 CLAUDE.md 的来源优先级查一下主流做法
4. **拆子任务**：一个子任务 = 一个可独立验证的改动 = 一个 commit。
   **子任务标题直接写成 commit subject**（`type(scope): 描述`），
   阶段 3 照抄不再判断，阶段 2 也才审得了 commit 拆分是否合理
5. **共享的新增物拆成前置子任务**：多个子任务都要用到的工具函数、
   类型、配置，单独拆一个前置子任务，不要留给并行组各写一份
6. **标依赖和文件集合**，算出并行分组
7. **回头对 BRIEF**：每条验收标准都有子任务覆盖到了吗
8. 写 PLAN.md

## 完成判据（全满足才能进下一阶段）

- [ ] BRIEF 的每条验收标准，都能指到至少一个子任务
- [ ] 每个子任务标题都是合法的 `type(scope): 描述`，可直接当 commit subject
- [ ] 每个子任务都有「改动文件」和「验证方式」，验证是命令或二元判定
- [ ] 依赖关系明确，并行分组已算出（文件集合不相交才能同组）
- [ ] 多个子任务共同依赖的新增物已拆成前置子任务，没留给并行组各写一份
- [ ] 违反设计判据的地方，都写了理由
- [ ] 引入的新库都写了下载量 / star / 最近发布时间
- [ ] 没有任何代码被写出来

## PLAN.md 模板

写到 `.dev/PLAN.md`。

````markdown
# PLAN: <需求名>

## 方案概述
<一段话：整体怎么改，为什么是这个方案>

## 排除的方案
- **<方案 A>**：<为什么不选>

## 引入的依赖
| 库 | 用途 | 下载量 / star | 最近发布 | 为什么不自己写 |
|---|---|---|---|---|
| | | | | |

## 子任务

<标题就是 commit subject，阶段 3 直接照抄>

### T1 · feat(parser): 支持 YAML 配置文件
- **改动文件**：`a.py` `b.py`
- **依赖**：无
- **复用**：<项目里的哪个现有实现> / 无（原因：…）
- **做什么**：<具体到能直接动手>
- **验证**：`<命令>` → 期望 <结果>

### T2 · fix(loader): 修正空文件时的报错
- **改动文件**：`c.py`
- **依赖**：T1
- …

## 并行分组
- 组 1（可并行）：T1, T3
- 组 2（依赖组 1）：T2

## 覆盖检查
| BRIEF 验收标准 | 由哪些子任务覆盖 |
|---|---|
| <验收 1> | T1, T2 |

## 判据例外
<违反设计判据的地方 + 理由。没有就写「无」>
````
