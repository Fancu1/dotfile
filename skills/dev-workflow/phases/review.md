# 阶段 4 · Review

**假设方案是对的**（阶段 2 已经审过），只看实现有没有跑偏、写得好不好。

## 谁跑

**fresh subagent**。输入：**diff** + `.dev/PLAN.md` + `.dev/BRIEF.md` + 代码库。

不给 `CHALLENGE.md`（意见已吸收进 PLAN），不给 `LOG.md`（验证的真伪是
阶段 5 的活），不给任何开发过程的对话上下文。

## 边界：审什么，不审什么

**不审**（阶段 2 已定，重提就是跟已拍板的决策打架）：

- 模块怎么拆、要不要抽象、抽象得对不对
- 用了哪个第三方库
- 文件怎么组织、整体架构

**审**（在既定方案之内）：

- 实现是不是真的按 PLAN 做的
- 这段代码本身写得对不对、好不好
- 有没有偷懒

**万一真的发现方案层面的严重问题** → 单独放进「方案疑虑」一栏，**不算
blocking**（除非它直接导致 BRIEF 某条验收不满足），交给用户判断要不要
回炉阶段 1。不要把它混进实现问题里。

## 铁律

1. **blocking 和 optional 必须分开**。被要求找问题的 reviewer 一定会找出
   问题，追着修 optional 就是过度工程。
2. **「没有 blocking」是合格结论**。不要为了证明审过而硬凑。
3. **每条 finding 指到具体的 `文件:行`**。指不出位置的意见一律不报。

## 检查清单

### 一、符合方案吗

- PLAN 要求的，有没有漏做
- PLAN 没要求的，有没有多做（范围蔓延）
- 实现方式跟 PLAN 说的一致吗？换了做法但没说明 = blocking

### 二、代码质量（既定方案内）

- **正确性**：逻辑对吗？边界情况（空值 / 空集合 / 超长 / 并发）处理了吗
- **实现选择**：同样的效果有没有更简洁或更地道的写法？AI 写的往往能跑
  但不是最合适的
- **一致性**：跟项目现有的写法、命名、错误处理模式一致吗
- **可读性**：命名说得清吗？嵌套层数、单函数长度是不是过头了

### 三、偷懒信号（只判 diff 的 `+` 行，发现即 blocking）

这些是「假装完成」，比写得不够好严重。

**只看本次 diff 新增的行。** 你的输入里有整个代码库，但你审的是这次改动 ——
仓库里原有的同类问题一律不报（真的很严重就进 optional）。把存量问题算到
这次头上，等于让用户去修一堆跟需求无关的东西。

- 遗留 `TODO` / `FIXME`，而 PLAN 里没说要留
- 捕获异常后 `pass` / 空 catch / 吞掉错误不上报
- 该配置的值硬编码在代码里
- 函数签名有参数但从没被用到
- 测试是空的、只 `assert True`、或者只测了 happy path 而 PLAN 要求测边界
- 注释里写着「简化实现」「暂时这样」「先这么写」

## Review 之后

- **blocking** → 回阶段 3 修，修完**复审**（见下），一直循环到无 blocking
  为止。终止条件是「没有必须改的问题」，不是「跑满几轮」。返修的 commit 走
  `fix(scope): 描述`，不照抄原子任务标题（见 `build.md` 的「返修 commit」）
- **optional** → 用户决定。采纳的先**往 PLAN 末尾追加子任务 `T{n+1}`**、写清
  它的改动文件，再走阶段 3 —— 不追加的话，阶段 3 的「声明外文件」检查会
  把它当越界拦下来
- **轮次用尽仍有 blocking** → 停下来让用户介入，不许自己续

## 复审（第 2 轮起）

输入换成：**上一轮的 blocking 清单** + **增量 diff**（只有返修 commit 动的
那部分）+ 已否决 optional 的标题清单。**不重新全量审整个改动。**

只回答两件事：

1. 上一轮每条 blocking，改后真的解决了吗（指到修复的 `文件:行`）
2. 返修本身有没有引入新的 blocking

**不要去挖上一轮没提过的老问题** —— 那是第 1 轮全量审的活。你现在的任务
是收敛，不是再发现一批。否决清单上的 optional 一律不许再报。

## 完成判据

- [ ] REVIEW.md 的「已过的检查项」三行都写了（主会话照着数，不靠感觉）
      —— **仅第 1 轮全量审要求。复审改成逐条列上一轮 blocking 的处置**
- [ ] 每条 finding 标了 blocking / optional，且指到 `文件:行`
- [ ] 偷懒信号类的 finding，指到的行都在本次 diff 的 `+` 里
- [ ] 所有 blocking 已修复，或用户明确接受
- [ ] 「方案疑虑」（如果有）已经交给用户判断
