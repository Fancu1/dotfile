# 阶段 0 · 澄清

把一句话需求变成一份**可执行的 BRIEF.md**。没有 BRIEF 不许进下一阶段。

## 铁律

1. **例子 ≠ 边界**。用户给的目标、角度、数量、示例全是示意，不是枚举。
   要挖例子背后的意图，主动拓展用户没说出、甚至没意识到的需求。
   只覆盖用户自己能看到的角度 = 不合格。
2. **不许附和**。用户的需求可能不合理，用户给的方案可能不是最优。
   判断有问题就先说出来 —— 这个阶段附和的代价会在后面每一环放大。
3. **能读出来、能查出来的，绝不拿去问用户**。问了显得没做功课，
   也白白消耗提问轮次。
4. **没得问就说没得问**。需求已经清晰就直接说「可以写 BRIEF 了」，
   不要为了显得认真硬凑问题。

## 流程

### 第 1 步 · 读项目

读项目 CLAUDE.md、README、相关代码、既有的同类实现。
搞清楚：现在是怎么做的、有什么能复用、这个需求会碰到哪些地方。
**这一步的产出不是给用户看的，是后面出选项的原料。**

### 第 2 步 · 查外部

用户的需求不一定合理，用户的解法不一定最优。去看这个场景在成熟
产品 / 顶级开源项目里是怎么解决的，按全局 CLAUDE.md 的来源优先级查。

- 涉及**做什么 / 产品形态 / 交互方式** → 必须查
- 纯技术实现、明确的小改动 → 跳过，别浪费时间

查到的东西**不要写成报告扔给用户**，要融进第 3 步的选项里。

### 第 3 步 · 交互式提问（主力）

用 AskUserQuestion，一轮 ≤ 4 题。开放式提问只在选择题实在做不出来时用。

**选项的质量线（不满足就别问）：**

- 每个选项带**一句话解释它意味着什么** —— 用户可能只看到 label
- 推荐项放**第一个**，label 末尾标「(推荐)」
- 选项要么带上**项目现状**（「你现在是 X，改成 Y」），要么带上
  **外部参照**（「A 项目的做法是……，另一种主流做法是……」）。
  两样都没有 = 这个问题是凭空臆测的，回第 1、2 步
- 不问显而易见的，专挑用户可能没想到的硬骨头

**连意图也可以做成选择题** —— 读完项目后给出 2-3 个对「你到底想解决
什么」的不同解读让用户选。用户往往说不清自己要什么，但一眼能认出
哪个是对的。

**要覆盖这六个维度**（不是每个都要单独一题，能合并就合并）：

| 维度 | 要问出什么 |
|---|---|
| 意图 | 想解决的**问题**是什么（不是想要的功能） |
| 边界 | 什么明确**不做**。至少 1 条 |
| 验收 | 怎么算做完 —— 追到能写出命令或二元判据为止 |
| 已有 | 复用什么、替换什么 |
| 约束 | 不能动什么、必须兼容什么、上限 |
| 失败 | 什么情况算失败、最坏会怎样 |

每轮问完要**推进边界**，不能原地打转。连续两轮没有新信息 → 说明
剩下的用户也答不上来，你来提议，让他否决。

### 第 4 步 · 写 BRIEF.md，给用户过目

用户明确认可后这一阶段才结束。

## 完成判据（全满足才能进下一阶段）

- [ ] 验收标准每条都是**可执行命令**或**二元判定问句**，无形容词
- [ ] **至少 1 条验收标准不经过项目的测试文件** —— 跑 CLI、打接口、执行
      脚本，从外面看结果。全靠 `pytest tests/test_new.py` 这类命令的话，
      「100% 满足需求」等于「通过了实现者自己写的断言」
- [ ] 「不做什么」至少 1 条
- [ ] 「意图」写的是问题，不是功能清单
- [ ] 第 2 步查到的外部做法，要么被采纳、要么在「已确认的决策」里
      写明为什么不采纳
- [ ] 用户明确认可 BRIEF

任一条不满足 → 回第 3 步继续，不许带着模糊的 BRIEF 往下走。

## BRIEF.md 模板

写到 `.dev/BRIEF.md`。**定稿后只许在末尾追加 amend，不许重写正文** ——
它是后面所有环节的锚点，改了就没有「100% 满足需求」这个说法了。

````markdown
# BRIEF: <需求名>

## 意图
<要解决的真实问题。一段话。不是功能描述>

## 范围
**做**
-

**不做**
-

## 验收标准
<每条必须能跑或能二元判定。这份清单后面会被 challenge / review /
verify 三个阶段直接当评分表用>
- [ ] `<命令>` → 期望 <结果>
- [ ] <二元问句>

## 约束
- <不能动什么 / 必须兼容什么 / 上限>

## 已确认的决策
- <澄清过程中拍板的，含被排除的选项和原因>
- <第 2 步查到但没采纳的外部做法，写明为什么>

---
## Amendments
<定稿后的补充追加在这里，带日期>
````
