# Medium 流程

目标：先完成影响分析和一次明确方案批准，再连续实现、独立检查并验收。

## 方案阶段（只读）

1. 读取当前实现、相关历史、测试和项目约定。
2. 输出完整但紧凑的影响面地图。
3. 给出方案卡：
   - 目标与非目标。
   - 当前行为与根因/缺口。
   - 推荐方案、关键取舍及被放弃的主要方案。
   - 触达路径及各自职责。
   - 可观察的验收条件。
   - 验证计划、风险和未知项。
4. 明确询问用户是否按该方案开始实现。把用户对讨论结论的认可与实施授权分开判断。

## 实施阶段（批准后）

1. 按可验证的增量组织实现，但保持需求上下文连续，不为每个小步骤重新审批。
2. 每个增量先做贴近行为的检查，及时发现方向错误；不要等全部完成后才验证。
3. 仅在触达路径互不重叠且合并边界明确时并行；主代理负责整合、冲突检查和最终判断。
4. 完成后执行一次独立 Review，重点检查验收遗漏、调用方回归、错误路径、契约变化和不必要复杂度。
5. 修复阻断项并复验。可选改进不混入阻断修复，除非用户扩展范围。
6. 运行聚焦测试、相邻回归，以及与公共影响相称的类型检查、lint 或构建。
7. 按交接卡交付，说明实现链路、方案偏差、验证证据和残余风险。

## 状态与文件

优先使用当前任务的计划状态，不默认写入仓库。只有任务确实跨会话、上下文容易丢失且项目允许时，才使用 `.agent-work/current-plan.md`；先确认它不会覆盖已有状态且不会意外进入版本控制。不要擅自修改 `.gitignore`。

不自动提交代码，不为单个子任务强制创建 commit。
