# Large 流程

目标：先锁定系统不变量和可恢复边界，再分批实施并证明兼容、迁移与发布安全性。

## Gate 1：范围与不变量（只读）

1. 建立基线：当前调用链、数据流、关键行为、性能/可靠性现状和已知缺陷。
2. 列出必须保持的不变量：数据完整性、兼容性、权限、安全、可用性和用户可见行为。
3. 明确目标、非目标、成功指标、禁止触碰区和未知项。
4. 请用户确认范围与不变量。未确认前不修改项目文件，也不创建项目内流程文档。

## 设计与挑战

Gate 1 通过后：

1. 完成深度影响面地图，覆盖生产者、消费者、契约、数据、权限、可观测性和发布链路。
2. 设计目标架构及过渡状态，明确迁移顺序、向后/向前兼容、双写或回填策略、失败恢复和回滚边界。
3. 将实施拆为可独立验证、可停止或可回退的批次；标明批次依赖、触达路径和验证门。
4. 给出测试矩阵：单元、集成、端到端、迁移演练、性能/容量、安全和故障场景中哪些必须执行。
5. 若可用，使用独立新视角做 challenge，专门寻找遗漏消费者、不可逆步骤、兼容缺口、失败模式和更小替代方案。主代理裁决并合并结论。

## Gate 2：方案与批次

向用户提交架构、迁移、兼容、回滚、发布、验证方案和批次顺序。只有明确批准后才进入实现；影响核心契约的方案变化需重新批准。

## 分批实施

1. 每批开始前确认前置条件与回退点，结束后立即执行该批验证并更新状态。
2. 不并行修改重叠的核心路径。可并行的调查、测试或独立模块必须有清晰所有权和合并边界。
3. 保持兼容层和迁移代码可识别，记录移除条件；不要把临时过渡状态永久化而不说明。
4. 独立 Review 覆盖整体设计和增量 diff，不把复审限制为上一轮发现。
5. 阻断项修复后重跑相关批次验证，并检查修复引入的新回归。

## 集成与发布准备

1. 运行批准的测试矩阵，区分已通过、未运行、环境阻塞和既有失败。
2. 演练或静态核对迁移、回滚、灰度、监控、告警和应急操作；没有权限时只提供可执行步骤，不代替用户执行。
3. 交付 release-readiness 结论：是否可发布、必要前置条件、阻断项、观察指标、回滚触发条件和责任边界。
4. 不自动部署、提交、推送或创建 PR。

## 状态文件

跨会话或多批次任务可在 Gate 1 批准后使用 `.dev/STATE.md`、`BRIEF.md`、`PLAN.md`、`DECISIONS.md`。若 `.dev/` 已存在，先读取并确认归属，绝不覆盖另一项活动任务。具体格式见 `handoff-and-artifacts.md`。
