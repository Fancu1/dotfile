# 覆盖与范围选择

## 每次开始的快速全局检查

检查项目根、当前 ref/HEAD、工作区状态、主要入口、模块地图、历史游标、未关闭 finding 和覆盖表。这个步骤用于选择范围，不代表完成全局 Review。

## 选择优先级

按顺序评估：

1. 未关闭 finding 的相关路径在本次再次变化。
2. 上次审计后发生变化的核心行为及其调用方、消费者和测试。
3. 重要但从未 Review、只 `mapped`、长期未复查或置信度降低的模块。
4. 轮换一个尚未覆盖或结论陈旧的全局关注面。
5. 长期未变化但位于关键业务链路的区域抽样。

范围受限时，优先保留高风险、变化活跃和未知程度高的区域。不要用固定文件数假装合理预算。

## 三条覆盖视线

### Change Coverage

- 计算历史游标到当前目标 commit 的变化。
- 追踪修改符号的直接调用方、消费者、配置和测试。
- 检查新代码是否延续或放大既有坏模式。
- 仅看 diff 不足以理解行为时，读取所在模块的完整职责和调用链。

### Module Coverage

覆盖深度：

- `none`：没有 Review。
- `mapped`：只确认职责、入口和边界。
- `sampled`：检查过关键路径或代表性代码。
- `deep`：检查核心链路、失败路径、消费者和测试安全网。

覆盖不是永久有效。核心行为、接口、依赖方向、上游契约或主要消费者发生实质变化时，降低置信度并重新进入选择范围。

### System Coverage

从全项目角度轮换检查：

- 模块边界与依赖方向。
- 领域对象、状态模型和公共契约的一致性。
- 错误处理、重试、并发和资源生命周期。
- 配置、权限、日志、指标和可观测性。
- 核心业务链路的测试安全网。
- 重复能力、废弃兼容层和绕过核心抽象的实现。

全局 Review 是跨模块综合，不要求每次逐文件扫描。

## Git 与工作区规则

- 不 fetch、不 checkout、不 reset；只使用本地已有 refs 和对象。
- 先用 Git 顶层目录确定项目身份。用户指定仓库内子目录时，仅将其作为本次范围；模块覆盖和跨模块影响仍相对仓库根判断。
- 逻辑子项目身份必须由用户明确选择。其 ID 基于父仓库身份和规范化相对路径，并在项目状态中记录父仓库；不同 clone 中的同一相对路径应映射为同一身份。
- 默认审计用户指定的本地 ref；未指定时审计当前 HEAD。
- 工作区不干净时默认排除未提交变化。对受影响文件尽量从目标 commit 读取；无法可靠隔离时缩小范围并说明。
- 只有用户在专项审计或复查旧结论时明确要求，才能纳入未提交内容。记录实际读取的相对路径、Git 状态和文件 SHA-256；不记录源码内容，也不读取或散列凭证、`.env` 等敏感文件。快照只能证明所审内容版本，不能充当 Git commit。
- 使用 ancestry 检查验证历史游标。若旧 commit 缺失或不是当前目标的祖先：
  1. 记录 `diverged`，不要把普通 diff 当完整增量。
  2. 本地存在共同祖先时，将其作为有限比较起点并明确缺口。
  3. 无可靠共同祖先时执行局部重新建立认知，不覆盖旧报告。
- 同一 remote 的不同 clone/worktree共享项目身份，但分别记录已知路径和本次目标 ref。

## 每次报告必须说明

- 本次 Change / Module / System 三条线分别如何处理。
- 为什么选择这些范围。
- 哪些区域只完成 mapped 或 sampled，不能算 deep。
- 哪些内容延期及下一轮推荐。
