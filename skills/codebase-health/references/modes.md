# 内部路由

这些路由是 AI 的执行细节，不是要求用户记忆的公开命令。先根据自然语言目标、已有状态与项目事实选择；用户使用旧模式词时只将其视为兼容提示。

## 建立项目认知

用于首次接入或历史状态已经不能可信复用的项目。

1. 识别项目目的、技术栈、入口、核心调用链、模块职责和外部边界。
2. 读取测试、构建、静态检查、CI 和运行说明，记录可用验证命令；不为了审计运行高成本或有副作用的命令。
3. 识别生成代码、vendor、构建产物、快照、大型夹具和其他默认排除路径。
4. 建立模块覆盖表与全局关注面覆盖表。
5. 对关键链路和一个代表性高风险区域做抽样，不承诺首次覆盖完整项目。
6. 创建全局状态和 baseline 报告，记录未知区域与下一轮建议。

建立认知只负责形成地图，不等于所有模块都已经 Review。没有实际深入的模块保持 `none` 或 `mapped`。

## 滚动审计

用于常规定期审计，也是默认模式。

1. 加载历史状态并校验审计游标。
2. 评估已有 finding 是否与本次变化相关。
3. 组合增量代码、覆盖缺口和一个全局关注面；受预算限制时明确延期。
4. 更新现有 finding，生成少量新候选和本次 delta 报告。
5. 更新覆盖深度、置信度、下次轮换方向和全局索引。

没有代码变化时，不重复旧结论。优先复查到期 finding、轮换一个未覆盖模块或全局关注面；没有足够价值时报告无需行动。

## 专项审计

用于指定模块、调用链、质量问题、事故范围或大量 AI 生成代码。

1. 明确目标和审计关注点。
2. 深入目标内部，同时检查入口、消费者、共享契约、相邻模块和测试。
3. 若用户明确要求检查未提交实现，可纳入 working tree；否则仍以已提交代码为基线。纳入时按状态格式记录本次实际读取文件的证据快照（相对路径、Git 状态和 SHA-256），不能只记录 `yes`，也不得保存源码内容。
4. 更新目标模块及受影响全局关注面的覆盖状态。
5. 不把专项检查冒充全项目健康结论。

## 复查旧结论

用于复查一个既有 finding 的处理结果。

1. 读取 finding 的原始证据、必须保持项、建议目标和历史状态。
2. 检查问题是否消失、复杂度是否转移、行为和契约是否保持、测试安全网是否增强。
3. 用户明确要求时可验证未提交实现；否则检查当前 HEAD。纳入时记录本次实际读取文件的证据快照（相对路径、Git 状态和 SHA-256），使后续复查能识别内容是否变化，但不得保存源码内容。
4. 更新状态：
   - `resolved`：证据表明问题已解决且未发现相关回归。
   - `observing`：方向改善但证据或运行周期不足。
   - `reopened`：原问题仍存在或出现同根因回归。
5. 保留原 finding ID 和历史，不以新 finding 替代复查结果。
