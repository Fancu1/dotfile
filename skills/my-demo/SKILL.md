# my-demo — 最小可运行版本生成器

把用户贴的一段需求,快速做成一个**能跑通、能直接运行看到效果**的最小可用版本(MVP)。

**成功标准:把需求里给的示例/用例亲自跑通、产出正确结果**。在此之上,再花小成本把输出弄干净。顺序永远是先可用、再好看——绝不为外观牺牲"能不能跑通"。

> **一键运行契约(最高优先级):用户最终只执行一行 `uv run <file>.py`。** 环境、依赖、国内源、Key、配置——全部由你提前备好并验证过,用户不碰任何额外步骤、不传任何参数、不设任何环境变量。

## 核心取向:够跑就停

最小版本的价值是"证明这个想法能 work",不是"经得起线上考验"。逻辑和健壮性上一切多余的东西都砍掉:

- **一个文件**。语言优先 Python(生态全、起步快),但按需求选——交互强可以单个 HTML,需求指定语言就用指定的。
- **只走 happy path**。不写 try/except,不做输入校验,不处理边界异常——跑的是预期输入。
- **不写测试**,不加类型校验仪式,不接 logging / config / 复杂 CLI 框架。
- **依赖最少**,不为"扩展性"留口子,不抽象、不加配置项。
- **内置需求里给的示例输入**,零参数一条命令就能看到结果。
- **文件名按功能起**(如 `todo_extractor.py`),不用 `demo_` 前缀。

注意区分:**砍的是逻辑层的过度设计,不是输出的观感**。输出该干净好读(整齐的表格 / 清楚的排版 / 简单的网页壳);但前提是先跑通,好看用小成本顺手做,别陷进去。

## 流程

1. **读需求、选语言**。判断要不要大模型:语义理解 / 抽取 / 生成 / 分类 → 要;纯逻辑 / 数据处理 → 不要。

2. **要用模型 → 读 `~/.llm/env.md`** 拿 BaseURL、model id、调用方式。别让用户解释 API,别联网搜。

3. **有不确定就交互问,但每个问题带上你最推荐的方案 + 一句理由**,让用户一句话能拍板(例:"输出我建议先用终端表格,最快看到效果,要不要?要不要再套个网页壳?")。只问会改变形态的点(输入来源、输出形态、要不要网页),最多 2-3 个;需求够清楚就直接写,别问废话。

4. **写一个文件**,内置需求里的示例输入,happy path,代码短到一眼看懂。

5. **把一切提前配好,让用户只敲 `uv run <file>.py`**——不拼参数、不传 Key、不设环境变量:
   - **依赖用 PEP 723 内联声明**,写在文件顶部,`uv run` 自动装、自动走国内源(本机已验证):
     ```python
     # /// script
     # dependencies = ["openai", "python-dotenv"]
     # [[tool.uv.index]]
     # url = "https://pypi.tuna.tsinghua.edu.cn/simple"
     # default = true
     # ///
     ```
     这样不用 `--with`、不用 `--default-index`。运行时缺什么依赖(如代理需要 `socksio`),你补进这个列表,别甩给用户。
   - **Key 走 `.env` 自动加载**:你从 `~/.llm/env.md` 取 Key,写进脚本同目录的 `.env`(`DASHSCOPE_API_KEY=...`);代码里 `from dotenv import load_dotenv; load_dotenv()`,再 `os.getenv("DASHSCOPE_API_KEY")` 读。**绝不硬编码、绝不让用户在命令行拼 Key**。`.env` 含明文 Key,别 commit(在仓库目录里就加进 `.gitignore`)。
   - 纯标准库、不需要模型的需求,这步可省,直接 `python <file>.py`。

6. **你亲自用"用户最终要敲的那条命令"(`uv run <file>.py`)把它跑通**。必须用这条命令本身验证——你验证的就是他要执行的,别用额外 flag / 环境变量绕过去跑通,否则交到他手里反而跑不了。跑通、看到正确输出为止;这一跑也顺手把 uv 依赖缓存预热,用户那条命令会秒出。

7. **交付三样**:文件路径、**那条唯一的运行命令**(`uv run <file>.py`)、实际跑出来的结果。

## 不要加载其他 skill

本 skill 自带从读需求到跑通的完整流程,这就够了。别再触发 brainstorming / test-driven-development / writing-plans / systematic-debugging 这些——它们是为更重的任务准备的,只会把"几分钟出活"拖成半小时。遇到 bug 直接读报错改,别上重流程。
