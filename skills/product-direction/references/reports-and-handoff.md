# 报告、讨论与交接

## 本次产品方向报告

```markdown
# Product Direction Review — <product> — <date>

## 中肯结论
<当前最值得做什么；证据不足时说明先学什么>

## 当前产品诊断
- 产品承诺：
- 核心用户与任务：
- 已有能力与闭环：
- 最大摩擦或未知：

## 调研与可迁移原则
<同类替代方案、用户问题证据、跨赛道原则及不适用边界>

## 主要方向
- 目标用户与问题：
- 为什么现在：
- 与现有能力的关系：
- 推荐目标：
- 易用性要求：
- 最小验证：
- 成功信号：
- 风险与未知：

## 备选方向
<最多 2 个，说明何时会优于主要方向>

## 克制清单
<现在不做什么及理由>

## 证据边界与未覆盖
<fact / inference / hypothesis；过期来源与延期问题>

## 运行信息
- Project ID:
- Target commit:
- Working tree observed:
- State updates:
```

面向用户的回答先呈现判断与关键理由，不要求用户阅读内部台账。来源链接放在支持对应判断的位置；状态报告可以保存直接 URL 与本地相对路径。

研究或候选尚在讨论时使用 `proposed`。用户提出修正后更新原机会与方向摘要；不为每条聊天回复机械创建重复报告。一次完整分析、证据实质变化、方向变化或用户明确决定时才写新的 append-only 报告。

## `$dev-workflow` 交接卡

用户明确选择某方向并准备实施时输出：

```markdown
交给 $dev-workflow
- Product direction：<PD-ID + 标题>
- 目标用户与痛点：
- 当前证据：
- 当前能力与缺口：
- 推荐最小范围：
- 必须保持的产品原则：
- 克制与非目标：
- 验收条件：
- 成功信号：
- 建议验证：
- 未知与实施风险：
```

交接卡定义产品问题、边界和可观察结果；实现方案、风险等级、批准门和代码验证由 `$dev-workflow` 决定。
