# Product Direction

帮助用户判断“下一步为什么做什么”，而不是生成一份功能愿望清单。用户只需描述产品困惑；AI 自动选择需要建立、刷新或深入的认知范围，并通过讨论形成中肯建议。

## 1. 确认边界与授权

1. 读取适用的 `AGENTS.md`、项目说明、仓库状态和已有产品资料。
2. 用户只讨论 Skill 设计或产品方法时保持完全只读，不创建状态。
3. 用户明确调用本 Skill 或要求执行产品方向分析时，可写入产品方向状态；不得修改项目、实现功能、提交、创建 PR、部署或改变远程数据。
4. 默认状态根为 `~/.codex/state/product-direction/`；用户可明确指定其他位置。状态根始终是目录，必须在其下使用完整状态结构；不得删除、替换、清空状态根目录，也不得把一次报告直接写成状态根同名文件。
5. 写入前解析项目根和状态根的真实路径。默认状态根与项目重叠时自动改用 `~/.codex-state/product-direction/`；候选路径已经是普通文件、fallback 仍重叠或用户指定位置不安全时才停止并请求有效的项目外目录。
6. 不保存凭证、原始私密反馈、环境变量值、大段私有源码或可识别个人的敏感资料。

## 2. 使用单一自然语言入口

不要要求用户选择模式、提供机会 ID 或记忆固定命令。没有指定项目时使用当前项目；没有指定关注点时回答“当前下一步最值得做什么”。

根据意图与历史自动调整工作：

- 没有可信状态时建立产品、能力和用户旅程认知。
- 已有状态时刷新变化、过期证据与未决机会。
- 指定用户、流程或方向时深入该问题及相邻影响。
- 提到上次建议时按标题、问题和证据匹配旧机会；只有多个候选都合理时才提问。

先探索可发现事实，再提出最多 1–3 个会实质改变方向的问题。不要用长问卷代替调研。

## 3. 建立当前产品认知

1. 识别产品承诺、目标用户、核心任务、所处阶段、约束和明确非目标。
2. 从文档、代码、测试、运行说明、issue、反馈和可用数据确认已有能力及核心用户旅程。
3. 区分已提交能力与 working tree：未提交实现可作为当前认知，但必须标记 `in-progress`，不能声称已经交付或验证。
4. 对关键未提交证据记录相对路径、Git 状态与 SHA-256；不读取或散列敏感文件。
5. 按 [references/state-schema.md](references/state-schema.md) 加载或初始化项目状态。

## 4. 做必要的最新调研

默认补充与当前决策相关的最新外部证据，而不是闭门推演。涉及可能变化的产品能力、价格、市场或设计行为时必须联网验证并保留直接来源。

- 同类产品和替代方案用于确认基本预期、现有做法与仍未解决的问题。
- 跨赛道优秀产品用于提炼可迁移原则，不因对方有某功能就建议照搬。
- 用户痛点优先使用真实反馈、issue、分析数据和第一手讨论；缺少需求证据时降级为 hypothesis。
- 调研范围围绕当前决策收敛，不做无目的的竞品百科。

研究方法、证据等级、设计原则迁移和判断视角见 [references/research-and-judgment.md](references/research-and-judgment.md)。

## 5. 综合判断产品方向

从产品承诺、任务完成度、发现性、默认值、认知负担、反馈与恢复、信任、差异化和克制程度识别真正缺口。综合痛点证据、影响频率、产品契合、易用性、实现风险、可逆性和学习价值，使用带理由的定性判断；只有数据足够时才使用数字评分。

每轮最多给出：

- 1 个主要方向。
- 2 个备选方向。
- 一份克制清单。
- 一个最小验证方案。

允许结论为暂不开发、先收集证据、先简化流程或先完成已有能力闭环。证据不足时推荐学习动作，不把猜测包装成路线图。

## 6. 讨论、记录与交接

1. 先给出可讨论的诊断与取舍，使用户能够修正目标和约束。
2. 研究与候选可以 `proposed` 保存；只有用户明确选择方向后才标记 `selected`。普通确认、认可讨论方向或“没问题”不等于选择实施。
3. 对同一问题更新原机会，不创建措辞不同的重复 ID；冲突结论保留历史并标记 `superseded`。
4. 先在 `projects/<project-id>/reviews/` 追加本次报告，再更新完整项目状态，最后更新状态根 `INDEX.md`；不得用单份报告替代状态结构。格式见 [references/reports-and-handoff.md](references/reports-and-handoff.md)。
5. 用户决定实施时只生成 `$dev-workflow` 交接卡，不自动修改产品。

## 7. 完成判定

仅在以下条件满足时结束：当前产品认知与未知项已区分；内部能力、用户问题和外部参考都已考虑；建议包含理由、克制与最小验证；事实、推论、假设和决定已区分；过期证据与未覆盖范围已说明；项目保持只读；状态写入结果已报告。
