# 需求覆盖与机制理解清单

基础版本：requirements-1。交互见 [交互规则](interaction-guide.md)，产物见 [文档契约](spec-template.md)。

## 1. 全量审视，分别处理

首次对 R01–R14 全部审视，不只查用户先举的角度。各项及实际子问题形成结论：
- 继承：指出已读规则或有效设计及适用依据。
- 已设计：记录结论和来源，区分用户决定与 AI 推荐。
- 自主空间：写实施边界、默认方向及不得改变的结果。
- 不适用：说明原因。
- 待调查/待关键决定：指出缺什么及影响。

已检查不等于已解决。父项已处理不能掩盖子契约、阈值或状态仍未知。关键未知影响目标、职责、接口或验收时，对应设计不可标可实施。普通局部选择可明确授权自主处理。

| 编号 | 检查项 | 必须覆盖的含义 |
|---|---|---|
| R01 | 问题与价值 | 原始问题、目标用户、预期收益、必要性与候选比较 |
| R02 | 当前背景 | 阶段、已有能力、实现、运行条件、基线、事实依据及未知 |
| R03 | 目标与范围 | 可观察目标、本次内容、后置、必须保留和允许改变行为 |
| R04 | 规范与约束 | 实际采用版本、模块/数据边界、外部承诺、默认与有效例外 |
| R05 | 行为与触发 | 页面、API、命令、定时器、事件、回调等实际入口及可见状态 |
| R06 | 职责与实现 | 模块、文件、关键函数责任、输入输出、顺序、分支与协作 |
| R07 | 交互契约 | API、模块接口、任务、事件、外部调用的数据与错误契约 |
| R08 | 数据与状态 | 归属、存储、读写、状态转换、事务、约束及已有数据兼容 |
| R09 | 异步生命周期 | 接收、持久化、调度、执行、完成、重试、取消、最终失败、重启 |
| R10 | 并发与失败 | 重复、竞争、顺序、时间边界、部分失败、恢复和可接受限制 |
| R11 | 身份与权限 | 身份来源、权限、资源归属、隔离与相关敏感数据边界 |
| R12 | 运行与变更 | 进程、配置、外部依赖、资源预算、启动停止、必要迁移和切换 |
| R13 | 验收与回归 | 场景、输入、预期、证明方式、已有行为保护与证据限制 |
| R14 | 实施与交接 | 文件影响、顺序、依赖、进度、决定、接手步骤和自主范围 |

清单防遗漏，不等于逐项问用户、生成长章节或建设对应基础设施。

## 2. 以完整业务生命周期建立理解

在约定范围建立实际能力和入口清单，标出现状与计划变化，逐项追踪终态、依赖与外溢影响。用户要掌握整个项目就覆盖整个项目；局部需求讲足相关背景，不重教无关系统。

API、页面、表、任务、模块、事件和配置都是链路对象。范围内有 20 个 API 就覆盖 20 个，同时发现没有 API 的定时、后台和维护流程。不能以代表性接口代替全量，也不能用模块图代替工作机制。

首次完整梳理，之后复用有效理解并复查变化；过去“已讲解”不代替新问题或变更后机制的说明。

| 角度 | 必须建立并讲解 |
|---|---|
| 业务行为 | 用户/系统完成什么；成功、处理中、失败的实际表现 |
| 触发与生命周期 | 谁何时启动；继续、重复、取消、结束；用户、定时、事件、回调 |
| 职责与协作 | 每步负责人、为什么由它负责、调用顺序、同步/异步 |
| 数据与状态 | 来源、拥有者、修改者、存储、流动；允许转换与不变量 |
| 并发与时间 | 同时操作、重复、顺序变化、跨日、超时、延迟、重启的影响 |
| 失败与恢复 | 错误传播、已完成部分、重试/补偿责任、用户与维护者如何得知和恢复 |
| 运行与资源 | 进程、外部依赖、配置影响、连接/并发/额度、启动停止 |
| 变更与验证 | 改变哪些机制、影响哪些能力、观察、定位和验证 |

每个重要机制说明：解决什么问题 → 怎样运行 → 为什么这样选择 → 接受什么代价 → 什么变化需要调整。实际讲解和文档分别记录，不让用户自己读代码补齐解释。

## 3. API 链路深度；其他入口采用等价深度

| 环节 | 需要说明并可追溯的内容 |
|---|---|
| 前端触发 | 页面、操作或自动行为、条件 |
| 请求构造 | 方法、URL、参数、请求体、字段来源、身份携带 |
| 后端入口 | 处理入口、公共处理、业务模块 |
| 校验 | 身份、权限、参数、资源归属、业务状态；位置与失败返回 |
| 业务执行 | 关键函数、执行顺序、分支、外部调用 |
| 数据变化 | 读写对象、责任、事务范围 |
| 异步交接 | 入队位置、参数、执行者、接口返回时的完成边界 |
| 异常恢复 | 超时、重复、部分失败、重试、取消、重启 |
| 返回展示 | 响应、前端状态、刷新/通知/轮询、最终结果 |
| 验证 | 整条链路场景、必须保持行为与证据 |

无前端/HTTP 的命令、定时器、消费者，将前两项替换为实际触发、输入构造及反馈，不凭空创建 API。公共机制可讲一次并标明适用入口；各入口差异、校验和结果仍逐项覆盖。

不能停在“入队后 Worker 处理”，要到业务终态、数据结果、用户/维护者可见状态。只列方法、函数名或字段不算完整讲解。

## 4. 主动推演反向操作和后台生命周期

订阅类示意：添加订阅 → 保存信息 → 抓取 → 保存文章 → AI 处理 → 展示结果。主动检查：
- 定时与手动同时刷新时如何协调。
- 重复文章的保存与处理。
- 配置变化对在途任务的影响，标识读取还是快照。
- 删除订阅时排队/执行任务及迟到结果。
- 外部不可用时仍可用的能力与状态。
- 重启后未完成工作的发现与处置。
- 积压的观察、处置及对其他能力的影响。
- 重新生成时旧结果、失败和迟到结果的关系。
- 重试与配额、时间窗口、重复写入的关系。

这是考虑角度，不是统一业务规则。按实际目标确定处理、可接受限制或不适用，不自动建设完整补偿/监控系统。

## 5. 记录与演进

首次在需求材料保存 requirements-1、采用条目的完整含义及用户扩展，用紧凑覆盖表即可；纯讨论无文档授权就在对话维护。不能只存编号或指向可变 Skill。

覆盖表列：条目及含义快照、处理结论、依据/设计位置、未决子项及影响。扩展使用需求内稳定标识如 U01，记录来源与判断边界，不伪装成基础版已经变化。

增量比较内容和前提而非编号：新增、修改、删除、拆分、合并列出关系；复查变化及关联项，未变结论引用保留。删除清单条目不自动删除有效约束或决定。

阶段、目标、规范、接口或用户纠正变化时，依赖判断复查，更新设计/讲解/文档状态。保留有效决定和用户扩展，不重发全套问卷。单次发现不写全局规范，不在运行中修改 Skill。
