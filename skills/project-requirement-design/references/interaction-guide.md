# 共创、理解与决定保真

先读 [覆盖清单](checklist.md) 的机制角度。用本文件决定怎样讨论，不把内部清单逐项变成问卷。

## 1. 一次一个主要待答问题

先调查能从项目获得的事实；只把影响目标、用户行为、成本、兼容、硬约束等实质取舍交给用户。已有决定和合理推导直接复用。以能力/业务场景组织顺序，必要前提先于依赖它的方案。

分别判断“需要用户决策”和“需要向用户讲清楚”。减少决策负担不能削减机制讲解。

| 类型 | 行为 |
|---|---|
| 需要用户取舍 | 说明问题、目标关联、背景、选项差异、推荐理由与代价，再提一个主要问题 |
| 已有方案但需要理解 | 完整说明一段机制或链路，提供“了解，继续 / 解释一下” |
| 普通局部实现细节 | 自主确定并记录，必要时集中概述，不逐个询问命名或辅助函数拆分 |

用户不需要抉择时，跨模块责任、数据流、状态、异步和恢复仍要讲实际作用。普通细节只限不改变行为、责任、契约和主要代价的局部选择，不能用它排除用户要求掌握的内容。

选择当前环境可用且允许该场景的问答工具；工具不可用或受限就用清晰文本，不硬编码能力。呈现前先说明背景，选项保持完整、自足。工具中已经出现的问题不在另一消息重复提问。

同一时间只保留一个主要待答项。异步等待时可调查独立内容或维护已有授权文档；不把沉默、等待超时或预选项视为答案。收到回答立即接续；有多个旧问题时先清理已回答或已失效的，不重新问。

## 2. 决策卡

每次包含六个含义，按当前问题自然组织，不强制六个标题：
1. 决定什么。
2. 与当前目标的关系。
3. 已核实背景、约束或仍需说明的假设。
4. 有竞争力选项及实际差异。
5. 推荐方案、理由和代价。
6. 一个明确问题。

优先两个有意义选项，有第三个实质方案时可增加；不凑明显无效选择。不强制最多五条短句。短而足够，用户不用补问背景才能判断。

示意：
> 当前自动处理要限制调用消耗。失败尝试也可能消耗资源。
> 首次获准即占额能限制尝试的任务总量，重试不重复占额，最终失败也不退；只统计成功结果能让更多文章最终成功，但失败调用消耗可能增加。
> 按当前成本目标，推荐首次获准计数。
> 选择按获准任务计数，还是只统计成功结果？

这是交互例子，不是所有项目的计费规则。已明确选择后不重问。

## 3. 理解卡与解释

以完整且可理解的一段业务流程讲述：实际触发 → 校验 → 职责协作 → 数据状态/同步异步 → 终态和反馈；补充相关失败、理由与代价。必要时给时序、具体输入或状态表。不以术语列表、文件目录或“详见文档”代替讲解。

一轮可以连贯讲一组相关入口；公共逻辑说明适用范围，差异逐项展开。约定范围必须覆盖，不能只讲代表性 API，也不要每个小函数都让用户点一次。

讲完给“了解，继续 / 解释一下”。这不是实施审批或考试：
- “了解，继续”表示愿意继续，最多记录已讲解、用户选择继续，不宣称已证明掌握。
- “解释一下”后围绕具体困惑和当前输入/状态深入，不重新播放整个架构概览，不要求先自行读源码。
- 解释期间保留决定与位置，解释结束接回原链路/待决事项。
- 用户主动要求略过时记录明确跳过，不假装已经解释或理解。
- 用户主动改变讨论顺序可跟随，同时保留未覆盖项供后续接续。

文档写清楚与实际讲清楚是两件事。不要等用户另行提醒才讲异步之后、失败之后或删除/配置变化等相关机制。

## 4. 决定的内容、来源与强度

重要决定保留：
- 内容及适用范围。
- 来源：用户明确决定、已读规范、已验证事实或 AI 推荐/自主选择。
- 强度：固定目标/契约、硬约束、推荐路径、局部自主空间或未决。
- 影响理解和实现的理由。
- 固定输入输出、golden example 及示意部分的区分。
- 关联模块、接口任务、数据状态、实施与验收。
- 替代哪个旧结论及原因。

来源、强度、是否解决独立表达。AI 推荐可被采用，但不能写成“用户已确认每项”。用户最初例子只作意图线索；经校准确认的固定行为要语义完整保留，不以抽象总结丢失关键数字、状态或条件。

“前面讨论过”不是依据；正文和必要引用必须能还原。不要整段抄聊天或所有旧方案；保存会使接手者误选、失去设计原因或影响实验比较的历史。

## 5. 修订按影响传播

任何决定或前提变化都检查：
目标/范围 → 模块职责 → 接口与任务 → 数据/状态 → 运行 → 实施 → 验收 → 讲解进度。

正文重写为当前有效方案，旧决定标替代并留必要原因。不能只在末尾追加一句新要求，让实施者判断前后哪个有效。已解释的机制发生实质变化，向用户说明变化与理由，受影响理解状态待补讲。

例：用户说明未上线、可直接暂停后，撤掉依赖在线服务的维护窗口、双队列和在线回退要求及对应估算、验收。保留必要启动/迁移/业务验证；不把它推导成清库许可。既有数据/任务保留仍独立判断。

例：用户选择合并结果回写步骤，要同步检查任务类型、写入责任、事务、错误、恢复和验收，不仅改流程图。先核对现行数据边界。

## 6. 三种进度与接续

| 维度 | 可记录状态与含义 |
|---|---|
| 设计 | 已分析、已设计、待调查、待关键决定；完成不能掩盖子项未知 |
| 讲解 | 已说明、需要进一步解释、尚未说明、用户明确跳过 |
| 文档 | 已写入、待同步、存在冲突、待补齐；无写授权时说明仅在对话 |

小需求可一张表，长需求保存在既有进度区或 progress.md。不构建数据库或状态引擎，不用统一百分比混合三者。代码实现、验证状态实施后另记。

恢复讨论先看当前有效规格、未决问题、上次讲解位置和用户最新输入，只复查变化。无新证据不重新挑战已定方案，不把用户的状态提问或解释请求当成取消原需求。

## 7. 保存与交付

有本需求文档授权即持续更新；没有则保持对话草稿。保存前核对已确认纠正、理由、否决原因、示例、未决与授权，再对照实际文件。重读并合并用户或其他会话改动，不覆盖未知内容。

必要决定收敛且授权形成文档后，依 [文档契约](spec-template.md) 整理最终版本，不机械追加“是否允许定稿”。尚有关键缺项则明确部分状态并继续；不能通过省略未决制造就绪。具体就绪和证据边界见 [验收与交接](handoff-and-validation.md)。
