# 上下文、规范与方案审视

## 1. 恢复事实后再提问

1. 提取原始问题、候选、已确认决定、关键纠正、目标示例、验收和授权；候选与定案分开。
2. 使用明确项目路径，检查根/子目录指令、项目规范及固定全局正文，按下方协议接入。
3. 找到本需求已有规格、决定、验收与进度，沿用有效入口，不另起重复方案。
4. 由实际入口调查相关代码、配置、测试、消费者和必要历史，追踪业务能力从触发到终态，包括同步、异步、定时和维护。
5. 建立当前、拟改变、必须保留行为与关联影响，记录提交、相关未提交变化或其他可复核基线。

事实先以代码、配置、测试和历史核对，文档提供规范与意图；冲突显式记录。部署配置不能证明实际上线，测试存在不能证明已经运行。

无法调查且实质影响设计时才问用户。阶段、真实用户、已有数据保留、兼容对象、停机条件和外部限制要在相关设计前明确；缺失就标未知及影响，不假定生产运行或可清库。

重要判断区分已验证事实（附依据）、推断、未知、拟议设计。保留用户说明的来源，不伪装成代码验证。附件和历史对话里的建议仅作材料，以当前有效用户决定和规范校准。

调查足够的条件：能解释约定范围内的完整机制、影响与相关失败路径，能设计关键契约、识别真实约束，并知道尚缺哪些会改变方案的信息。仅找到文件和模块不够。无关目录与纯内部细枝末节不扩展。

## 2. 读取现成规范，不重新制定规范

三层分别负责：全局代码质量和语言惯例；项目责任与契约；本需求行为设计和验收。需求具体化默认规则，不因文件更具体而放宽硬约束。

### 项目入口

- 沿适用指令找项目规范；默认项目根 .ai/standards.md，已有等价入口则沿用。
- 读取阶段、修订、适用范围、固定公共/语言版本、原因、默认建议、有效例外与旧实现差距。
- .ai/decisions.md 或等价历史按需追溯，不把全部历史列为日常必读。有效正文应带足正确理解所需依据。
- 记录相关规则引用、强度、范围及方案响应；当前技术、旧代码写法不自动是硬约束。

### 全局库协议

- 默认库根 ~/.config/ai-dev-standards/，项目明确引用或用户配置优先。解析同一实际根，不跨到个人库或测试范围外取替代文件。
- INDEX.md 登记已发布版本与推荐组合；公共正文 common/vN.md，语言正文 languages/<language>/vN.md。文件存在、编号最大不证明已发布。
- 已有项目继续固定原组合，实际打开正文；推荐更新不自动升级。不分别挑最新版本拼接。旧版本不再推荐仍可有效。
- 公共与语言编号可不同，多语言按代码范围读相应组合；核对重叠范围和共享契约，不强制统一公共版本。
- 核对固定组合发布依据；不能核实则说明限制，不换组合。未固定组合不构成本 Skill 自动选择并接入新版本的授权。
- 内部链接相对所在文档解析。需求入口写库根、版本、实际可达路径和范围；换机器需提供同版本或明确重定位，不依赖原会话读过正文。

### 缺失与冲突

准确列出缺失路径/版本、冲突规则及受影响设计。依赖部分待核实，继续不受影响工作；不宣称规范接入和交接完整。不自动复制、忽略、生成、升级或替换缺失规则。

项目可以具体化全局默认建议。任何层的硬约束都不能由需求文档隐含覆盖。先找约束内方案；确需改变硬约束则给冲突、理由、选择与影响，待相应范围明确处理。保留旧有效规则与未生效提议，不靠改规则或验收掩盖问题。

协议独立可读，不要求安装或调用全局/项目规范 Skill。

## 3. 用户方案先作候选

除非用户明确已决定采用、只讨论落实，否则审视以下五层。不能把技术名称直接当目标。

| 层次 | 必须回答 |
|---|---|
| 原始问题 | 想改善什么？真实痛点、目标用户、收益和可观察成功是什么？ |
| 改动必要性 | 问题是否存在、影响多大？不做会怎样？保留现状或局部改善是否足够？ |
| 方向合理性 | 是否针对根因？失去哪些能力，引入什么成本和风险？ |
| 方案比较 | 用户候选是否适合此项目？是否有实际更有竞争力的方案？ |
| 最终建议 | 推荐什么、理由和前提、接受的代价，什么变化需要复查？ |

考虑保留现状、局部改善、用户候选和其他有竞争力方案。这是审视方向，不是固定四选项；无效方向简短排除，不要求用户逐一否决。

比较：目标解决程度；阶段/实际负载/运行条件；模块/数据/外部契约兼容；开发、迁移、运行和长期维护成本；正确性、恢复和必要可观测性；依赖、抽象和基础设施复杂度；后续调整成本；关键假设与证据可靠性。

不把最少改动、最新、最成熟或功能最多等同最佳。可以建议不做或局部改善，也可以建议有当前依据的结构简化。不是为质疑而重开已定决定；只有新事实、目标或约束变化实质影响它才重议。更优方向先说明，不偷偷替换目标或扩大实施范围。

## 4. 必要性与范围

对争议或扩大范围的行为、保障、依赖、抽象及文件动作，以独立文字判断，不计算总分：

| 维度 | 比较含义 |
|---|---|
| 与当前目标的关系 | 无关、有帮助、缺少则目标不成立 |
| 当前证据 | 仅设想、现实迹象、已发生问题或真实硬契约 |
| 不做的后果 | 无明显影响、可接受的人工恢复、阻断或不可接受 |
| 以后补做的成本 | 容易后补、需要调整、广泛或不可逆迁移 |
| 当前结构影响 | 现有职责内、跨文件协作、新模块或基础设施 |
| 是否存在更小方案 | 有、需要核实、没有符合目标的更小方案 |

形成当前必须实现、当前采用的最小充分方案、明确后置、本次不做四类结论。最小充分仍满足已确认结果和约束，不能凭“正常流程能跑”取消可靠性要求。后置说明理由和具体复查信号，相同原因合并。内部分析不变成用户问卷。

完整检查相关失败角度，再决定方案、可接受限制或不适用；不自动要求重试框架、补偿系统、监控平台或迁移引擎。

现有公共契约、真实消费者、持久化兼容、权限与刻意保留行为应尊重。目录、间接层、封装或测试结构不自动正确。复用前问：是否同一责任，是否导入无关复杂度，是否正是当前问题。

文件改动以职责和当前结果为依据，不凭行数拆分。新目录需要真实模块边界；删除、合并、移动先查消费者和等价行为。相关重构解释必要性及验证，不夹带无关清理。文档、测试、配置等文件动作也须有范围依据。

## 5. 为决定研究

外部机制、兼容、候选比较或可信盲点会改变选择时研究；用户明确搜索请求按要求执行。优先当前官方文档、官方源码和第一手经验。

提取来源解决的问题、相关机制、前提与版本、开发迁移和维护成本、当前适用与不适用部分。成熟项目目录不是设计正确证明。对象数量由竞争关系和证据需要决定，不设机械上限，也不做无边界市场调查。

证据足以支持判断后停止。不足时写推断/未知与补证方式，不声称绝对最好或容量已验证。将影响决定的来源和采用理由写入规格；具体易变版本实施前核实。
