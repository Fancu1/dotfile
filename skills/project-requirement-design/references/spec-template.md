# 需求文档契约

以能独立实施为标准，内容具体度由行为和契约需要决定，不以文档短作为成功条件。固定规则、共享契约和重要决定只维护一份，其他位置引用。

## 1. 保存位置与拆分

优先沿用项目已有需求路径和当前需求入口。没有等价组织时，用 docs/requirements/<需求短名>/spec.md；短名按问题命名，避免与已有需求冲突。用户指定单文件或其他位置时服从。

小需求在单份规格包含完整背景、方案、决定、实施和验收。跨模块或独立维护需要时使用：
- spec.md：唯一入口，目标、范围、依据、总流程、关键决定与阅读顺序。
- contracts.md：多个模块共享的接口/任务/事件/状态契约；单一使用点可留设计正文。
- modules/<模块名>.md：独立模块设计，引用共享契约，不复制多份定义。
- acceptance.md：场景较多或需要独立维护执行证据时拆出。
- progress.md：跨会话、持续执行或多步骤需要独立进度时拆出；小需求的同类信息可在入口内。

拆分依据责任和阅读维护需求，不设字数/页数阈值，不建空文件或目录。已有等价文件名继续作为入口，不为套模板迁移。不要自动改 AGENTS.md 或建历史需求总索引。需求状态保存在项目材料，不能依赖安装目录里的私有状态。

链接按文档位置解析；现有文件链接实际检查，拟新增代码路径标明“计划新增”，不能报成现有链接。默认用中文叙述，保留实际技术符号；遵循用户及项目的写作要求。

## 2. spec.md 必备含义

标题：需求实现规格：<需求名称>。章节可合并，不填空泛套话；以下信息不能丢失。

### 状态、依据与入口

记录当前修订、设计状态（讨论中/设计就绪/需复查，或既有等价表达）、讲解与文档完整状态、本需求授权。指向唯一当前设计，不能用最新时间戳判断多个候选哪个生效。

列明项目阶段、相关能力、代码/配置/测试依据与调查基线、相关未提交变化、事实与推断未知。静态调查不写成运行验证。

记录实际项目规范、固定全局公共与适用语言版本、库位置、适用范围、读取结果、相关规则和例外。缺失/冲突精确列出，换机器所需材料必须可识别。接入协议见 [决策框架](decision-framework.md)。

### 问题、目标与范围

说明原始问题、目标用户、预期变化、候选方案评估和采用理由。区分本次实现、最小充分方案、明确后置及条件、本次不做。列出必须保留与允许改变的行为，抽象目标转为可观察结果。

### 当前与目标流程

按业务能力描述实际入口、完整生命周期、模块合作和外溢影响；对照现状和变更。覆盖 [清单](checklist.md) 的角度，以时序图、状态表和文本表达实际机制，不把模块图当作全部设计。

### 决定、示例与自主空间

正文给当前有效结论，保存重要理由、来源、强度、适用范围、固定示例及必要的替代关系。完整规则见 [交互规则](interaction-guide.md)。已确认请求/响应、数字、状态、顺序不能在概括时失真。

明确固定目标/契约、规范硬约束、推荐路径、局部自主空间和未决事项。自主空间有边界和默认方向，不能把待决定的业务语义写成“实施时再看”。

### 设计、实施与验收入口

写入下列模块、函数、契约和数据/异步信息，或链接到对应拆分文档。给依赖顺序、每步行为结果、文件动作、验证入口、接手步骤。不得用“按照之前讨论”或聊天链接补关键设计。

记录清单版本及实际条目含义快照、结论、设计引用、未决子项和用户扩展；可集中在附表，既保留覆盖依据又避免正文重复。

## 3. 模块与文件设计

每个受影响模块说明：
- 本次解决的问题、当前职责和目标职责。
- 输入输出、上下游、调用顺序与分支。
- 数据读写、写入责任、状态或资源所有权。
- 已有文件和预计新增职责，以及如何验证模块与合作行为。

文件计划使用“文件/拟议位置、动作、职责、行为改动、关联验证”表。按需展示相关子树前后变化，不贴整仓库目录。改动动作有当前依据，保留凝聚职责；不按行数拆分，不添加惯例性清理或 README 工作。

## 4. 关键函数的实施依据

跨模块调用、状态推进、事务、后台执行和关键错误处理函数逐一描述：
- 所在模块/文件，现有还是拟新增；现有名字与签名须核实。
- 输入、输出、前置和后置条件。
- 执行步骤、顺序、分支和被调用者。
- 数据与外部副作用。
- 错误类别、传播及调用者责任。
- 事务、取消、超时和重试边界。

可写函数签名、状态表、时序或伪代码，无需生产代码和逐行补丁。局部辅助函数名称、拆分和普通实现写法可留自主空间；关键责任与业务选择不能留猜测。

不接受“保证一致性”“加上幂等”“按规范实现”作为完整逻辑。以事务入队示意：
~~~text
请求处理：
  校验请求和业务状态
  在同一已指定事务中保存业务变更与创建任务
  两者成功提交后才返回已接受
后台执行：
  读取所需数据，核对工作仍然有效
  执行外部操作
  按已确定的提交策略保存结果并推进状态
  按错误语义重试或终止
~~~
这仅演示粒度，不是所有项目必须同事务，也不是可直接交接的最终方案。实际文档必须填清具体数据、有效性判定、事务适配、幂等标识、提交/崩溃窗口、错误和状态结果。

## 5. API 与共享契约

对受影响接口提供方法、URL和身份机制。字段表表达：
| 位置/字段 | 类型 | 必填 | 默认/空值/约束 | 来源与含义 |
|---|---|---|---|---|
| 按实际接口填写 | 核实或明确拟议类型 | 明确 | 仅列影响行为的规则 | 前端或其他调用者如何生成 |

必须说明：
- 路径、查询、请求头、请求体，验证顺序中影响行为的部分。
- 身份、权限、资源归属、业务状态校验的位置与失败结果。
- 成功响应、失败响应、状态码、错误触发条件。
- 前端/调用方触发及展示、刷新或后台结果获取。
- 同步返回与后台完成边界、兼容条件。
- 与字段定义一致的具体请求/响应例子和验收输入。

已有接口由代码证据确认；新接口明确拟议，不能凭空补成现存事实。只有 JSON 样例而没有语义不足；也不能只写类型表却不解释处理逻辑。

内部调用、任务、事件、回调和外部集成使用等价契约：生产者、消费者、输入输出字段、错误、版本/兼容及生命周期。共享状态和契约只保留一份权威定义，其他文档引用；示例与测试引用同一语义。

## 6. 数据、状态与异步

按实际范围描述：
- 数据所有者、读取与修改入口、必要字段/类型、唯一性和完整性约束。
- 状态、允许转换、触发条件、禁止转换及并发保护。
- 事务覆盖步骤，业务提交与任务/事件交接窗口；外部副作用不能凭数据库事务假定只发生一次。
- 旧数据、运行配置与消费者兼容，必要迁移和明确保留范围。

每类异步任务说明：触发条件；可靠接受点；参数是标识还是快照及理由；执行者与队列/资源隔离；协调、重复、顺序；超时、重试预算、最终失败、取消；重启与部分完成；哪些外部重复允许、哪些业务副作用不可重复；业务终态与任务终态；用户及维护者如何观察和恢复。

次数、时间、阈值影响验收时给确定值或明确可配置契约及测试取值。关键未决不能隐藏在“参数可配置”之后。不用队列产品名代替可靠性语义。

## 7. 实施顺序和进度

按依赖给出可实现/验证的行为步骤，各步关联模块、文件、契约和验收。验证随对应行为安排，不留到所有代码完成后才发现契约不匹配。写清必要本地环境、测试数据、已知基线失败及外部依赖，命令须来自项目或标明计划新增。

长需求进度记录任务、依赖、目标、实现状态、验证证据、重要自主决定、当前待决与下一步。设计/讲解/文档状态按交互规则独立记录。实施前实际结果为空或未执行，不能把计划写为已完成。

## 8. 验收、就绪与保存

验收表、无聊天检查和接手契约使用 [验收与交接](handoff-and-validation.md)，不要在此另建重复标准。

授权内准备局部修改，写入前重读目标文件，发现其他修改先合并。必要时用同目录临时文件替换，保留未授权范围；不声称多文件写入原子性。拆分或修订后重读入口、引用、契约、决定、覆盖及状态。

失败或中断时按磁盘实际内容报告已写/未同步部分；恢复先核对完整性，未同步候选不当作当前设计。没有语义或依据变化就不无意义刷新时间或重写文件。
