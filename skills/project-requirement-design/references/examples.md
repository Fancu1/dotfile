# 案例、正反例与行为演练

以下材料用于校准行为，不是所有项目的默认业务规则。真实案例改编自用户提供的《评估 Kafka 与 River 取舍》；为可重复演练保留该次已确认条件，不将其当成 Scope 当前代码或运行事实。日常使用不需要访问原会话。

## 1. 先审视用户方案

用户：
> 我觉得这个项目没必要使用 Kafka，换成 River 就够了。帮我讨论方案并写开发文档。

合理开场：
> 我先检查 Kafka 实际承担哪些业务、当前运行条件和项目规范，弄清你希望减少的成本，再比较保留并简化、替换以及有竞争力的方案。然后给出推荐和代价。

调查后应能回答原始问题、必要性、方向合理性、方案比较、推荐。能从项目查出的事实不先问用户，无法得知且重要的阶段/偏好再问。

反例：
> 好，马上写 River 迁移计划，分三步替换生产者和消费者。

问题：把候选当目标，尚未判断是否值得换。

反例：
> River 总是更简单，因此最适合。

问题：无项目依据，未核对需要的语义、现有契约与新代价。

相反场景：原始材料证明痛点是可通过配置修正的告警，而替换丢失必要的历史回放能力。应能推荐先修正配置并保留现状，不为迎合迁移要求创造收益。该结论仅适用给定证据。

用户明确说“已经比较并决定采用 X，只讨论接入”时，复用决定；仅在新硬约束/事实实质影响可行性时重议，不机械重做选型。

## 2. 先核实阶段，纠正后同步全部影响

用户补充：
> 切换时直接允许暂停，不需要处理维护窗口，因为项目没有正式上线。

合理回应：
> 切换按停止旧服务、处理必要迁移、启动新版和业务验证来设计。我会同步撤下在线维护、双队列和在线回退要求。已有业务数据与旧任务保留仍分别确定，未上线不代表清空数据库。

同步更新范围、设计、估算、操作步骤、验收与未决项；不能只在末尾附一句“可暂停”，而验收仍要求在线切换。

需要避免：
- 从 docker-compose.prod 等名称推断已有真实用户。
- 用户已说明未上线后继续让其选维护窗口。
- 从未上线推出全部历史任务、数据库都可删除。
- 继续把生产验证列为本次必需完成条件。

## 3. 固定回归案例：结果写入、重试与配额

该案例已经确认：
- 未正式上线，允许直接暂停切换；不建设无停顿或在线交接机制。
- 用户选择 AI Worker 直接保存结果，取消独立结果回写任务。
- 接受有限次数自动重试，以及恢复时可能再次调用 AI。
- 同一逻辑任务首次获准占一个名额，重试不重复占，最终失败不退还。

固定示例：
> 每日上限 8，已占 7。新逻辑任务获准后计数变成 8；该任务重试期间仍为 8；最终失败后仍为 8。

这三个状态分别进入验收。不能改成成功才计数、失败退回 7、每次重试加 1，或把初始 7 解释为必须已经成功的文章数。

未确认：具体重试次数、超时、跨日规则、实现事务、旧数据/旧队列任务保留细节。曾经推荐“总共 3 次尝试”不等于已确认，不得把建议升级成固定规则。

写入职责仍受实际项目规范约束。例如硬规则要求通过文章模块公开入口提交结果，则 Worker 可调用该入口，不能凭“直接保存”绕开责任。若无法在既有边界下完成选择，明确冲突，不偷偷改规则。

用户改变结果写入职责时，检查生成/回写任务数量、模块责任、保存规则、事务、状态、幂等、错误和验收，而不只更新箭头图。

## 4. 不需决策也需要讲解

给定以下仅用于讲解的设计：一项后台工作可靠入队后返回，Worker 执行，界面查询任务结果；未约定具体 URL。

合理讲解：
> 点击操作后，前端先提交业务对象标识。后端确认身份、对象归属及当前状态，再保存任务。接口返回“已接受”表示任务已经保存，工作还没完成。Worker 读取任务检查对象仍可处理，完成后保存结果并更新业务状态，界面再查询到结果。
>
> 同样请求再次到达时怎样识别重复、对象被删除时在途任务怎样结束、外部操作成功但结果未保存时如何恢复，这些会改变最终行为，需要按当前规范说明具体策略。下面逐段展开已经确定的策略与仍待确定的部分。
>
> 对当前这段流程，你可以选择“了解，继续”或“解释一下”。

这是说明讲解结构的例子，不是完整设计；真实使用必须补上已核实/已设计的接口、状态、校验及各分支。不能把整段带有待定策略的示意当“完整就绪”。

反例：
> 后端入队，Worker 负责后续。都是普通实现细节，不用关注。

问题：关键业务机制被普通细节分类隐藏。

用户：
> 解释一下为什么接口返回了，结果还没出来。

合理解释：
> 这里有两个时刻：任务可靠保存后，接口就能告诉页面已接收；真正结果要等 Worker 完成。页面此时显示等待/处理中，后续按已经设计的查询或通知方式获得终态。我们还要明确超时与失败展示，避免页面永久停在处理中。

解释后回原讨论位置，不重新询问已确认的选型，也不要求用户证明自己掌握了。

## 5. API 只是入口之一

范围给定 20 个 API、一个定时更新任务、一个删除清理任务。应建立完整入口与能力映射，按业务场景连贯讲解每条路径，公共处理只讲一次并指明适用范围，各入口差异仍覆盖。

定时更新与手动刷新交汇处要说明并发、去重和状态；删除清理要说明在途工作与迟到结果。不能只列 20 个接口名字，也不能只讲前三个后说剩下类似。

没有 HTTP 的例子：
> 每天扫描待处理文件，转换完成后归档，失败文件第二天能否重试？

应追踪定时触发、文件选择和占用、转换、输出提交、归档、失败/重启、重复扫描与运行观察；不凭空设计前端/API。必要重试与归档行为需要明确，普通局部函数可自主。

## 6. 从正文发现缺口

待评审草稿：
> 保存结果时保证幂等。失败自动重试。任务最后更新 completed，删除资源时取消任务。所有测试通过即可交付。

应识别：逻辑任务标识、幂等作用范围、重复副作用、重试错误/预算、保存与终态窗口、取消与完成竞争、删除后迟到结果、真实通过标准都不明确。提出具体调查或设计，不因为标题齐全而标就绪。

相反，小型文案修改不需要填满上述机制：单文档说明目标文案、出现条件、影响页面、保持行为及针对性验证，其他清单给有依据的不适用即可。

## 7. 保存、接续和授权

用户：
> 把这次讨论整理成项目文档，之后继续边讨论边更新。

应找到现有需求位置，授权内维护文档，不每轮要求另行保存许可。先读文件，变更后复核共享契约和验收。用户仅说“没问题”不能启动代码、goal 或提交。

新 AI 接手时，提供入口及必要规则、代码和状态；不要求原始聊天或个人记忆补足关键理由。新代码基线改变时复查受影响内容，不无差别重做全部问卷。

若缺固定规范 common/v1.md，但库存在推荐 v2：明确缺项和受影响范围，继续其他调查，不能自动用 v2 或声称接入完成。库根被指定为隔离夹具时，不回退到真实个人库。

## 8. 行为验收矩阵

在隔离示例项目或只读材料中演练；观察实际行为和产物，不匹配固定措辞。结构检查、同一 AI 自查、独立演练与真实使用效果分别报告。

| 场景 | 通过标准 |
|---|---|
| 提出替换技术 | 审视问题、必要性、方向、替代与推荐，不直接施工 |
| 保留现状更好 | 根据实际证据建议不换或局部改善 |
| 尚未上线 | 不预设在线迁移，不推导清库许可 |
| 固定规范版本 | 实际读固定正文，按范围使用，不自动升级 |
| 缺失或冲突 | 精确标影响，继续独立工作，不假就绪或改硬规则 |
| 20 API 加定时任务 | 逐项覆盖并识别非 API 机制，不抽代表样例代全貌 |
| 无 HTTP 需求 | 围绕实际命令/定时/事件、数据和生命周期 |
| 无取舍但需理解 | 关键机制讲完整，提供理解交互 |
| 请求解释 | 具体解释后接续，不丢决定或重发全部问题 |
| 改关键决定 | 同步职责、契约、任务、验收与讲解状态 |
| 配额固定例 | 完整保留 7→8、重试8、最终失败8 |
| 小需求 | 单文档完整，不建空模块或迁移系统 |
| 跨模块需求 | 共享契约单一来源，输入输出与衔接一致 |
| 文档有关键空缺 | 发现真实未决，不凭完整标题称就绪 |
| 换 AI 接续 | 入口、规范、最小项目资料足够还原关键决定与实施验收 |
| 普通实现分歧 | 有自主空间，不逐函数审批也不修改硬契约 |
| 仅说没问题 | 无额外代码、goal、提交或外部操作 |
| 结构检查成功 | 如实限于结构，不称交互/交接效果已证明 |

演练记录输入条件、执行方式、实际输出/文件、观察结论、失败或未测项。不要把矩阵列出等同于所有场景都已执行。

无聊天复核给最小原始材料、产物与任务，不提供期望答案或作者补充解释。独立复核需环境允许且已有授权；同一 AI 模拟不可冒称独立，独立认可也不证明最终代码正确。

## 9. 参考实践的采用边界

- [Kiro Specs](https://kiro.dev/docs/specs/)：需求、设计、任务职责分开，按本需求决定文件数量。
- [GitHub Spec Kit](https://github.github.com/spec-kit/)：产物衔接与跨文档一致性，不引入完整命令体系。
- [Anthropic 长任务实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：目标、进度、环境、真实验证，不自动继承提交或编排。
- [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)：背景、理由和替代方案，补足本场景要求的具体实施契约。
