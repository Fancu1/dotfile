# 项目规范完整确认清单

内置版本：project-core-1。编号用于关联，不替代问题内容。首次逐项审视；维护时比较项目保存的内容快照、用户扩展与此版本，按语义变化复查。

## 十个确认领域

| 编号 | 领域 | 确认问题与判断边界 |
|---|---|---|
| P-01 | 全局规范接入 | 公共和语言规范来自哪个库、哪些已发布版本和兼容组合？分别适用哪些代码？既有固定版本、缺失项、冲突和必要例外是什么？不要独立挑选各文件的最高版本。 |
| P-02 | 核心业务约束 | 哪些结果必须始终成立？哪些操作不能重复生效？哪些状态转换禁止？规则来源是用户承诺、真实外部契约还是 AI 推荐？不能从一次示例推导未经确认的商业承诺。 |
| P-03 | 业务职责 | 关键能力分别由哪个逻辑模块负责、不负责什么？共享业务规则由谁维护？逻辑职责与当前包、目录、进程分别是什么？不强制服务化或固定层次。 |
| P-04 | 模块交互 | 能力通过何种边界提供？允许的依赖与数据流向是什么？哪些访问会绕过所属业务规则？跨模块共享代码的责任在哪里？函数、接口、RPC 等机制何者是现状、默认或必要限制？ |
| P-05 | 数据责任与一致性 | 谁拥有数据及其业务规则，谁能读写，依据何种边界？哪些更新需要共同成功？允许什么延迟、不一致和部分成功？删除、保留与衍生副本有哪些实际要求？事务、ORM、缓存和仓储布局通常保留实现空间。 |
| P-06 | 对外契约 | API、事件、UI、CLI 的已有行为与兼容承诺是什么？错误语义、分页、标识、版本等哪些需要统一？不适用的入口略过，尚未承诺的局部细节留给需求设计，不能用默认建议改写既有承诺。 |
| P-07 | 异步协作 | 哪些结果稍后产生？接受请求表示接收、可靠保存还是完成？丢失、重复、乱序、失败、重试、取消与重启后的预期及责任是什么？如何观察状态？机制是现状、默认还是必要约束？不能凭存在 Kafka/队列/worker 推断已满足可靠性。 |
| P-08 | 身份与隔离 | 实际角色、用户、租户及信任边界是什么？权限由谁判定、在哪些入口执行，包括确实存在的后台入口？哪些数据或操作必须隔离？单用户工具不默认引入租户体系。 |
| P-09 | 运行与外部限制 | 当前阶段实际需要的性能、可靠性、成本、运行环境及第三方限制是什么？维护者需要哪些错误、任务状态或关联信息定位失败？哪些是已验证限制、默认预算或未知目标？不编造数值，不自动引入集群与完整可观测平台。 |
| P-10 | 例外与调整空间 | 现状与生效规则或拟定目标的差距在哪里？有效例外由何依据支持，范围及适用条件是什么，能否扩展？哪些只是拟议例外？哪些方式可由 AI 自行优化，需保留什么结果和兼容性？不能将已知违规永久合法化。 |

## 如何判定已处理

- `形成约束`：指向生效规则，说明保护的结果、范围和依据。硬约束与默认建议分开。
- `沿用或采用默认`：说明已有规则或推荐依据、适用条件及可调整空间。
- `交给实施决定`：说明仍需保护的边界及开放选择；不得留下会改变目标或外部承诺的关键空白。
- `不适用`：说明项目为何没有该问题，而不是仅写“无”。

待决是未完成状态。一个领域允许有多个结论或局部待决；记录实际未解决的问题，不用四选一强迫虚假的完整状态。完整覆盖要求所有适用问题都有有依据的结论；不要求每个问题都生成一条规则，也不要求用户逐个回答。

## 沿流程补漏

用项目真实或已确认的核心流程连起 P-02 至 P-09，检查责任是否断开、数据是否绕过规则、成功返回是否与后台结果混淆。对相关的失败、重复、并发、超时、重启、版本变化推演预期；无需为不存在的机制发明故障类型。

例如“添加订阅 → 抓取内容 → 保存文章 → AI 处理 → 展示结果”：文章保存责任与 AI 结果写回责任是否一致？抓取失败是否影响订阅已创建？重复结果是否重复扣费（仅当确实存在计费）？用户看到的状态是否真实？这些是调查问题，答案不能从例子直接复制。

## 清单演进

新增问题先判断属于项目长期边界、全局规范还是单次需求。项目扩展用 `USR-...` 标识，保存完整问题、范围、来源及结论；不自动修改 Skill 或全局库。

保存采用版本的完整问题与判断边界快照。内置更新或用户修订时比较内容：增加、修改、删除、拆分、合并均检查影响并保存前后关联；删除问题不自动删除有效规则。前提、范围、约束来源或契约变化时，即使条目编号和正文未变也要复查。无关旧结论可引用原批次，不重抄或重问全部内容。
