# 项目产物与全局接入

## 文件职责与单一事实源

默认项目根下 `.ai/standards.md` 为开发入口正文，`.ai/decisions.md` 为维护记录，根 `AGENTS.md` 仅增加必要读取指令。已有等价文件先确认其作用与有效性，沿用原路径和组织；不并行生成另一套相同规则。用户指定位置时以该位置为准。

规范数据保存在项目中，与 Skill 安装目录分离。维护记录可读但不属于日常开发必读历史；正文必须带足适用条件、原因与例外。

### 规范正文的最低信息

结构可随项目调整，以下含义不能丢失：

1. **状态和项目背景**：规范修订标识、对应记录；项目目标、阶段、现有能力、调查依据及时间或提交。事实单列，不把静态检查写成运行验证。
2. **全局组合与读取范围**：库根、明确公共及语言文件版本、适用代码范围、已核对组合；缺失或冲突列为接入未完成。
3. **生效项目约定**：业务责任、必要交互和数据边界、外部行为及异步要求，按项目组织。只生成有实际内容的部分。
4. **默认选择与开放空间**：目前沿用的技术或实现选择、可调整条件；避免重复事实段落。
5. **有效例外、已知差距与未完成项**：例外范围、依据和扩展限制；目标规则与旧实现的差距；待决候选不混入生效规则。

每条规则使用稳定引用标识（例如 R-01，现有编号则沿用），保留要求、强度、范围、必要原因及可观察的违反方式。可紧凑写在同一段，不强迫填空表。强制要求与可调整的建议分别表达，避免同一个编号的“必须”被理解为覆盖后面的默认建议。

示意（只有对应责任与需求成立时才能采用）：

> R-01 文章写入责任｜必须。文章内容和处理状态由文章能力维护，AI 处理模块通过其公开写入入口提交结果，避免两处各自维护状态转换。模块可位于同一进程；入口可由实施选择。检查跨模块写入路径是否绕过该入口。既有例外若存在，在此列明范围；不能只藏在历史记录。

具体测试代码与命令属于需求开发；这里提供“怎样判断违反”的依据，不承诺用静态检查即可证明全部业务结果。

### 维护记录

保留清单版本、完整问题与判断边界快照、用户扩展以及修订关系。每次变化记录：

| 信息 | 最低要求 |
|---|---|
| 批次及生效关系 | 本次请求、原规范修订、本次候选修订；正文实际引用的修订才是当前生效内容。候选记录本身不代表生效。 |
| 逐项结论 | 条目及快照版本、结论或待决、规则引用或开放空间；首次覆盖全表，增量引用未变结论所在批次。 |
| 依据与理由 | 用户明确决定、既有生效规则、代码事实或 AI 自主决定分别标明。观察到的写法不能单独证明它应当成为硬约束。 |
| 影响与差距 | 受影响关联项、保留或替代旧结论的理由、已知违规及例外边界。 |
| 检查及待决 | 引用、组合、语义与读取入口的实际结果，尚未解决的问题和未验证项。 |

规则正文与清单版本分别维护。仅记录或依据变化无需增加正文修订；无新语义、依据或待决变化则不追加记录，不刷新时间戳。用户扩展不会因 Skill 更新丢失。

## 接入全局规范

协议与 `global-dev-standards` 产物保持一致，但不要求安装或运行该 Skill；本节足以读取现成规范库。

- 默认库根 `~/.config/ai-dev-standards/`，允许用户覆盖。解析一次实际库根；隔离演练不得回退到个人库。
- `INDEX.md` 登记已发布文件和推荐组合。公共正文为 `common/vN.md`，语言正文为 `languages/<language>/vN.md`；不把目录存在或最大编号视为已发布。
- 新接入选择入口的完整兼容组合，实际读取相关正文并检查项目适用性。公共与语言版本号不必相同，不能分别挑“最新”拼接。
- 已有项目继续固定原组合；入口推荐变化不触发自动升级。历史版本不再被推荐仍可有效；缺少发布依据时如实标注无法核实，不擅自替代。
- Go/Python 等混合项目按代码范围分别绑定完整组合。公共版本不同并不自动构成冲突，但重叠范围及共享契约须语义核对。冲突部分保留原有效组合或标待决，不强行统一到最新公共版本。
- 项目可具体化默认建议；不得凭文件更具体而放宽全局硬约束。真实冲突给推荐和影响，在未解决前保留有效规则。
- 库或固定文件缺失时，列出准确缺项和受影响范围，不生成伪版本或自行创建全局库。独立项目规则可形成部分完成产物；接入完成状态必须保持否。全局规则存在但不适用时须有理由，不为求完整随意标“不适用”。
- 正文用正确可解析的文件链接并记录库根和版本。项目内部链接相对所在文档解析；全局链接使用本环境实际可达路径，注明跨机器需提供相同版本或显式更新库位置。不能默默复制、忽略或改用其他版本。

## 项目读取入口

先读取现有根及相关子目录指令，检查是否已有等价入口或冲突。新增入口仅表达必要读取关系；不覆盖其他内容、重复插入同段，或认为子目录可以随意推翻硬约束。

默认入口示意，路径按实际产物替换：

> 开发前读取 `.ai/standards.md`，并实际读取其中固定的公共规范与本次改动涉及语言的规范文件，按各自作用域共同遵守。若引用缺失或存在冲突，说明受影响范围，不擅自替换版本或放宽硬约束；继续可在已知约束内完成的工作。

用户要求只写规范不改入口时不修改 AGENTS，报告“规范已写入，读取入口未接入”。入口存在不意味着每个运行环境已经自动加载引用正文。

## 增量维护与可靠保存

1. 读取将修改文件的现有内容，识别等价规范、候选、用户扩展和未提交改动。只修改本次规范及必要入口，不修改代码来消除文档差距。
2. 比较请求、清单快照、项目事实及前提。检查新增/修改/删除/拆分/合并的条目及受影响规则；完整保留仍有效决定与关键理由。退役条目不自动使规则失效。
3. 在内存或隔离临时位置准备正文、记录及最小入口修改。检查覆盖、可执行性、过度约束、层间冲突、引用与例外。无依据的强制项改成有边界的默认或待决，不能用修改验收预期掩盖问题。
4. 未解决冲突的提议仅放记录中并明确未生效，旧有效规则继续保留。不受影响的更新可落地，结果说明部分完成。首次生成有待决时，仅列已成立规则和清楚的待决边界，不称全量规范已经确认。
5. 写入前重读文件并比较原内容。发现其他修改则重读合并；不能覆盖未知改动。先保存完整候选记录，再保存经检查的正文，最后接入根入口；使用可靠局部编辑或同目录临时文件替换，避免截断文件。不建设发布引擎或声称多文件事务原子性。
6. 重读产物，核对正文修订与记录、所有适用全局引用、项目入口和保留内容。写入失败按实际状态报告，不凭内存中的候选宣称完成。恢复时正文和实际入口是读取依据，未被正文采用的候选不自动生效；不自动发布旧候选。

交付区分：清单覆盖是否完整、全局接入是否完整、入口是否接入、规范语义及结构检查范围、代码是否验证。普通实现分歧不新增审批流程；修改硬约束和未授权外部操作仍遵守已有边界。
