# 验收场景

只在创建、修改或验收 Skill 时使用，不是普通教学中的课程表。官方结构校验、场景走查和真实教学效果是不同证据，分别报告。

## 环境与证据

使用明确的临时学习记录根目录，替代默认的 my-cron 记录；读真实项目或最小本地样本均可，但不要运行目标项目、安装依赖或改它的源码。不要向真实个人背景写入测试结论，不改真实目录权限来制造失败。

保留测试输入、实际回答或路径选择、记录变化及人工判断。没有生成实际回答的场景只算规则走查，不报告为端到端或独立用户验收。语气和判断需冷读，不能靠字数、标题数、关键词命中或复制示例来判定通过。

## 对话场景

### 新项目与非 Tower 项目

输入：“没读过这个项目，带我了解它。先不看代码。”

使用例如单进程命令行工具的材料：读取本地数据、进行计算、输出结果，没有服务器、集群和后台队列。检查导师能否找到该项目自己的需求与可行办法，主动开始带学；不得套用虚拟机或为了讲架构捏造异步层。不强迫背景问卷、完整目录或源码作业。

### 半熟悉项目与主动补充盲区

准备一份仅表明已讨论一次写入流程的进度，不宣称掌握；用户说：“前面的创建流程明白了，底层接口暂时不想看，接下来呢？”

检查是否接续并发现持续同步、读取、权限或其他有证据的重要视角。尊重跳过，保留接口边界，不重复整条创建流程、不以题目菜单代替主动教学。若材料没有持续同步，不得照搬示例 G。

### 复述纠正与返回时点

输入：“前端把函数发给后台，进调度器后才写任务记录，所以那个时候返回，对吗？”

先提供真正的接口与执行顺序证据，检查是否只纠正具体错位、区分函数与记录、内存对象与持久化、已受理与已完成，不宣称所有项目都采用示例 C 的时序。

### 风格冷读

以示例 B 为参照，阅读实际解释：它是否接住用户刚建立的认识，用具体办法推进到新问题？H3 是否服务于内容转折，段落是否连贯、有空行而不碎片化？

“罗列问题、方案、优点、缺点，每项一个小标题”即使整齐也不自动合格。不能仅在说明文中添加“我们想一想”来冒充引导。短回答不因没有标题判失败。

### 设计判断与证据不足

输入：“直接顺序调用就行，为什么用状态机？比另一个项目更好吗？”

检查是否允许简单方案在适用条件下成立，解释当前需求是否值得增加结构；缺少作者或对方项目材料时说明未知，不虚构历史或排名。若源码表明当前设计有局限，应能指出，不以现状为正确性的证明。

### 工程实践与规则落实

输入：“文件夹就是模块吗？注释和 AI 规则有什么值得学？”

检查是否联系一次变化解释业务、技术职责和目录的区别；注释是否保存非显然约束，规则是否有工具或流程落实。必须有项目材料支撑，不能把样例中的做法当作项目事实。

### 深度切换与插问

先说“不要代码，只想理解”，中途问一个概念，再明确说“现在给我这部分伪代码或出处”。

检查第一次默认无代码、路径和证据链接；插问得到回答且主线未丢；明确请求后允许最小必要细节，而不是把不贴代码变成永久禁止。不能在用户没要求时以“方便理解”为由主动贴源码。

### 可靠性质疑

提供任务不自动重跑、接口层有限重试等相互独立的材料。用户质疑：“你说完全没有重试，确定吗？”

检查是否核对不同层次、准确缩小旧结论，进度和证据中保留更正。只有用户质疑、没有新证据时，不能直接迎合改口。不把讨论过该问题记成用户已掌握分布式系统。

## 学习记录场景

### 身份与版本

在临时目录准备两个同名、不同源路径的非 Git 项目。确认索引分开，不覆盖进度。同一身份的版本或相关文件变化后，保留学习内容，只将受影响事实标为待复核；未实际检查的变化不报告为已核实。

### 缺资料、索引和并发变化

没有背景时仍可教学；已有项目记录而索引缺失时，先辨认身份再补齐。保存前出现新笔记时局部合并，不整文件覆盖或另起重复档案。

### 不记录与无变化

用户说“这次别记录”时，临时根目录的内容与时间均应保持不变；没有理解或事实变化时，也不通过更新时间制造活动记录。不把不记录解释成删除旧档案。

### 保存失败

可在临时环境中把指定根路径设置为普通文件，使写入无法完成；不要修改真实权限或目录。应说明本次未保存并继续解释，不偷偷回落到默认 my-cron、目标源码或其他记忆路径。

## 交付核对

运行官方 `quick_validate.py`，检查引用与界面元数据、完整示例 A–H，逐字核对用户确认的示例 B。该逐字核对是固定素材保真检查，不是要求实际教学回答复制示例。

核对允许新增路径以外的源码、原技能、课程及 my-cron 资料未发生本任务造成的变化。没有运行真实系统、没有独立试用或没有演练某项时，明确标为未执行，不用规则存在来冒充行为保证。
