# Go 开发规范

与通用开发规范共同使用。本文件补充 Go 的具体写法，不规定项目的框架、目录分层或数据库访问方式。

## 格式与命名

- 使用 gofmt 格式化代码。
- 普通名称采用 mixedCaps，导出名称首字母大写；不使用下划线分隔普通变量、函数和类型名称。
- 常见缩写保持一致，例如 `userID`、`HTTPClient`、`ParseURL`，不混用 `userId`、`HttpClient` 等写法。
- 包名使用简短的小写名称，表达具体职责；避免将不同能力持续堆入 `utils`、`common`、`helpers`。
- 布尔名称表达明确状态，例如 `enabled`、`isExpired`、`hasPermission`，避免含义模糊的 `flag`。
- 集合使用复数业务名称，例如 `articles`；需要强调映射关系时，使用 `articleByID`、`usersByRole`。
- `ctx`、`err`、局部循环索引 `i` 等惯用短名称可以保留。业务对象使用可辨认的业务名称。

## 函数与方法

- 动作函数使用明确的动词及必要的业务对象，例如 `FetchArticle`、`SaveArticle`。避免 `DoWork`、`ProcessData` 等无法判断具体行为的名称。
- 类型已经表达的信息不在方法名中重复，例如使用 `subscription.Cancel()`。
- 方法用于表达所属类型的行为；不依赖该类型状态或职责的独立计算，使用普通函数即可。
- 同一类型统一使用相同的接收者名称，使用类型相关的简短名称，不混用 `self`、`this` 和其他别名。
- 修改接收者状态的方法使用指针接收者。其他方法结合复制成本、类型语义和方法集选择，不按个人习惯随意切换。
- 不定义调用顺序隐蔽的 API。必要的初始化应由构造入口保证，或在非法状态下返回明确错误。
- 避免出现无法从调用处理解的多个布尔参数，例如 `Save(article, true, false)`。根据复杂度采用有名称的类型、选项或职责更明确的方法。
- 需要 context 的函数，将 `context.Context` 作为第一个参数，通常命名为 `ctx`。

## 类型与接口

- 使用能够表达已知数据结构的类型，不用 `any` 逃避已经明确的字段和契约。
- 默认使用具体类型。需要替换实现、隔离外部依赖或建立测试边界时，再定义接口。
- 接口围绕使用方需要的行为设计，不机械地为每个结构体生成一份包含全部方法的接口。
- 不仅为了统一形式，就给所有构造函数增加接口返回值、错误返回值或配置结构；这些应对应真实需要。

## 错误处理

- 普通业务失败通过 error 返回，不使用 panic 代替错误处理。
- 检查错误后及时处理，使成功路径保持清楚。
- 增加错误上下文时描述失败的操作；需要保留错误链时使用 `%w`。
- 调用方需要识别错误时使用 errors.Is 或 errors.As，不依赖错误字符串匹配。
- 错误向上返回时，默认由负责最终处理的边界记录日志，避免每层重复记录同一次失败。
- 有意忽略错误时，应能说明不会影响正确性的原因；原因不明显时在代码附近解释。

## 并发与资源

- 新增 goroutine 时，必须能从实现中识别其管理者、退出条件和失败处理方式。
- 属于请求的工作应遵守请求的取消约定。需要在请求结束后继续执行的工作，应由具有独立生命周期的任务或服务管理。
- 不随意使用 context.Background() 替换已有上下文，切断上游取消和超时控制。
- 根据所有权和通信需要选择锁或 channel，不强制所有并发场景使用同一种机制。
- 使用 channel 时明确关闭责任，不由无法判断发送是否结束的一方随意关闭。
- 取得需要关闭的资源后安排可靠的释放路径。循环中需要及时释放的资源，不依赖累积到整个函数结束才执行的 defer。

## 注释

- 导出 API 编写以标识符开头的说明，描述用途及调用者需要知道的关键契约。
- 项目控制之外的接口实现、生成代码或已有统一文档机制，可按相应约定处理，避免复制无用说明。
- 内部函数不要求全部添加注释；名称和实现已经清楚时，不重复解释。
- 注释示例：

  // FetchArticles 抓取订阅源中的文章。
  // 单条文章解析失败时跳过该条；订阅源无法读取时返回错误。

  其中的失败行为必须与实际契约一致，不能套用示例文字。
