# Skill 验证

仅维护 Skill 时使用，不是用户日常生成规范的流程。结构检查不能证明生成物有用；AI 自述遵守不能替代实际读写和行为证据。

## 方法

先运行 skill-creator 的 quick_validate.py，检查本 Skill 的内部链接、样例、清单编号和界面说明；确认引用中没有仍要求执行的版本/发布流程。

行为测试在隔离目录，用当前可用的 AI 执行环境实际加载待测 Skill，从自然语言请求开始。可串行运行独立测试上下文，不手工制作最终结果冒充生成。测试提示只给请求、Skill 位置和允许范围；预期答案留在测试审查侧。

保存请求、退出状态、回复、实际工具调用和前后文件摘要。测试产物不得写进真实个人规范库、项目或其他 Skill。允许准备已有正文和冲突作为前置条件。

## 关键场景

1. **模糊偏好生成 Go**：用户只说易读、一致、不要过度设计。AI 直接生成公共与 Go 两份当前正文，不先问整张清单；命名、方法调用、注释等写法具体，设计规则有条件与例外，不产生版本、INDEX、台账或 Python 文件，不冒称用户逐项确认。
2. **局部更新及重复调用**：改变注释语言并保留业务术语例外，已有自定义条款和无关文件不变；重复请求不发生写入。
3. **只读检查与项目归属**：检查遗漏并讨论 ORM 或技术栈，不修改文件、不将项目实现写成全局硬约束。
4. **新增角度与公共关联**：用户补充此前遗漏的代码质量要求，直接补进正文；公共要求影响已有语言写法时同步检查，只处理相关条款，不生成清单快照。
5. **Python 补充**：复用已有公共规范，生成同等具体的 Python 写法，避免复制 Go 习惯或加载无关语言。自有公共偏好保留。
6. **未决硬约束冲突**：说明实际冲突，不静默选择优先级，不将未解决内容说成有效成品；独立工作仍可完成。
7. **下游实际使用**：给新的开发/评审上下文只提供生成的公共和语言正文以及普通代码任务，不提供 Skill、清单、标准答案或维护历史。检查是否能据规则选写法、指出具体违反，且允许合理例外。

下游可用性至少观察：业务命名与方法调用；日志后伪装成功与合理缓存降级的区别；真正需要的接口与无收益转发层的区别。可以使用正反代码片段，不向被测上下文提示哪一段有错。

检查产物时依据本次请求、用户认可的成品尺度和代码行为，不用“文件存在/包含若干关键词”代替语义判断。保留少量代表性原始输出供人工复核。不要为了通过验证向测试提示塞答案或调整用户预期。

实际未运行的场景如实列出。未测试中断恢复不能声称有恢复保证；当前设计不提供多文件事务或发布协议。最终报告结构、生成更新行为和下游应用各自的结果，不保证所有未来模型和任务都一致。
