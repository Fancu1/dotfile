# 公共确认清单

内置版本：`core-1`。这是确认问题，不是已批准的规范。每行独立处理；可映射到同一规则，但保留逐项结论。推荐起点是可选择的默认，不冒充用户决定。用户扩展与本清单共同构成有效清单，按 library.md 保存内容依据。

## 代码表达

| 编号 | 确认问题 | 推荐起点与边界 |
|---|---|---|
| EXP-01 | 格式化遵循什么依据？ | 沿用语言与项目工具；不在公共层硬编码命令或版本。 |
| EXP-02 | 命名和语言惯例如何表达含义并保持局部一致？ | 优先领域词汇、明确单位，不给所有语言套同一命名法。 |
| EXP-03 | 函数与类型的职责如何清楚？ | 能说明承担什么责任，避免无关职责；不指定架构或行数配额。 |
| EXP-04 | 控制流如何容易理解？ | 避免无意义嵌套和隐式跳转，不为简短牺牲语义。 |
| EXP-05 | 重要状态变化和副作用如何明确？ | 用契约、命名、结构或必要注释表达，不要求所有函数纯函数化。 |

## 注释要求

| 编号 | 确认问题 | 推荐起点与边界 |
|---|---|---|
| COM-01 | 注释使用什么语言？ | 优先明确偏好和项目惯例；否则可默认与维护者语言一致，标记 AI 选择。 |
| COM-02 | 哪些业务约束和特殊行为需要解释？ | 解释代码无法可靠表达的条件、原因和后果。 |
| COM-03 | 哪些公开契约和设计原因需要说明？ | 解释前提、必要例外和不直观取舍，不要求每个函数必写注释。 |
| COM-04 | 如何防止注释过时、矛盾或重复代码含义？ | 行为变化时同步相关注释，不按数量验收或机械逐行解释。 |
