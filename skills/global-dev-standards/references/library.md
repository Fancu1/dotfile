# 规范库与维护格式

## 目录与事实源

默认库根 `~/.config/ai-dev-standards/`，用户可覆盖。使用一次解析出的同一根；不要在测试或指定库之外初始化个人库。相对路径均基于库根，Markdown 链接则按所在文档正确解析。

- `INDEX.md`：已发布文件及批次、当前推荐组合。它是发布状态依据，不把目录中最大的版本号当作有效版本。
- `common/vN.md`：公共规范；`languages/<language>/vN.md`：语言补充。只生成实际启用的语言。
- `records/checklist.md`：清单版本、已采用条目内容快照、用户扩展、修订关系。
- `records/decisions.md`：逐项处理、来源、理由、待决、兼容检查和变更批次。

清单和决策记录可追加新批次或修订，保留历史及用户扩展。未发布批次不能覆盖此前有效判断。不存在历史库时创建；已有库时先读取格式与内容，不粗暴重写成模板。

## 最小输出模板

模板用来保证接手 AI 能唯一理解依据，表格可以扩展，不需要额外 JSON 系统。示意值需替换为实际结论，不直接发布模板。

### INDEX.md

```markdown
# 全局开发规范

库根：本文件所在目录。项目必须固定组合中的明确文件版本并实际读取。

## 当前推荐组合
| 使用范围 | 公共版本 | 语言版本 | 核对批次 |
|---|---|---|---|
| 通用 | [common/v1.md](common/v1.md) | 不适用 | B001 |
| Go | [common/v1.md](common/v1.md) | [languages/go/v1.md](languages/go/v1.md) | B001 |

## 已发布版本与记录
| 文件 | 发布批次 |
|---|---|
| common/v1.md | B001 |
| languages/go/v1.md | B001 |

维护记录：[清单](records/checklist.md)、[决定](records/decisions.md)。
```

保留所有历史已发布版本的登记。已被替换的推荐组合不再用于新接入，但项目固定旧版本仍有效。组合中的版本必须完整存在且兼容。语言补充不可独立取“最新”与公共文件拼接；Go、Python 的推荐公共版本可以不同。

### 规范正文

```markdown
# 公共开发规范 v1
适用：跨语言代码质量。与明确选定的语言补充共同使用。

## C-01 规则短名
强度：必须 / 默认建议（二选一）。
要求：具体可执行的要求。
适用条件与关键原因：会影响规则正确理解的前提。
例外或开放空间：必要例外；具体机制由项目选择的部分。
```

规则编号跨版本追踪同一含义，不将同一编号用于无关新规则。措辞保持简短，不为每条强行填无意义段落。条件、原因与例外必要时必须保留；公共责任不复制为各语言的整段规则。语言正文声明所需公共规则前提，兼容性通过入口组合表达，不固定必须与同号公共版本搭配。

### 清单记录

```markdown
## 清单 K001
基础：core-1；启用补充：go-1；用户扩展：无。
| 条目编号 | 本次采用的完整确认问题与判断边界 | 来源及版本 | 前序关系 |
|---|---|---|---|
| EXP-01 | 实际问题及足以比较语义的边界 | 内置 core-1 | 初次 |
```

保存每个适用条目的问题及判断边界，不能只列编号或指向会被升级覆盖的 Skill 路径。语言快照同理。用户扩展用 `USR-...` 编号并记录范围；不伪造内置版本已改变。用户对内置项的调整保留原编号、旧内容及本库的新修订；不修改 Skill 文件。

内置升级时比较之前快照与新的内置内容，再结合用户扩展；冲突不可用升级覆盖。删除条目标记退役，拆分/合并列出关联旧编号，旧结论留历史，不直接继承为新条目的“已处理”。措辞只改表面但语义未变时记录比较依据即可。

### 决策记录

```markdown
## 批次 B001
意图：实际自然语言请求的语义。
依据：入口原状态；清单 K001；用户明确偏好或其他依据。
发布状态：以 INDEX.md 是否登记本批次为准；记录本身不意味着发布。

| 条目 | 依据清单/修订 | 结论 | 来源 | 规则引用或开放空间及理由 |
|---|---|---|---|---|
| EXP-01 | K001 | 沿用/默认 | AI 推荐，未获用户逐项确认 | common/v1.md C-01；实际理由 |

影响与重查：变化的语义、失效判断、关联项以及可复用旧结论的依据。
组合核对：公共与每个受影响语言版本是否兼容，原因及结果。
待决或未验证：实际问题；没有则说明没有。
变更结果：候选、已发布或失败情况，最终以入口核实。
```

首次覆盖所有适用项；增量批次只记变化和关联项，并引用未变判断所在批次，不抄整张表。记录字段可合并，但条目、内容依据、处理结论、来源、规则/开放空间和理由不能丢失。硬约束也可能来自 AI 推荐，必须区分约束强度与谁作了决定；已授权生成不等于用户亲自确认了每条措辞。

只读检查在回复中报告，不为了记录覆盖而写文件。已发布记录与候选记录并存时，读取者应按批次和入口区分，不用最后一段自动覆盖有效结论。

## 增量失效

对照本次请求、当前内置清单、库内快照和有效规则：

| 变化 | 需要复查 |
|---|---|
| 新增、修改或删除条目 | 变化含义、旧结论、对应规则及关联项；删除清单项不自动删除有效规则。 |
| 拆分或合并 | 每个新项的实际含义及旧决定能否沿用，保留前后关联。 |
| 偏好、来源或适用范围变化 | 依赖该依据的决定，不能只比编号和规则文字。 |
| 公共规则改变 | 先判断所有当前推荐语言组合的影响，再复查受影响规则；无影响须有理由。 |
| 前提被推翻 | 所依赖判断重新处理；无法证明仍适用就不能沿用完成状态。 |

只改变依据记录而正文仍合理时，不增规则版本；同样请求、内容和依据都未变时不增版本也不追加无意义记录。

## 发布协议

不增加专用发布引擎，使用当前可靠的本地文件工具完成以下顺序：

1. 记录当前入口和将维护文件的实际内容，识别已有候选。选择尚未占用的新规则版本名；不能覆盖已发布文件或含用户改动的候选。新建库无入口时明确属于首次发布。
2. 将候选规则、清单与决策记录准备完整。记录按批次追加并保留此前内容，追加阶段即使失败也不能破坏此前可用记录；必要时也通过同目录临时文件替换记录。正文文件存在不意味着已发布。
3. 检查所有适用确认项有可追溯结论，待决不算覆盖。检查语义、必要原因、硬约束、引用及推荐组合。某语言组合冲突时保留它的旧组合；兼容且不受冲突影响的其他组合可以更新，并明确此次是局部完成。若冲突影响所有候选组合，就不切换入口。
4. 在入口同目录准备完整临时入口。所有新登记文件及记录必须已写好并可读，旧登记须保留。替换前再核对旧入口/记录未被其他写入改变；出现变化时重读合并，不覆盖另一人的更新。
5. 用同文件系统原子替换（例如 `os.replace`）切换 INDEX.md，而非直接截断写入口。此动作是发布边界。切换前失败保留旧入口；没有旧入口则维持未发布状态。
6. 替换后重读入口并验证所有引用、组合和批次。结果以磁盘事实为准，不能仅凭记录写了“成功”宣称发布。

恢复时读取旧入口与未登记候选，核查它们是否完整、与当前请求和前提一致。可复用完整候选；不完整或不再适用的候选保留未发布，另选未占用版本。不要递归删除候选目录、改权限、覆盖用户扩展或偷偷放宽检查以推进。

## 接入约定

本 Skill 只产出规范库，不修改项目。后续项目流程选择并固定明确组合，实际读取公共和涉及语言文件；规范正文应能独立理解。缺少固定版本时报告，不改用推荐最新版本。各层具体化默认规则不等于任意覆盖硬约束，真实例外要显式处理。
