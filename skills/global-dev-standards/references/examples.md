# 交互与成品尺度

## 偏好模糊也能先给成品

用户：帮我生成 Go 全局规范。我不知道该怎么写，希望代码容易读、风格一致，不要过度设计。

AI 开始：我会把这些偏好落实到命名、方法、注释和设计取舍中，普通细节采用一致的默认，直接生成公共与 Go 两份规范。

随后实际生成 `common.md` 与 `languages/go.md`，具体程度参照 assets 下两份成品。内部走完整检查，不先问布尔变量命名、receiver 名称或抽象阈值。

AI 交付：已生成两份规范（给实际链接）。采用了中文业务注释、明确的 Go 命名约定、按真实需要引入接口等默认。项目规范引用这两个路径并要求开发前实际读取即可。

不要说“你已逐项确认”，不要附 43 项决策表，也不要以“接下来等你回答清单”结束。

## 用户主动讨论

用户：先讨论一下注释怎么写，暂时不要生成。

AI：建议默认中文解释业务原因；公开 API 说明调用前提、失败和副作用；内部代码不逐行翻译。例如 `FetchArticles` 应说明单条解析失败是否跳过、源读取失败是否返回错误。这样调用方不必读实现才能理解契约。

在回复中给具体草案，再根据反馈调整。保持只读，不把讨论认可当成尚未请求的文件修改授权。不恢复完整问卷。

## 明确偏好覆盖默认，更新不重建

用户：把注释改成英文，但业务术语可以保留中文，其他不要动。

AI 读取已有正文，局部替换注释语言条款，保留该例外；检查语言文件是否有相关重复规定或相反要求，只调整受影响内容。交付说明实际变更，不再次询问所有偏好，不生成新版本或记录。

用户再次提出同样请求：如果当前已满足，说明无需变更，不重写文件。

## 项目事项与未知冲突

用户：检查规范有没有遗漏，所有项目都应该统一用一个 ORM 吗？

AI 只读检查当前规则，说明 ORM 属于项目选择，给出全局层可采用的依赖评估原则；不写文件或全局强制 ORM。

用户：更新 Go 方法命名，已有的两条相反注释硬约束暂时还没决定怎么改。

AI 完成不受影响的命名调整，保留并说明注释冲突，不能借机静默放宽其中一条或宣称所有规范已无冲突。

## 同一个要求怎样写才可用

不足：命名清楚，遵守语言惯例。

可用：布尔变量表达状态，如 `enabled`、`isExpired`；避免用 `flag` 表示无法从名称理解的状态。集合使用复数业务名称，如 `articles`。

不足：适度抽象，避免重复。

可用：先判断两处代码是否表达同一规则、是否应该共同变化。仅外形相似但业务含义不同，允许独立；不要仅为未来可能替换给每个结构体生成接口。

不足：后台任务应有明确责任。

可用：实现中必须能识别后台任务的管理者、退出条件和失败观察路径。需要在请求结束后继续的工作交给独立生命周期管理，不仅为提前返回就启动无人管理的 goroutine。
