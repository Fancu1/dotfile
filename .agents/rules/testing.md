# 测试、验证与交付规范

本文件规定 Go 后端项目完成实现后的测试、验证、自检和交付方式。

目标不是追求测试数量，而是能够回答：

> 这次实现是否真的符合需求？
> 关键失败场景是否被保护？
> 实际代码是否仍然符合已经确认的设计？
> Agent 声称“完成”的依据是什么？

验证分为三个层次：

1. **行为验证**：功能实际是否正确；
2. **设计验证**：代码组织是否符合 Plan 和项目规范；
3. **交付验证**：最终 Diff、验证结果和未覆盖内容是否清楚可信。

---

# 1. 核心原则

验证应围绕：

> **需求承诺、重要风险和设计约束**

而不是围绕：

> “这次改了多少行代码”。

测试数量不是目标。

覆盖真正可能出错且会影响业务结果的地方才是目标。

---

# 2. 测试通过不代表任务完成

以下结果只能证明部分正确：

```text
go test ./...
通过
```

它不能自动证明：

- 模块职责正确；
- Service 编排清晰；
- Repository 没有隐藏业务逻辑；
- API 契约符合 Plan；
- 没有增加多余抽象；
- 没有夹带范围外修改；
- 并发和恢复行为正确；
- 实际运行链路能够工作。

因此完成任务前必须同时进行：

```text
行为验证
+
设计验证
+
Diff 检查
```

---

# 3. 验证以 Plan 的验收条件为起点

存在已确认 Plan 时，完成实现后先重新读取 Plan 中的：

- Use Case；
- 业务链路；
- 关键函数；
- 数据变化；
- API 契约；
- 异步行为；
- 失败与边界；
- 验收条件。

然后逐项验证。

例如 Plan 写明：

```text
正常创建
→ admin 新增
→ event 新增

event 写入失败
→ admin 回滚

重复创建
→ admin_exists
```

那么测试至少应该覆盖这些结果。

不要实现完成后重新发明一套更容易通过的验收标准。

---

# 4. 测试优先验证可观察行为

优先测试：

```text
输入
→ 行为
→ 状态变化
→ 返回结果
```

例如：

```text
调用 CreateAdmin
→ admin 被创建
→ event 被创建
→ 返回正确结果
```

而不是重点测试：

```text
某个私有 helper 被调用了几次
某个 if 分支是否存在
内部函数具体按什么顺序调用
```

除非这些调用顺序本身属于业务契约。

测试应允许内部实现合理重构。

---

# 5. 不为私有实现机械写镜像测试

不要因为出现一个函数：

```go
normalizeRoleIDs(...)
```

就一定单独写测试。

如果它只是某个 Use Case 的简单内部步骤，可以通过业务测试覆盖。

适合单独测试的内部逻辑通常是：

- 复杂纯算法；
- 大量边界输入；
- 独立解析逻辑；
- Unicode / 时间 / 金额等容易出错的计算；
- 多处复用且语义稳定的逻辑。

判断标准：

> 单独测试它是否能够明显提高错误定位或边界覆盖？

如果不能，不为了覆盖率数字机械增加测试。

---

# 6. 不测试第三方库本身

不要重复证明：

```text
标准库能不能解析 URL
GORM 会不会执行 INSERT
JSON Encoder 能不能编码字符串
第三方 RSS Parser 能不能解析官方示例
```

应测试：

> 我们如何使用这些能力，以及我们的业务约束是否正确。

例如使用正文提取库时，应测试：

```text
给定固定 HTML
→ 我们得到预期标题和正文
→ 导航内容被过滤
→ 空正文按我们的契约失败
```

而不是重新测试整个 Readability 实现。

---

# 7. 测试分层

根据改动实际风险选择测试层级，不要求所有任务全部执行。

常见层级：

```text
静态检查
单元测试
Repository / 数据库测试
Service 测试
API 测试
Worker / 异步测试
集成测试
Race / 并发测试
E2E
实际运行验证
```

每层解决不同问题。

不能用一种测试宣称覆盖所有风险。

---

# 8. 静态检查

Go 代码修改后，至少执行项目已有的：

- format；
- import；
- lint；
- static analysis；
- build。

例如项目存在：

```text
mise run backend-lint
mise run backend-build
```

则优先使用项目统一入口。

如果项目没有统一入口，再根据实际工具使用：

```text
gofmt
go test
go vet
staticcheck
go build
```

不要为了通过检查：

- 关闭有效规则；
- 增加无意义 ignore；
- 大范围格式化无关代码；
- 修改工具配置掩盖当前问题。

---

# 9. Repository 与数据库验证

涉及 Repository 时，应根据实际操作覆盖：

- 查询结果；
- 插入；
- 条件更新；
- 唯一约束；
- 外键；
- 删除行为；
- 事务；
- 并发写入。

Repository 测试关注：

> 持久化操作是否符合它声明的语义。

例如：

```text
CreateArticle
→ 只创建 Article

CreateArticleContent
→ 只创建 Content

MarkArticleImportReady
→ 只在正确 revision + pending 下更新状态
```

不要通过 Repository 测试重新实现完整 Service 业务流程。

---

# 10. 事务必须验证失败路径

只测试全部成功是不够的。

如果业务要求：

```text
A + B + C 必须共同成功
```

至少选择关键失败点验证回滚：

```text
A 成功，B 失败
→ A 不保留

A、B 成功，C 失败
→ A、B 都回滚
```

例如：

```text
CreateArticle
→ CreateArticleContent 失败
→ Article 不应存在
```

```text
CreateArticle
→ CreateArticleContent
→ MarkImportReady 失败
→ Article 和 Content 都应回滚
```

事务测试应证明：

> 不会留下业务上无法解释的半完成状态。

---

# 11. 数据迁移验证

新增或修改 migration 时，至少根据实际风险验证：

## 新数据库

```text
空数据库
→ 执行全部 migration
→ 最终 schema 正确
```

## 历史升级

如果项目支持已有数据库升级：

```text
旧版本数据库
→ 应用新 migration
→ 原有数据保留
→ 新结构正确
```

## 约束

验证：

```text
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
INDEX
```

是否符合设计。

## 数据转换

存在数据迁移时验证：

- 原始数据是否完整保留；
- 转换结果是否正确；
- ID 是否保持；
- 关联关系是否保持；
- NULL / 默认值是否符合设计。

不得通过：

```text
删除数据库重新初始化
```

来代替 migration 验证。

---

# 12. 已应用 migration 不修改

发现历史 migration 不满足新需求时：

```text
新增 migration
```

而不是直接修改已经应用的 migration。

测试数据库可以重建，不代表生产或用户已有数据库可以重建。

涉及破坏性变化时，应按 `data.md` 和项目迁移规范处理。

---

# 13. Service 测试重点验证业务规则

Service 是主要业务负责人，因此测试重点包括：

- 业务校验；
- 状态判断；
- Use Case 分支；
- 事务结果；
- 幂等语义；
- 跨 Repository 协作；
- 调用其他 Service 的业务行为；
- 外部结果如何转成业务结果。

例如：

```text
CreateArticleFromImport

pending + 当前 revision
→ 创建 Article
→ 创建 Content
→ Import ready

已有 Article
→ 复用
→ 不覆盖正文

旧 revision
→ stale
→ 不写入数据
```

Service 测试应让人能够从测试场景理解业务规则。

---

# 14. 业务入口不能绕过 Service 规则

如果某项业务可以从：

```text
HTTP
Worker
Cron
CLI
```

多个入口触发，应验证关键规则不会只存在于其中一个入口。

例如：

```text
Article 不允许重复覆盖原文
```

这条规则应由 Article Service 保证。

不能：

```text
HTTP 会校验
但 Worker 可以绕过
```

重要业务规则的测试应尽可能放在拥有规则的 Service 层。

---

# 15. API 测试验证外部契约

API 测试重点验证：

- Method / Path；
- Request 解析；
- 未知字段；
- Path / Query 参数；
- 状态码；
- Response DTO；
- Error Code；
- Null / Empty 语义；
- Location；
- 资源归属；
- Service Error → HTTP Error Mapping。

例如：

```text
POST /api/article-imports

非法 URL
→ 400 ARTICLE_IMPORT_INVALID_URL

新请求
→ 202
→ 返回 pending
→ Location 指向状态资源

已有 ready
→ 200
→ 返回 article_id
```

API 测试不应承担所有业务规则测试。

复杂业务主要在 Service 层覆盖。

---

# 16. API 测试不要依赖真实外部系统

普通自动测试中：

```text
HTTP Handler
→ Service Fake / Test Double
```

或：

```text
完整本地 Service
→ Fake 外部 Client
```

不要默认：

```text
真正访问 GitHub
真正调用 AI
真正抓取某个新闻网站
```

否则测试容易因：

- 网络；
- 限流；
- 网站变化；
- Token；
- 费用；

变得不稳定。

---

# 17. 外部 Client 使用固定样本测试

解析网页、RSS、Webhook 等能力时，优先保存固定测试 Fixture。

例如：

```text
testdata/
├── article.html
├── article-no-title.html
├── rss.xml
└── atom.xml
```

测试：

```text
固定输入
→ 固定业务结果
```

而不是每天访问真实网站判断测试是否通过。

真实网站测试属于：

> 集成验证 / 手工验证

不属于默认 CI 单元测试。

---

# 18. 外部调用测试错误分类

Client / Connector 应覆盖与业务有关的主要错误类别，例如：

```text
timeout
429
5xx
非法响应
认证失败
连接失败
内容过大
解析失败
```

重点验证：

> 我们是否将外部错误正确分类。

例如：

```text
HTTP 503
→ temporary

非法 Feed
→ permanent

缺少认证配置
→ configuration error
```

重试策略本身由 `runtime.md` 定义。

---

# 19. 异步受理必须验证原子性

如果业务承诺：

```text
保存业务状态
+
提交持久任务
```

必须共同成功。

例如：

```text
CreateArticleImport
+
Enqueue(import_article)
```

测试至少覆盖：

```text
状态写入成功，Enqueue 失败
→ 两者全部回滚
```

不能留下：

```text
pending
但是没有任务
```

如果系统采用其他恢复策略，也必须验证对应恢复行为。

---

# 20. Worker 测试覆盖生产到消费的关键语义

异步任务至少根据实际业务考虑：

```text
正常消费
重复消费
过期任务
旧 revision
可重试失败
永久失败
最终失败
请求取消
进程停止
```

不是所有 Worker 都必须覆盖全部情况。

根据任务真实风险选择。

---

# 21. 重复消费必须验证

默认假设异步任务：

> 可能执行超过一次。

因此应验证：

```text
第一次成功
→ 第二次再执行
```

不会：

- 重复创建业务对象；
- 覆盖已经完成的数据；
- 重复发送不可接受的副作用；
- 将新状态改回旧状态。

如果某项副作用无法完全做到 exactly-once，应明确实际保证，而不是测试里假装只会执行一次。

---

# 22. 旧任务和旧结果必须验证

存在：

```text
revision
version
generation
updated_at
optimistic lock
```

等机制时，应测试：

```text
旧任务晚到
→ 不能覆盖新结果
```

例如：

```text
revision=1 Worker
revision=2 已重新受理

revision=1 完成
→ stale
→ 不写入
```

---

# 23. 重试测试验证业务结果，不绑死队列内部实现

测试应关注：

```text
临时失败后最终可以成功
永久失败不会无限重试
最终失败会正确更新业务状态
```

不要过度依赖：

```text
内部 Job ID
具体数据库任务行
队列内部函数调用次数
```

除非这些就是 Job 模块本身的测试。

业务测试应尽量对队列实现保持独立。

---

# 24. 取消与 Shutdown 需要针对性验证

涉及：

- Worker；
- 长网络请求；
- Cron；
- 后台 goroutine；
- Server Shutdown；

时，根据风险测试：

```text
context cancel
进程 shutdown
正在执行的任务
停止领取新任务
清理资源
```

需要区分：

```text
请求取消
任务超时
服务正常停机
强制终止
```

它们不一定具有相同业务语义。

不要把所有：

```go
context.Canceled
```

都解释成业务失败。

---

# 25. 并发风险使用 race 和并发场景测试

涉及：

- goroutine；
- shared state；
- Worker；
- 并发更新；
- 状态竞争；
- cache；
- scheduler；

时，应考虑执行：

```text
go test -race
```

并补充真实竞争场景。

例如：

```text
两个请求同时创建相同资源
两个 Worker 同时完成同一任务
旧 revision 与新 revision 同时写回
```

Race Detector 通过不代表业务竞争正确。

因此：

```text
race check
+
业务并发测试
```

两者解决不同问题。

---

# 26. 幂等验证必须模拟重复操作

如果 Plan 声明操作幂等，应实际验证：

```text
相同请求连续执行两次
```

例如：

```text
收藏
取消收藏
重复提交相同 URL
重复完成任务
重复创建已存在订阅
```

不能只看代码里存在：

```text
UNIQUE
ON CONFLICT
```

就宣布幂等。

需要验证外部可观察结果。

---

# 27. E2E 只覆盖关键用户链路

E2E 成本高，应重点覆盖真正重要的完整链路。

例如：

```text
提交文章链接
→ pending
→ Worker 完成
→ 文章进入列表
→ 打开正文
```

而不是为每个输入校验写浏览器测试。

适合 E2E：

- 跨多个模块；
- 前后端状态协作；
- 异步状态更新；
- 用户关键流程；
- 单层测试难以证明的行为。

简单 validation 留在较低层测试。

---

# 28. E2E 不应该依赖真实付费 AI

默认使用：

```text
Fake / Stub AI Provider
```

提供稳定输入输出。

测试：

```text
系统如何处理 AI 结果
```

而不是：

```text
这个模型今天是否生成了一段满意的文章
```

真实 AI 内容质量属于：

- 手工验收；
- 专门评测；
- 独立集成测试。

不能与普通 CI 稳定性混在一起。

---

# 29. 测试使用隔离数据

自动测试不得默认使用：

- 用户真实数据库；
- 开发中的个人数据；
- 生产数据；
- 正在运行服务的数据卷。

优先：

```text
临时 SQLite
临时目录
临时端口
独立容器
测试专用数据库
```

测试完成后清理自己创建的资源。

不能因为“测试方便”删除用户已有数据库或 Volume。

---

# 30. 测试不能依赖执行顺序

每个测试应尽量能够独立执行。

不要要求：

```text
TestCreate 必须先运行
然后 TestUpdate
然后 TestDelete
```

测试自己创建需要的数据。

如果确实测试完整状态流程，应在一个明确测试场景中完成，而不是依赖多个测试函数运行顺序。

---

# 31. 时间相关测试使用可控时间

涉及：

- 重试；
- 到期；
- 复习间隔；
- Token 过期；
- Cron；
- timeout；

时，避免大量真实 sleep。

优先：

- 可注入 Clock；
- 明确时间输入；
- 可控 Scheduler；
- 小范围同步机制。

不要为了等一分钟的定时任务让测试真的 sleep 一分钟。

如果为了测试引入 Clock 抽象反而显著增加复杂度，应根据实际需求权衡。

---

# 32. 随机性应可控

涉及随机值时：

- 固定 Seed；
- 注入 Generator；
- 只断言与随机具体值无关的性质。

不能出现：

```text
这个测试偶尔失败是正常的。
```

Flaky test 属于问题，不属于可接受状态。

---

# 33. 测试失败时不能修改正确需求迎合实现

如果实现和测试冲突，先判断：

```text
需求错？
Plan 错？
测试错？
实现错？
```

不能因为实现已经写完：

```text
直接把测试 expected 改成当前错误行为。
```

特别是原有测试表达稳定契约时，应优先保留。

需要改变业务契约时，应先按对应设计流程确认。

---

# 34. 不删除有效测试制造通过

禁止：

```text
删掉失败测试
注释断言
扩大误差范围
跳过测试
降低校验
```

只为了让 CI 变绿。

确实发现测试已经过时，应说明：

- 为什么旧预期不再成立；
- 新契约是什么；
- 哪个需求授权了变化。

然后同步修改测试。

---

# 35. 不把 Mock 调用次数当成主要业务断言

不推荐：

```text
Expect(repo.Create).Times(1)
Expect(repo.Update).Times(1)
```

作为主要正确性证明。

更重要的是：

```text
最终业务结果是否正确？
失败时是否回滚？
重复调用是否安全？
```

调用次数可以用于：

- 确认真正重要的副作用没有重复发生；
- 外部调用成本很高；
- 重复调用本身就是错误；

但不应该让测试与普通内部重构高度耦合。

---

# 36. 测试名称应表达业务场景

推荐：

```text
TestCreateAdminRejectsDisabledRoles
TestCreateArticleFromImportRollsBackWhenContentSaveFails
TestArticleImportIgnoresStaleRevision
```

不推荐：

```text
TestCreate1
TestErrorCase
TestServiceMethod
TestFoo
```

读测试名应大致知道：

> 在什么条件下，预期发生什么。

---

# 37. Table-Driven Test 按实际价值使用

适合：

```text
大量输入边界
相同流程不同参数
状态码映射
parser cases
validation cases
```

不适合把：

```text
完全不同的业务场景
```

硬塞进一张巨大 table。

测试可读性优先于形式统一。

---

# 38. 测试代码也要可读

测试应使用：

```text
Arrange
Act
Assert
```

或等价清晰结构。

例如：

```go
func TestCreateAdminRejectsDisabledRole(t *testing.T) {
    // 准备管理员不存在、角色已禁用的数据。

    // 调用 CreateAdmin。

    // 断言返回 ErrInvalidRoles。
    // 断言没有创建管理员。
    // 断言没有创建事件。
}
```

不要让测试初始化代码淹没真正断言。

复杂 Fixture 可以抽辅助函数，但避免建立另一个测试框架。

---

# 39. 测试辅助函数不隐藏关键前提

例如：

```go
prepareEverything(t)
```

内部创建：

```text
用户
角色
文章
任务
设置
数据库
```

会让测试难以理解。

更推荐名字明确：

```text
createTestUser
createEnabledRole
insertPendingImport
```

测试读者应知道场景依赖什么状态。

---

# 40. 设计验证独立于行为测试

代码实现完成后必须进行设计检查。

至少检查：

## 业务负责人

```text
这个 Use Case 是否仍由正确 Service 负责？
```

## Service

```text
能否从 Service 主流程看出关键业务步骤？
```

## Repository

```text
是否隐藏了名称之外的重要业务行为？
```

## API

```text
Handler 是否仍然只是协议入口？
```

## Worker

```text
是否绕过 Service 直接修改业务状态？
```

## Client / Connector

```text
是否开始承担业务判断？
```

## 数据

```text
表和字段是否仍然表达 Plan 中定义的业务事实？
```

## 依赖

```text
是否出现新的反向依赖或循环依赖？
```

## 抽象

```text
是否新增了没有真实职责的接口、中间层或公共组件？
```

测试通过不能替代这些检查。

---

# 41. 实现完成后必须对照 Plan

存在确认后的 Plan 时，交付前逐项对照。

至少检查：

```text
Use Case
→ 实现了吗？

业务链路
→ 顺序一致吗？

关键方法名
→ 是否按计划？

文件位置
→ 是否按计划？

模块负责人
→ 是否改变？

数据表和字段
→ 是否一致？

事务
→ 是否扩大或缩小？

API
→ Method / Path / DTO / 状态码是否一致？

异步
→ Producer / Consumer / 状态 / 重试是否一致？

边界
→ Plan 承诺的失败情况是否实现？
```

如果存在设计级差异，必须明确报告。

不要静默偏离 Plan。

---

# 42. Diff 是最终验证对象之一

交付前查看完整任务 Diff。

至少检查：

```text
git diff
git status
```

或者对应工具。

检查：

- 有没有无关文件；
- 有没有调试代码；
- 有没有临时日志；
- 有没有 TODO；
- 有没有注释掉的旧代码；
- 有没有误改配置；
- 有没有自动格式化大量无关文件；
- 有没有敏感信息；
- 有没有生成文件被误改；
- 有没有用户原有修改被覆盖。

测试只验证运行结果。

Diff 检查验证：

> 实际到底改了什么。

---

# 43. 不夹带无关重构

验证阶段如果发现：

```text
旁边还有一个类似问题
```

不要自动一起修。

除非：

- 当前需求无法正确完成；
- 当前修改已经触及同一代码；
- 不处理会制造明确不一致。

否则记录为：

```text
范围外问题
```

单独报告。

验证阶段不是扩大任务范围的机会。

---

# 44. 注释也属于交付检查

根据 `go.md` 检查：

- 新增导出声明是否有注释；
- 注释是否以标识符开头；
- 业务语义是否清楚；
- 空值 / 单位 / 副作用是否必要说明；
- 注释是否与最终实现一致。

不要保留：

```text
TODO later
temporary
hack
```

等无法判断处理条件的注释。

临时方案必须说明：

- 为什么存在；
- 什么条件下可以删除。

---

# 45. 错误处理属于验证内容

检查新增错误路径：

- 是否被吞掉；
- 是否只记录日志后返回成功；
- 是否丢失底层原因；
- 是否重复记录同一个错误；
- 是否将敏感信息返回给客户端；
- 是否错误分类成 retryable；
- 是否把正常业务状态变成 500。

行为测试应覆盖关键错误。

Diff Review 负责发现没有进入测试的明显错误处理问题。

---

# 46. 日志不是正确性的替代

禁止：

```go
if err != nil {
    log.Error(err)
    return nil
}
```

然后认为错误已经处理。

如果失败影响业务结果：

> 调用方、任务框架或状态资源必须能够感知。

日志用于观察。

不是业务错误处理机制。

---

# 47. Build 成功不等于运行成功

```text
go build
```

只能证明：

> 当前代码能够编译。

它不能证明：

- 配置正确；
- Migration 正确；
- HTTP 可以启动；
- Route 正确；
- Worker 注册正确；
- 外部依赖可用；
- Docker 正确；
- 前后端能协作。

根据改动风险增加对应验证。

不要将：

```text
build passed
```

表述成：

```text
feature verified
```

---

# 48. Unit Test 通过不等于完整链路通过

例如：

```text
Service Test
```

通过不能证明：

```text
HTTP DTO
→ Handler
→ Service
→ DB
```

整体可以运行。

跨层契约发生变化时，应增加 Integration Test 或 E2E。

反过来，也不能只依赖 E2E，而完全没有低层失败测试。

不同测试解决不同问题。

---

# 49. 测试范围根据风险选择

低风险修改：

```text
局部纯函数
简单文案
简单 Response 字段
```

可以使用较小验证范围。

高风险修改：

```text
数据库迁移
事务
权限
支付
Worker
并发
重试
Shutdown
外部回调
状态机
```

需要更强验证。

验证成本应与失败风险成比例。

不要机械规定：

> 每次必须跑所有 E2E。

也不要为了节约几分钟跳过明显相关的重要验证。

---

# 50. 优先先跑针对性测试，再跑完整检查

开发过程中：

```text
修改
→ 针对性测试
→ 修正
```

完成后：

```text
相关测试
→ 全量项目约定检查
```

这样可以快速发现问题，同时保证最终整体没有回归。

不要每改一行都跑整个项目。

也不要最后完全不跑完整回归。

---

# 51. 长测试需要说明原因

如果某项验证：

- 很慢；
- 需要 Docker；
- 需要大型 Fixture；
- 需要真实外部环境；

应只在确实需要时执行。

如果因为环境限制无法执行，应明确报告：

```text
未验证：
Docker E2E

原因：
当前环境没有 Docker daemon

替代验证：
unit + integration + build 已通过
```

不要把未执行描述成“应该没问题”。

---

# 52. 真实外部验证与自动测试分开

例如真实抓取网页。

自动测试：

```text
固定 HTML Fixture
→ parser
```

额外真实验证：

```text
访问 3 个公开样本 URL
→ 检查正文提取质量
```

最终报告应区分：

```text
自动测试结果
真实样本验证结果
```

不要混成一句：

> 测试通过。

---

# 53. 验证结果必须真实记录

执行命令后，交付时报告：

```text
命令
结果
必要时退出码
```

例如：

```text
mise run backend-lint
→ passed

mise run backend-test
→ passed

mise run backend-build
→ passed

go test -race ...
→ passed
```

如果失败：

```text
frontend-e2e
→ failed
→ 原因：...
```

不能：

- 隐瞒失败；
- 只说大部分通过；
- 没执行却说通过；
- 根据以前运行结果冒充本次结果。

---

# 54. 验证结果区分三种可信度

最终说明应区分：

## 已验证

实际执行并得到结果。

```text
backend-test 已运行并通过
```

## 根据代码判断

没有实际运行，但有充分代码依据。

```text
该分支复用已有错误映射，本次没有单独运行 HTTP 集成测试。
```

## 未验证

明确没有检查。

```text
没有调用真实 AI Provider。
```

不要将三者混在一起。

---

# 55. 完成标准

一个任务不能因为：

```text
代码已经写完
```

就宣布完成。

默认完成标准：

```text
实现完成
+
相关测试通过
+
项目约定检查通过
+
设计对照完成
+
Diff 检查完成
+
未覆盖内容已明确
```

如果其中某项因为环境原因无法完成，应明确说明。

---

# 56. 交付说明的默认结构

最终交付保持简洁，但必须提供足够证据。

推荐：

```text
完成

- 实现管理员创建能力；
- 创建时校验角色；
- 管理员和审计事件同事务写入。


关键链路

POST /api/admins
→ AdminService.CreateAdmin
→ GetAdmin
→ ListRolesByIDs
→ Transaction(
    CreateAdmin
    → AppendEvent
  )
→ 201


Plan 对照

- 业务流程：一致
- 模块职责：一致
- API：一致
- 数据结构：一致
- 事务范围：一致
- 设计级偏差：无


验证

- backend-lint：passed
- backend-test：passed
- backend-build：passed
- race：passed


未验证

- 未执行真实外部系统调用。


范围外

- 发现旧 Admin 查询存在重复逻辑，本次未修改。
```

如果项目还有 Commit 要求，再按 `contributing.md` 增加 Commit 信息。

---

# 57. 不重复用户已经知道的大量细节

最终交付不是重新复制整个 Plan。

只需要告诉用户：

```text
最终做成了什么
核心链路在哪里
是否偏离 Plan
验证结果是什么
还有什么没验证
```

如果用户需要详细实现，再进一步展开。

---

# 58. 设计级偏差必须主动报告

下面变化属于设计级偏差：

- 核心 Service 改名；
- 模块归属改变；
- 新增 Plan 外的模块；
- 文件移动到不同职责层；
- 新增表；
- 字段语义变化；
- 事务边界变化；
- API Method / Path / DTO 变化；
- 同步改成异步或反过来；
- 新增重要依赖；
- 失败语义改变。

出现这些情况时，最终交付不能只说：

```text
已按 Plan 完成。
```

必须写：

```text
与 Plan 的差异：

原计划：
...

实际：
...

原因：
...
```

---

# 59. 非设计级局部实现差异不必逐项报告

例如：

- 一个私有 helper 改名；
- 局部变量调整；
- 两个小函数合并；
- 测试辅助函数移动；
- 同包内小范围代码整理。

只要：

- 不改变设计语义；
- 不影响外部契约；
- 不改变模块职责；

无需在交付报告逐项说明。

---

# 60. 验证失败时不要急着交付

如果存在明显失败：

```text
unit test failed
build failed
lint failed
migration failed
E2E failed
```

默认应先分析并修复。

只有：

- 无法在当前环境修复；
- 失败属于任务范围外；
- 需要用户业务决定；

时才停止并报告。

报告时给出：

```text
失败是什么
为什么发生
是否由本次修改导致
推荐怎么处理
```

不要只粘贴一大段日志让用户自己判断。

---

# 61. 需要用户决定时给推荐方案

验证过程中如果发现必须由用户决定的问题，例如：

```text
修复失败需要改变已有 API 契约
```

不要问：

```text
怎么办？
```

应该：

```text
当前发现：

已有 API 返回 200，
新的正确行为需要区分资源状态冲突。

方案 A
保持 200，通过 body 表达失败。

方案 B
改为 409 Conflict。

推荐：B

原因：
- 当前属于状态冲突；
- 客户端需要稳定区分；
- 与项目其他 API 一致。

请选择 A / B。
```

如果环境支持交互式选择，优先使用。

---

# 62. 测试代码属于正式代码

测试文件也需要：

- 清晰命名；
- 可读结构；
- 合理抽象；
- 保留业务含义；
- 避免复制大量脆弱实现细节。

不要因为：

```text
只是测试
```

就允许：

- 巨大不可读 helper；
- 全局共享状态；
- 依赖执行顺序；
- 随机失败；
- 隐藏数据前提。

测试是业务契约的一部分。

---

# 63. 交付前最终检查清单

完成任务前至少快速检查：

## 需求

- Plan 中的 Use Case 是否全部完成？
- 是否夹带范围外需求？

## 业务

- 核心流程是否正确？
- 失败与重复行为是否正确？

## 架构

- Service 是否仍是业务主要阅读入口？
- Repository 是否只承担持久化？
- Worker / API 是否绕过 Service？

## 数据

- 事务是否正确？
- Migration 是否安全？
- 数据约束是否正确？

## API

- DTO、状态码、Error Code 是否一致？
- 是否出现无意兼容性变化？

## 异步

- 是否考虑重复执行？
- 旧任务能否覆盖新结果？
- 失败和恢复语义是否正确？

## Go

- format / lint 是否通过？
- 导出声明注释是否符合要求？
- 是否有资源泄漏、错误吞掉或 context 问题？

## 测试

- 计划中的关键验收场景是否覆盖？
- 是否存在明显未测试的高风险分支？

## Diff

- 是否只有本次必要修改？
- 是否存在调试代码或敏感信息？
- 是否保留用户已有修改？

## 交付

- 是否准确报告验证结果？
- 是否明确未验证内容？
- 是否说明设计级偏差？

---

# 64. 最终目标

测试和验证的目的不是让 Agent能够说：

> “所有测试通过。”

而是让用户能够相信：

> **实现满足需求，
> 关键风险已经验证，
> 代码仍然符合确认过的设计，
> 最终交付的每一个结论都有明确依据。**

理想开发结果应该是：

```text
Plan 定义预期
↓
实现代码
↓
行为测试证明功能
↓
设计检查证明结构
↓
Diff 检查证明范围
↓
交付说明提供证据
```

而不是：

```text
代码能编译
↓
宣布完成
```
