# 数据建模与事务规范

本文件规定后端项目中的数据建模、数据库约束、Repository 粒度、事务、并发与迁移设计。

目标是：

> 让数据结构能够直接表达业务事实和生命周期，
> 让数据库承担适合数据库保证的一致性，
> 让事务边界与业务成功条件一致，
> 并让读者能够从 Service 看清楚业务数据是怎样发生变化的。

---

# 1. 数据建模从业务事实开始

设计表之前，先回答：

> **这张表的一行，代表什么业务事实？**

必须能够用一句明确的话描述。

例如：

```text
users
一行代表一个用户。

articles
一行代表一篇已经进入系统的文章。

article_imports
一行代表某个用户对一个 URL 的一次稳定导入状态。

sentence_reviews
一行代表某个用户对某条例句当前的复习状态。
```

如果无法清楚说明“一行代表什么”，不要立即建表。

不要从：

```text
这个功能需要哪些字段？
```

开始设计。

应从：

```text
系统中实际存在什么业务对象或业务事实？
它什么时候产生？
什么时候变化？
什么时候结束？
谁拥有它？
```

开始。

---

# 2. 判断是否应该新建表

出现新的业务概念时，先判断能否复用现有数据结构。

以下情况通常说明它可能应该成为独立表：

- 有独立身份；
- 有独立生命周期；
- 在其他对象创建之前就可能存在；
- 需要独立查询、分页或筛选；
- 需要独立更新；
- 有自己的状态变化；
- 需要独立唯一约束；
- 会被其他对象引用；
- 删除规则与现有对象不同。

例如：

```text
文章导入 != 文章

article_imports
pending → ready / failed

articles
表示已经存在的可阅读文章
```

导入失败时可能根本没有 Article，因此不能为了少建一张表，把导入状态强行塞进 `articles`。

---

反过来，如果数据：

- 没有独立生命周期；
- 永远跟随父对象创建和删除；
- 不需要独立查询；
- 不需要独立更新；
- 没有独立业务身份；

则通常不需要单独建表。

不要因为：

- 字段比较多；
- 代码比较长；
- “以后可能会用”；
- 想让表看起来更规范；

就机械拆表。

---

# 3. 不按 API、Service 或页面机械建表

API、Service、页面和数据表不是一一对应关系。

例如：

```text
POST /article-imports
```

不代表一定需要一张与 API 完全对应的表。

反过来：

```text
一个 Article Service
```

也可以操作多张与 Article 业务相关的表。

数据表应表达：

> **需要长期保存的业务事实**

而不是表达：

> 当前代码有几个模块。

---

# 4. 表设计必须明确这些内容

新增或修改表时，至少明确：

```text
表名

一行代表什么

业务负责人

主键

业务唯一性

重要字段及含义

NULL 语义

默认值

外键关系

删除行为

状态与生命周期

主要查询方式

需要的索引
```

Plan 中涉及新表时，应能给出类似：

```text
表：article_imports

一行代表：
- 一个用户对一个 URL 的稳定导入状态。

负责人：
- Article Service

主键：
- id

业务唯一性：
- user_id + url

状态：
- pending
- ready
- failed

关联：
- user_id → users
- article_id → articles，可空

删除：
- Article 删除后保留导入记录，article_id 置空。

主要查询：
- 按 user_id + url 查询
- 按 id + user_id 查询
```

---

# 5. 主键与业务唯一键分开考虑

主键用于稳定标识一行数据。

业务唯一键用于表达：

> 业务上什么东西不能重复存在。

不要认为有 `id` 主键以后，就不需要其他唯一约束。

例如：

```text
website_subscriptions

id
    数据库身份

UNIQUE(user_id, feed_url)
    业务规则：
    同一个用户不能重复订阅同一个源
```

重要的业务唯一性，应尽可能由数据库约束兜底，而不是只依赖：

```go
先 SELECT
没有
再 INSERT
```

因为这种方式无法单独解决并发创建。

通常采用：

```text
业务预检查
+
数据库唯一约束兜底
```

---

# 6. 字段必须表达明确语义

每个新增字段都应能够回答：

> 谁会写它？
> 谁会读它？
> 它表达什么业务事实？

如果回答不出来，不应因为“以后可能需要”就添加。

避免使用：

```text
data
info
extra
metadata
value
flag
```

这类无法表达实际业务含义的字段名，除非它确实代表一个明确的通用结构。

字段命名和 Go 类型命名遵循 `go.md`。

---

# 7. NULL、空值和默认值必须有明确区别

不得把：

```text
NULL
""
0
false
[]
```

随意当成同一种“没有值”。

例如：

```text
finished_at = NULL
```

可以表示：

> 从未完成。

而不是：

> 完成时间未知。

又例如：

```text
source_url = NULL
```

可以表示：

> 文章不是通过 URL 导入。

这种语义必须稳定。

如果空字符串和 NULL 没有业务区别，优先选择一种统一表达，不让代码长期处理两套含义。

---

# 8. 状态字段必须对应真实生命周期

不要为了看起来完整，给每张表都增加 `status`。

只有对象确实存在生命周期时才使用状态。

例如：

```text
article_imports

pending
→ ready

pending
→ failed
```

设计状态时必须说明：

- 初始状态；
- 允许的状态；
- 谁可以改变状态；
- 哪些状态允许继续操作；
- 是否允许重新进入之前的状态；
- 终态是什么；
- 删除是否属于状态。

如果状态组合变复杂，应先检查是不是：

> 一张表实际上混入了两个不同生命周期的对象。

---

# 9. 不使用多个布尔字段隐式表达状态机

避免：

```text
is_running
is_finished
is_failed
is_canceled
```

这些字段很容易产生不合法组合：

```text
is_finished=true
is_failed=true
```

如果它们表达互斥状态，应优先使用一个明确状态：

```text
status = pending | ready | failed
```

真正独立的布尔属性仍可以使用布尔字段。

---

# 10. revision / version 只在真实并发问题中使用

不要为所有表机械增加 `revision`。

当存在下面这种情况时，可以引入 revision/version：

```text
请求 1 开始处理
↓
用户重新发起请求
↓
请求 2 成为最新任务
↓
请求 1 晚到
↓
不能让旧结果覆盖请求 2
```

此时可以使用：

```text
id + revision + expected_status
```

进行条件更新：

```text
UPDATE ...
WHERE id = ?
  AND revision = ?
  AND status = 'pending'
```

目标是保证：

> **旧工作结果不能覆盖新的业务状态。**

如果不存在这种竞争，不要仅为了“支持并发”增加 revision。

---

# 11. JSON 与关系表的选择

不要因为 JSON 写起来简单，就默认把关系存 JSON。

也不要为了“数据库规范”，把所有结构都拆成表。

## 更适合字段或关系表

当数据需要：

- 独立查询；
- 独立筛选；
- 独立更新；
- 外键约束；
- 唯一约束；
- 多对象关联；
- JOIN；
- 数据库保证引用完整性；

优先使用普通字段或关系表。

例如：

```text
user ↔ role
```

如果角色需要查询、删除、约束和关联，使用关系表通常比：

```json
{
  "role_ids": [1, 2, 3]
}
```

更合理。

---

## 更适合 JSON

当数据：

- 总是随父对象整体读取；
- 总是整体替换；
- 没有独立身份；
- 不需要数据库查询内部成员；
- 表达结构树、快照或有序复杂结构；

可以使用 JSON。

例如：

```text
文章生成时使用的词语文字快照
书籍目录树
第三方返回结果的稳定快照
```

关键问题不是：

> JSON 好不好？

而是：

> **这个数据是否拥有独立业务身份和查询需求？**

---

# 12. 快照数据与引用数据要区分

设计字段时判断：

> 后续希望看到“当前值”，还是“当时的值”？

例如：

```text
生成文章时选中了单词 "abandon"
```

如果未来删除或修改原始标记后，历史生成文章仍应知道当时使用了什么词，那么应保存：

```text
words = ["abandon", ...]
```

这样的快照。

而不是只保存：

```text
mark_id
```

反过来，如果业务要求始终读取对象当前状态，则应该保存引用。

不要把“引用”和“历史快照”混在一起。

---

# 13. 外键表达生命周期关系

存在真实实体关系时，优先考虑数据库外键。

设计外键时必须明确删除行为：

```text
CASCADE
SET NULL
RESTRICT / NO ACTION
```

选择依据是业务语义。

例如：

```text
Article 删除
→ ArticleContent 没有独立存在意义
→ CASCADE
```

而：

```text
Article 删除
→ Import 仍然需要保留“曾成功导入”的历史事实
→ article_id SET NULL
```

不要因为：

> CASCADE 比较方便

就使用 CASCADE。

也不要为了避免数据库约束，把所有关系都只留给应用代码维护。

---

# 14. 不默认使用软删除

不要机械给所有表添加：

```text
deleted_at
is_deleted
```

只有业务确实需要：

- 恢复；
- 审计；
- 法规保留；
- 历史查询；
- 被其他长期事实引用；

时才采用软删除。

否则使用真实删除通常更简单。

如果需要审计历史，应优先判断：

> 审计记录是否应该成为独立业务数据，

而不是让所有业务表永远保留软删除字段。

---

# 15. 数据库约束负责保护稳定不变量

适合数据库直接保证的规则，优先落实为数据库约束，例如：

- NOT NULL；
- UNIQUE；
- FOREIGN KEY；
- CHECK；
- 数据类型；
- 必要的条件更新。

Service 仍然负责提供用户可理解的业务错误和业务流程。

不要只依靠 Service：

```text
先查有没有
→ 判断可以写
→ INSERT
```

数据库应该为并发情况下的最终一致性提供兜底。

同时，不要试图把所有复杂业务规则都塞进数据库约束。

判断原则：

> **数据库保证数据永远不能进入明显非法状态；
> Service 决定当前业务操作是否允许发生。**

---

# 16. 索引从真实查询开始设计

不要：

> 看到字段就建索引。

先列主要查询：

```text
按 user_id + url 查询导入
按 user_id + id 获取详情
按 enabled + next_check_at 查询到期订阅
按 user_id + id 倒序分页
```

再为这些查询设计索引。

组合索引的字段顺序应与真实查询条件和排序方式匹配。

不要为了未来可能查询而提前建立大量索引。

同时检查：

- UNIQUE 是否已经自动提供可用索引；
- 外键查询是否需要额外索引；
- 排序与分页是否能复用索引；
- 新索引的写入成本是否合理。

性能问题没有证据时，不提前做复杂优化。

---

# 17. 时间、数量和金额必须有稳定单位

时间字段应明确：

```text
时间点
持续时长
日期
```

不要混用。

例如：

```text
created_at
next_check_at
```

表示时间点。

而：

```text
timeout_ms
interval_seconds
```

表示持续时长。

持续时长需要从字段名、类型或注释看出单位。

项目没有其他约定时，持久化时间点默认使用统一时区表达，例如 UTC；展示层再做时区转换。

金额、精确比例等不能接受浮点误差的数据，不使用普通浮点数直接保存业务值，应根据业务选择整数最小单位或精确 decimal 表达。

---

# 18. Repository 的粒度是“明确的数据操作”

Repository 负责：

- SQL / ORM；
- 查询；
- 插入；
- 更新；
- 删除；
- 条件更新；
- 数据库约束错误识别；
- 事务机制。

Repository 方法应该能从名字理解主要副作用。

例如：

```text
CreateArticle
CreateArticleContent
MarkArticleImportReady
FindArticleByURL
ListDueSubscriptions
```

避免：

```text
Process
Handle
CompleteEverything
SaveData
UpdateAll
```

---

“一项 Repository 操作”不等于“一条 SQL”。

下面这种操作完全可以由一个 Repository 方法完成：

```text
删除某个用户已有的关联
+
批量插入新的角色关联
```

前提是它整体表达一个清晰的数据操作。

但是：

```text
创建 Article
+
创建 ArticleContent
+
修改 Import 状态
+
决定是否复用旧 Article
```

已经包含多个业务步骤。

这种跨业务数据操作应由 Service 显式编排，而不是藏在名称模糊的 Repository 方法中。

---

# 19. Service 决定业务事务边界

事务边界来源于业务成功条件。

先问：

> **哪些变化必须共同成功，否则这次业务操作就应该视为失败？**

例如：

```text
创建管理员
+
写入必须存在的创建审计记录
```

如果业务要求两者共同成功，则应该处于同一事务。

又例如：

```text
创建 Article
+
保存 default ArticleContent
+
把 Import 标记为 ready
```

如果只有三者全部成功才能表示“导入完成”，应共同提交。

---

# 20. 多表业务事务应在 Service 中可见

Service 应显式展示关键业务写入顺序。

例如：

```text
ArticleService.CreateArticleFromImport

1. 校验 Import 当前状态和 revision

2. Transaction

   tx.CreateArticle(...)

   tx.CreateArticleContent(...)

   tx.MarkArticleImportReady(...)

3. Commit
```

这样读者能够直接理解：

> 导入成功到底意味着数据库发生了什么。

不要变成：

```text
ArticleService.CreateArticleFromImport
→ repo.CompleteImport(...)
```

然后需要继续深入 Repository 才能知道实际上创建了哪些业务对象。

事务的业务步骤属于 Service。

事务的：

- Begin；
- Commit；
- Rollback；
- SQL connection；
- ORM transaction object；

等机制属于 Repository。

Service 不直接操作 SQL 或 ORM Transaction。

---

# 21. 事务回调必须只使用事务绑定的 Repository

例如：

```go
store.Transaction(ctx, func(tx *Store) error {
    // 这里只使用 tx
})
```

不得在事务回调里：

```text
tx.CreateA()

外层 store.CreateB()
```

否则两次操作可能并不属于同一个事务。

事务 API 应尽量让这种错误难以发生。

---

# 22. 数据库事务中不执行不可控外部操作

数据库事务内不得等待：

- HTTP 请求；
- RPC；
- AI / LLM；
- 文件上传；
- 大型文件解析；
- 用户交互；
- 长时间 CPU 工作；
- 不受本数据库控制的远程系统。

错误方式：

```text
BEGIN

写 pending

调用外部 HTTP，等待 20 秒

解析网页

写结果

COMMIT
```

正确方向通常是：

```text
事务外
→ 获取 / 计算 / 验证外部结果

事务内
→ 快速校验当前业务状态
→ 写入最终结果
→ Commit
```

或者：

```text
事务 1
→ 保存业务状态 + 持久任务

后台外部调用

事务 2
→ 条件写回结果
```

目标是保持事务：

> **短、明确、可重试。**

---

# 23. 异步受理必须考虑业务状态与任务的一致性

如果业务状态：

```text
pending
```

意味着：

> 后续一定存在一个持久任务可以处理它，

则不能出现：

```text
事务 1
→ 保存 pending
→ Commit

随后 enqueue 失败
```

导致永久留下没有任务的 pending 数据。

如果队列和业务数据可以共享事务，优先：

```text
Transaction
→ 保存业务 pending
→ EnqueueTx
→ Commit
```

如果不能共享事务，则应根据实际可靠性需求评估：

- outbox；
- 恢复扫描；
- 补偿；
- 幂等重新提交。

不要因为看到“异步”就机械建设 Outbox。

先明确真正需要保证什么。

---

# 24. 幂等与去重必须落到稳定身份上

需要重复调用安全时，先定义：

> **什么代表同一次业务操作？**

可能是：

```text
user_id + url
request_key
external_id
business_id + revision
```

不要用随机任务 ID 代替业务幂等身份。

任务执行可以重复，但业务结果不能错误重复产生。

例如：

```text
Worker 调用 AI 两次
```

可能无法完全避免。

但可以保证：

```text
旧任务不能覆盖新 revision
同一个请求不会重复写入同一业务结果
```

不要在没有证据时宣称“exactly once”。

通常应该按照：

> **可能至少执行一次**

来设计异步结果写入。

---

# 25. 并发写入不能只依赖“先查再写”

这种代码：

```text
if !Exists(key) {
    Create(key)
}
```

无法单独解决并发。

如果业务要求唯一，数据库应该有对应 UNIQUE 约束。

应用层的查询用于：

- 提前返回更明确业务结果；
- 减少无意义写入。

数据库约束负责最终兜底。

对于状态竞争，可以使用：

```text
UPDATE ...
WHERE id = ?
AND status = ?
AND revision = ?
```

然后检查受影响行数。

不要依赖：

```text
我刚刚 SELECT 时它还是 pending
```

来推断稍后更新仍然安全。

---

# 26. 锁只解决真实竞争问题

不要为了“线程安全”默认对所有操作：

```text
SELECT FOR UPDATE
```

或建立全局互斥锁。

先明确：

- 哪两个操作可能同时发生；
- 它们同时发生会产生什么错误；
- 唯一约束、条件更新或 revision 是否已经足够；
- 是否真的需要悲观锁。

优先选择最小的正确性机制。

具体实现结合当前数据库能力决定。

---

# 27. 跨 Service 的数据修改遵循业务所有权

一个业务模块需要查询其他模块数据时，可以通过项目允许的读取边界获取必要信息。

但是修改其他业务模块拥有的状态时，应通过该业务负责人提供的操作。

不要为了事务方便，让一个 Service 随意更新所有业务表。

例如：

```text
Subscription Service
```

发现新的文章链接后，可以调用：

```text
Article Service
```

受理文章导入。

而不是直接修改：

```text
article_imports
articles
```

这样数据写入责任与业务责任保持一致。

---

# 28. 事务不能跨越不属于同一个数据库的一切东西

一个数据库 Transaction 只能保证它实际控制的数据。

不能因为代码写在：

```go
Transaction(func() {...})
```

里，就认为下面这些也获得原子性：

```text
HTTP API
Redis
Kafka
第三方服务
文件系统
AI API
另外一个数据库
```

如果业务要求跨系统一致性，需要显式设计：

- 最终一致性；
- Outbox；
- Saga / 补偿；
- 幂等消费；
- 状态恢复。

只在真实业务需要时采用，不默认建设分布式事务框架。

---

# 29. 数据迁移只向前演进

已经应用或可能已经应用到真实环境的迁移：

> **不得直接修改。**

后续 schema 变化新增 migration。

不要为了让当前代码干净而重写历史迁移。

新数据库应：

```text
从第一版 migration
一路执行到最新版本
```

仍然得到正确结果。

已有数据库应：

```text
旧版本
→ 新 migration
→ 最新版本
```

得到等价结构。

---

# 30. 迁移设计必须考虑真实旧数据

修改已有表时，不只考虑：

> 新建数据库能不能成功。

还必须考虑：

- 已有数据如何转换；
- NULL / 默认值如何补；
- 外键是否成立；
- 唯一约束是否与历史数据冲突；
- 主键是否保持；
- 关联数据是否保持；
- 索引是否恢复；
- 自增序列是否保持；
- 在途任务是否受影响。

例如新增：

```text
NOT NULL
```

字段时，必须说明历史行使用什么值。

不能简单假定：

> 旧数据肯定符合新规则。

---

# 31. 破坏性迁移需要明确数据保留方案

以下变化需要特别检查：

- DROP TABLE；
- DROP COLUMN；
- 改变主键；
- 改变唯一范围；
- 改变外键；
- 数据类型收窄；
- 重建包含现有数据的表；
- 大规模 backfill；
- 改变状态含义。

Plan 中必须说明：

```text
旧数据如何处理
是否需要备份
失败怎样恢复
是否需要停服
是否允许回滚
```

不得通过：

```text
删数据库重新创建
删除 volume
```

来解决真实数据迁移问题，除非明确处于可丢弃的开发测试环境。

---

# 32. 大规模 Backfill 与 Schema Change 分开考虑

如果迁移涉及大量数据，不要默认在一个长事务中：

```text
改 schema
+
扫描全部历史数据
+
复杂业务计算
```

应评估：

```text
先兼容新旧字段
→ 分批 backfill
→ 验证完成
→ 再收紧约束
```

当前数据量很小、数据库明确允许一次完成时，可以直接迁移。

不要为了假想规模提前建立复杂迁移框架。

---

# 33. 数据迁移不能承载普通业务逻辑

Migration 负责：

> 数据结构和历史数据升级。

不要在 Migration 中调用：

- 外部 API；
- AI；
- 网络服务；
- 当前业务 Service；
- 不稳定的运行时代码。

历史 migration 必须能够长期重放。

如果需要业务级重新处理，应设计独立的一次性任务或工具，而不是把它藏在 schema migration 中。

---

# 34. 敏感数据遵循最小保存原则

设计字段时检查是否包含：

- 密钥；
- Token；
- Cookie；
- 凭证；
- 用户隐私；
- 第三方原始响应；
- 可能包含敏感信息的大段日志。

能不保存就不保存。

---

# 35. Plan 涉及数据时必须展示这些内容

当需求涉及数据结构或事务时，Plan 中必须至少让用户看到：

```text
数据对象
↓
表及一行的业务含义
↓
字段和重要约束
↓
表之间的关系
↓
主要读写
↓
事务边界
↓
重复 / 并发保护
↓
迁移影响
```

推荐格式：

```text
数据

表：article_imports

一行代表：
- 一个用户对一个 URL 的稳定导入状态。

字段
- id
- user_id
- url
- status
- article_id
- revision

唯一
- user_id + url

关联
- user_id → users
- article_id → articles，可空

状态
pending
→ ready
→ failed


业务写入

ArticleService.CreateArticleFromImport

Transaction
→ 校验 Import(user_id, id, revision, pending)
→ CreateArticle
→ CreateArticleContent
→ MarkArticleImportReady
→ Commit


并发保护

- user_id + url UNIQUE
- 完成条件包含 revision + pending
- 旧 revision 不允许覆盖新尝试
```

不要只在 Plan 中写：

```text
新增 article_imports 表并补充 Repository。
```

---

# 36. 需要用户确认的数据决策

如果存在多个都合理、但会明显影响：

- 产品行为；
- 数据生命周期；
- 删除语义；
- 历史兼容；
- 数据归属；
- 表之间关系；

的设计，应按照 `plan.md` 使用：

> **推荐方案 + 选择题**

向用户确认。

例如：

```text
取消订阅后，历史导入记录如何处理？

A. 删除历史记录
B. 保留历史记录，将 subscription_id 置空

推荐：B

原因：
- 可以保留文章来源历史；
- 已经受理的导入仍然可以完成；
- 不需要因为取消订阅删除已经存在的文章。

请选择 A / B。
```

不要问：

```text
取消订阅的数据你想怎么设计？
```

普通数据库技术选择由 Agent 根据本文件和项目现状自行决定。

# 37. 数据设计完成前自检

设计完成后，至少检查：

## 模型

- 每张表能否一句话说明“一行代表什么”？
- 是否把两个不同生命周期的对象塞进同一张表？
- 是否存在为了“规范”而多建的表？
- 是否把应该独立查询的数据随意塞进 JSON？

## 字段

- 每个新增字段是否有当前用途？
- NULL、零值和默认值语义是否明确？
- 时间、数量和单位是否明确？
- 状态是否表达真实生命周期？

## 关系

- 外键是否表达真实关系？
- 删除行为是否符合业务？
- 多对多是否应该使用关系表？
- 历史快照和当前引用是否区分？

## 一致性

- 哪些规则应该由 UNIQUE / FK / CHECK 保证？
- 哪些规则必须由 Service 判断？
- 并发写入是否只依赖“先查再写”？

## 事务

- 哪些写入必须共同成功？
- Service 中是否能直接看到这些关键写入？
- Repository 是否隐藏了额外业务动作？
- 事务是否包含网络、AI 或其他长时间操作？

## 异步

- 业务状态和持久任务是否可能出现不一致？
- 重复消费是否安全？
- 旧结果是否可能覆盖新状态？

## 迁移

- 新库能否从零初始化？
- 旧库如何升级？
- 历史数据是否保留？
- 已应用 Migration 是否保持不变？
- 破坏性变化是否有备份和恢复方案？

如果这些问题没有明确答案，数据设计还没有完成。

---

# 38. 最终目标

数据设计应该做到：

```text
业务事实
↓
清晰的数据对象
↓
明确的表和字段
↓
数据库约束保护稳定不变量
↓
Service 表达业务状态与事务
↓
Repository 提供清晰的数据操作
↓
并发与重复执行不会破坏结果
↓
Migration 可以安全演进已有数据
```

最终应让读者能够回答：

> 为什么需要这些表？
> 每张表的一行代表什么？
> 为什么这些字段放在这里？
> 什么东西不能重复？
> 数据之间是什么关系？
> 删除以后应该发生什么？
> 哪些写入必须共同成功？
> 并发执行会不会产生错误数据？
> 旧数据库怎样安全升级？

如果这些问题仍然只能通过阅读大量 Repository SQL 才能理解，
数据模型和事务设计还不够清晰。
