# Agent 上下文与规则加载规范

本文件规定 Agent 在开发、设计、评审和排查问题时，应该如何获取项目上下文、加载规则、读取代码和使用项目地图。

目标是：

> 让 Agent 在每个 Session 中快速获得完成当前任务所需的准确上下文，
> 避免重复扫描整个仓库、一次性加载全部规则、反复读取已经确认的信息，
> 同时避免因为上下文过少而违反项目约定或误解现有实现。

原则是：

> **按任务加载，而不是全量加载。**
>
> **地图负责定位，规则负责约束，源码负责确认事实。**

---

# 1. 不默认加载整个项目

开始任务时，不要默认执行：

```text
cat AGENTS.md
cat .agents/rules/*
cat README.md
cat docs/*
扫描整个 repository
```

也不要因为“可能相关”就一次读取大量文件。

先判断当前任务属于什么类型，再读取最小必要上下文。

目标不是：

> 尽可能了解整个项目。

而是：

> **准确了解完成当前任务所需的部分。**

---

# 2. 上下文分成不同类型

Agent 应区分下面几类信息，不把它们混成同一种上下文。

## 2.1 当前任务

包括：

- 用户当前要求；
- 已确认的需求；
- 当前 Plan；
- 本轮明确范围；
- 用户本轮补充或修改的决定。

这是当前任务最直接的上下文。

---

## 2.2 开发规则

例如：

```text
plan.md
architecture.md
usecase.md
data.md
go.md
runtime.md
testing.md
contributing.md
```

规则回答：

> **这类问题应该按照什么方式设计和实现。**

规则不是项目当前实现的描述。

---

## 2.3 项目地图 / Codebase Map

项目地图回答：

> **当前能力大概在哪里。**

例如：

```text
Article Service
→ 文章创建、导入、正文和阅读进度

Worker
→ 后台任务流程

Repository
→ 持久化

sourceclient
→ 外部网页和 RSS
```

项目地图主要用于定位相关代码。

它不能代替真实源码。

---

## 2.4 当前源码与测试

源码、测试、Migration、配置等用于确认：

> **项目现在实际上是怎么工作的。**

修改代码前，对受影响部分必须以当前源码为准。

---

## 2.5 项目契约和历史决定

例如：

- 当前 API 行为；
- 表结构；
- 已确认的模块职责；
- 已采用的业务取舍；
- 兼容要求；
- 为什么某个设计没有采用。

这些用于避免 Agent 每次重新设计已经确认的问题。

---

## 2.6 历史讨论

历史聊天、旧 Plan、旧方案只能作为背景。

不能因为历史讨论中曾经出现过某个方案，就认为它仍然有效。

如果历史方案已经被：

- 后续讨论否定；
- 当前规则覆盖；
- 当前源码替代；

则以当前有效状态为准。

---

# 3. AGENTS.md 只作为入口

项目根目录的 `AGENTS.md` 应尽量保持简短。

它主要负责：

- 项目是什么；
- 当前最重要的硬约束；
- 规则文件在哪里；
- 不同任务需要读取哪些规则；
- 项目地图在哪里；
- 重要授权边界。

不要把完整的：

- API 契约；
- 数据表说明；
- 运行参数；
- 历史迁移；
- 模块实现细节；

全部复制进 `AGENTS.md`。

`AGENTS.md` 的作用类似：

> **导航页，而不是整本手册。**

---

# 4. 规则按任务类型加载

收到任务后，先判断影响范围。

然后按需要读取规则。

推荐路由：

```text
Plan 模式
→ plan.md
→ 再按 Plan 实际涉及内容补相关规则

模块拆分 / 调用关系
→ architecture.md
→ usecase.md

Service / Repository / 业务流程
→ usecase.md
→ architecture.md

数据表 / 字段 / 事务 / Migration
→ data.md

HTTP / API / DTO
→ api.md

Go 实现
→ go.md

Worker / Job / Cron / 外部调用
→ runtime.md

外部 Client / Connector
→ runtime.md

测试 / 验收
→ testing.md

Commit / Git
→ contributing.md
```

不要因为任务涉及 Go，就自动加载所有后端规则。

例如：

```text
修改一个纯字符串处理函数
```

通常只需要：

```text
go.md
相关源码
相关测试
```

不需要同时加载：

```text
data.md
runtime.md
api.md
migration 文档
```

---

# 5. 跨领域任务必须加载双方规则

按需加载不等于只看一个文件。

如果任务跨多个领域，应加载所有真正受影响的规则。

例如：

```text
新增异步文章导入
```

可能需要：

```text
plan.md
architecture.md
usecase.md
data.md
runtime.md
api.md
testing.md
```

因为它同时影响：

- Service；
- Repository；
- Task；
- Worker；
- 数据状态；
- HTTP；
- 测试。

不要为了减少上下文而漏掉真正相关的规则。

原则是：

> **减少无关上下文，不减少必要约束。**

---

# 6. 优先使用项目地图定位

如果项目存在：

- AOCI-CODE；
- Codebase Map；
- Repository Map；
- Architecture Map；
- 其他项目索引；

开始任务时优先使用地图确定：

```text
相关业务模块
相关入口
可能影响的文件
调用关系
相关数据对象
```

例如：

```text
需求：修改文章导入完成逻辑

项目地图
→ Article Service
→ article/import.go
→ article_import Repository
→ Article Worker
```

然后只读取这些相关源码。

不要因为开启了新 Session，就从：

```text
rg Service
rg Repository
tree backend
```

重新推断整个项目。

---

# 7. 项目地图不是最终事实

地图用于：

> 导航。

源码用于：

> 确认。

地图中的描述可能：

- 过期；
- 简化；
- 尚未同步；
- 无法表达所有边界。

因此，在修改一个能力之前，必须读取真正相关的源码和测试。

例如：

```text
地图：
ArticleService 负责导入

↓ 定位

实际修改前读取：
service/article/import.go
worker/article_import.go
repository/article_import.go
相关测试
```

不要只根据地图直接修改代码。

---

# 8. 读取源码按调用链展开

不要无目的连续打开文件。

优先沿真实调用链读取。

例如：

```text
HTTP Handler
↓
Service
↓
Repository / Client
↓
Worker
↓
结果写回
```

或者从业务负责人反向定位：

```text
Service
↓
谁调用它？
↓
它调用谁？
```

每读取一个文件，都应该能回答：

> 我为什么需要看这个文件？

如果无法回答，通常说明读取范围正在失控。

---

# 9. 不因为文件名看起来相关就全部读取

例如任务涉及：

```text
article import
```

不代表要读取所有：

```text
article*.go
article*.md
article tests
article frontend
```

先通过：

- 项目地图；
- symbol search；
- references；
- call hierarchy；
- 精确文本搜索；

定位真正入口。

然后扩大上下文。

推荐：

```text
先窄
→ 不够
→ 再扩大
```

而不是：

```text
先全部读
→ 再从里面找有用信息
```

---

# 10. 优先使用结构化代码导航

如果当前环境提供：

- Go LSP；
- definition；
- references；
- call hierarchy；
- symbol search；
- repository code search；

优先使用这些能力定位代码。

例如想知道：

```text
Service.CreateArticleFromImport
```

被谁调用，不要第一选择就是：

```text
rg CreateArticleFromImport .
```

如果结构化引用查询可用，优先使用它。

文本搜索仍然适合：

- 查常量；
- 查错误码；
- 查配置；
- 查字符串；
- 查数据库字段；
- 查尚未建立符号关系的内容。

原则不是禁止 `rg`。

而是：

> **有更精确工具时，不用最原始方式反复重建调用关系。**

---

# 11. 已经读取且没有变化的内容不要反复加载

同一个 Session 中，如果规则或文件没有变化，不要因为进入下一个步骤再次完整读取。

例如已经读取：

```text
data.md
service/article/import.go
```

实现过程中没有修改相关规则，就不需要每执行一个命令都重新 `cat`。

可以重新读取的情况：

- 文件刚刚被修改；
- Context Compaction 后关键内容已经不再可靠保留；
- 发现之前理解可能错误；
- 任务范围发生变化；
- 需要核对最终实现。

---

# 12. Context Compaction 后只恢复关键上下文

发生 Context Compaction 后，不要重新：

```text
从头读取整个项目
```

优先恢复：

```text
当前任务目标
↓
已确认 Plan
↓
当前实现进度
↓
直接相关规则
↓
直接相关项目地图
↓
正在修改的源码
```

然后继续。

不要因为压缩发生，就重新读取：

```text
所有规则
所有 README
所有历史讨论
```

---

# 13. 保持一个当前任务摘要

对于较长任务，Agent 应维护一个非常短的当前状态模型。

至少知道：

```text
当前目标
当前范围
已确认的重要决定
已经完成什么
正在处理什么
还剩什么
重要文件
尚未解决的问题
```

例如：

```text
Task

目标
- 完成文章导入 Worker

已确认
- Article Service 是业务 owner
- Worker 不直接写表
- FetchArticle 在事务外
- revision 防止旧任务覆盖

已完成
- Task 类型
- Worker 基础流程

剩余
- 终态失败
- recovery test
```

这个摘要用于保持方向。

不要把整个聊天重新复制进任务摘要。

---

# 14. 当前任务决定优先于旧讨论

如果当前用户明确说：

```text
不要新增独立 Book Service
```

那么即使过去聊天曾经设计过 Book Service，也不能继续采用旧方案。

Agent 应区分：

```text
曾经讨论过
已经确认
后来被否定
当前仍有效
```

不要把聊天历史当作不可变 Memory。

---

# 15. 规则与项目事实发生冲突时不能静默处理

例如：

```text
architecture.md
要求 Worker 不直接写业务表

但当前源码中某 Worker 正在直接调用 Repository
```

不能：

```text
看到代码这样写
→ 认为规则失效
```

也不能：

```text
看到规则
→ 顺手重构整个旧项目
```

应该判断：

```text
这是当前任务相关的违规？
还是历史代码？
是否在授权范围？
```

如果影响本次设计：

> 明确指出冲突，并按照规则设计新代码。

如果需要修改旧代码才能正确实现当前需求：

> 在 Plan 中说明。

如果只是无关历史问题：

> 不扩大当前范围。

---

# 16. 不把现有代码自动当作规范

现有代码只能证明：

> 当前存在这种写法。

不能自动证明：

> 这种写法是推荐模式。

尤其遇到：

- 历史代码；
- 临时实现；
- 尚未重构模块；
- 明确存在 TODO 的代码；

不要为了“保持一致”复制问题。

如果项目中存在明确的 Golden Example / Reference Implementation，可以优先参考。

例如：

```text
service/article/import.go
```

被项目规则明确指定为：

> 跨表业务编排的参考实现。

那么可以作为设计样本。

没有明确指定时，不自动把某个文件当模板。

---

# 17. 规则比示例优先

如果：

```text
规则说：
Service 显式编排跨表业务操作
```

而某个旧 Repository 存在：

```text
CompleteEverything()
```

不要因为找到现有例子就继续复制。

示例帮助理解规则。

示例不能覆盖明确规则。

---

# 18. 不为了减少上下文而复制规则内容

例如 `plan.md` 需要数据设计原则时，不要把整个 `data.md` 再复制进去。

正确做法：

```text
Plan 涉及表结构时读取 data.md。
```

而不是：

```text
plan.md
包含一份 data.md

architecture.md
又包含一份 data.md
```

规则应该：

> **单一职责 + 相互引用。**

避免同一规则在多个文件重复维护。

---

# 19. 一条规则只维护一个主要来源

例如：

```text
Go 命名
→ go.md

事务与数据模型
→ data.md

异步运行
→ runtime.md

Commit
→ contributing.md
```

其他文件只引用：

```text
具体命名遵循 go.md。
```

不要复制完整正文。

这样修改规则时只需要改一个位置。

---

# 20. 区分通用规则与项目事实

跨项目规则应该描述：

> 默认怎么设计。

例如：

```text
跨表业务写入应由 Service 显式编排。
```

项目规则描述：

> 当前项目具体怎么实现。

例如：

```text
ArticleService.CreateArticleFromImport

→ CreateArticle
→ CreateArticleContent
→ MarkArticleImportReady
```

不要把当前项目：

```text
article_imports
website_subscriptions
```

这样的具体表名写进通用 Go 开发规则。

---

# 21. 项目事实尽量由地图和契约维护

会频繁变化的内容，例如：

- 当前有哪些模块；
- 当前有哪些表；
- 当前 API；
- 当前 Worker；
- 当前业务调用关系；

不应该大量写入通用开发规则。

它们更适合放在：

```text
项目地图
contracts
project-specific docs
```

否则每次业务功能变化，都要修改大量规则文件。

---

# 22. 历史信息不进入默认上下文

以下内容默认不需要每次开发加载：

- 历史 Migration 过程；
- 为什么三个月前删除某个模块；
- 已经完成的重构流水账；
- 所有过去 Plan；
- 所有 Release Notes；
- 全部架构演进记录。

如果当前任务涉及：

```text
旧数据库升级
兼容历史 Task
恢复旧数据
```

再按需读取。

正常功能开发只需要知道：

> **当前有效状态。**

---

# 23. README 不是默认完整上下文

README 主要面向：

- 使用；
- 启动；
- 项目介绍；
- 开发入口。

不要每次开发都把完整 README 当作业务设计依据。

如果任务涉及：

```text
启动命令
部署
配置
使用方式
```

再读取相关部分。

业务职责优先使用：

```text
项目地图
规则
源码
契约
```

---

# 24. 测试也是上下文的一部分

理解一个已有能力时，不只读取实现。

相关测试可以帮助确定：

- 实际契约；
- 边界情况；
- 历史 Bug；
- 并发语义；
- 失败行为。

但不要默认读取整个测试目录。

优先定位：

```text
与正在修改的方法或 Use Case 直接相关的测试。
```

---

# 25. Migration 是数据事实的重要来源

涉及：

- 数据表；
- 字段；
- 外键；
- 索引；
- 历史兼容；

时，应读取：

```text
当前 schema 来源
相关 migration
数据规则
```

不要只根据 ORM Model 推断数据库真实结构。

同样，也不要为了一个不涉及数据的普通逻辑修改，加载全部 Migration 历史。

---

# 26. 外部资料只在需要时加载

涉及：

- 新依赖；
- 新技术方案；
- 标准协议；
- 第三方 API；
- 复杂架构选择；

时，可以查：

- 官方文档；
- 成熟开源实现；
- 项目源码。

不要每一个普通修改都重新进行广泛 Research。

---

# 27. 外部资料不能覆盖项目决定

即使开源项目采用：

```text
某种目录结构
某种 ORM
某种 Event Bus
```

也不能因为：

> 大项目都这么做

就覆盖当前项目已经确认的设计。

外部资料用于回答：

> 别人怎么解决类似问题？

最后仍需要结合：

- 当前规模；
- 项目规则；
- 已有能力；
- 用户需求；

做决定。

---

# 28. 外部检索不得泄露私有上下文

使用 Web、GitHub Search、第三方 MCP 或其他外部服务时，不直接提交：

- 私有源码；
- 公司业务名称；
- 内部 API；
- 密钥；
- 用户数据；
- 完整私有聊天记录。

需要搜索时，先抽象成通用技术问题。

例如不要搜索：

```text
公司 payroll approval southService CompleteTask 这里怎么拆
```

而应搜索：

```text
Go service repository transaction orchestration pattern
```

---

# 29. Skill 按任务触发，不默认全部加载

如果存在多个 Agent Skill：

```text
octocode-research
database-review
api-design
workflow-retrospective
```

不要每次任务全部加载。

只有当前任务符合 Skill 的职责时再使用。

例如：

```text
重要新功能 / 架构设计
→ octocode-research

复盘最近开发过程
→ workflow-retrospective
```

普通局部 Bug 修复不需要调用全部 Skill。

---

# 30. 工具可用不代表每次必须使用

例如已经安装：

```text
Octocode
AOCI-CODE
LSP
GitHub MCP
```

应根据任务选择。

不要因为工具已经安装，就为了“充分利用”每次都调用。

例如：

```text
修改一个已知位置的错误文案
```

不需要：

```text
搜索 GitHub 开源实现。
```

工具的目标是降低成本。

不是增加固定步骤。

---

# 31. 已有专用工具时优先使用专用能力

反过来，如果任务明显属于某种专门能力，应优先使用已经存在的工具。

例如：

```text
查调用关系
→ LSP / References

研究开源实现
→ Code Research Tool

理解项目整体结构
→ Codebase Map

查第三方 API
→ 官方文档工具
```

不要每次都退化成：

```text
grep
cat
普通网页搜索
```

---

# 32. 不因为工具失败就阻塞整个任务

专用工具不可用时：

1. 记录工具失败；
2. 使用可靠的替代方式继续；
3. 不虚构工具已经提供的结果。

例如：

```text
项目地图不可用
→ 使用源码搜索和调用关系确认
```

不要因为 AOCI 暂时失效，就认为项目无法开发。

---

# 33. Plan 模式中的上下文加载

进入 Plan 模式后，优先读取：

```text
AGENTS.md
plan.md
```

然后根据需求影响补：

```text
architecture
usecase
data
runtime
api
go
testing
...
```

再使用项目地图定位真实代码。

Plan 阶段的目标是：

> 获得足够信息设计未来实现。

不是：

> 提前读完整个项目所有实现。

只需要深入到能够确定：

- 业务负责人；
- 调用链；
- 关键方法；
- 数据结构；
- 文件位置；
- 事务；
- 异步行为；
- 验收方式。

---

# 34. 实现阶段不重新从零理解 Plan

Plan 已经确认后，实施阶段应直接以最新 Plan 为任务上下文。

不重新：

```text
把需求再推导一遍
重新设计模块
重新决定表结构
```

除非实际源码证明 Plan 存在错误。

实施阶段重点加载：

```text
确认后的 Plan
相关规则
将要修改的源码
相关测试
```

---

# 35. Plan 与当前代码冲突时必须指出

实现前发现：

```text
Plan 认为 A 调 B

实际源码已经变成 A 调 C
```

不能：

```text
偷偷按照源码改成另一套实现。
```

应判断：

- Plan 是否过期；
- 项目代码是否在 Plan 后变化；
- 是否影响业务设计。

如果是设计级变化，回到 Plan 处理。

如果只是局部实现细节，可以在不改变设计的情况下调整。

---

# 36. Review 阶段只加载评审所需上下文

Review 不应该重新读取整个仓库。

优先读取：

```text
确认后的 Plan
实际 Diff
受影响规则
相关关键源码
相关测试结果
```

评审重点是：

```text
实现是否符合 Plan
实现是否符合规则
是否出现范围外修改
```

---

# 37. 调试阶段围绕证据扩大上下文

排查问题时不要一上来读整个模块。

从证据开始：

```text
错误日志
失败测试
HTTP 响应
Stack Trace
数据库状态
```

然后沿调用链扩大：

```text
入口
→ 业务判断
→ 数据访问
→ 外部调用
```

每次扩大都应该由当前证据驱动。

---

# 38. 不把日志或错误信息当作完整事实

例如日志显示：

```text
article import failed
```

不能立刻假设：

```text
数据库写入失败。
```

需要继续确认：

- 外部 Fetch；
- Service；
- Repository；
- Retry；
- Context Cancel；

哪一层真正失败。

上下文加载应该帮助验证假设，而不是为假设寻找支持。

---

# 39. 大文件优先定位再读取局部

对于非常大的：

```text
runtime.md
contracts.md
service.go
migration.sql
```

如果工具支持定位标题、Symbol 或行范围，优先：

```text
找到相关 Section
↓
读取相关范围
```

不要默认每次完整读取几千行。

但涉及整份契约语义时，应读取足够上下文，避免断章取义。

---

# 40. 不为了节省上下文只读取搜索命中单行

搜索结果只是定位工具。

例如：

```text
rg MarkArticleImportReady
```

找到一行以后，不应直接根据这一行修改。

需要读取：

- 所在函数；
- 相关类型；
- 前后业务逻辑；
- 必要调用方。

目标是：

> **减少无关上下文，而不是减少理解。**

---

# 41. 优先保留“决定”，不要保留全部讨论过程

如果一次讨论最后确定：

```text
书籍继续使用 Article Service
```

后续上下文只需要保存：

```text
决定：
书籍继续属于 Article Service。

原因：
复用已有正文、解释、阅读进度能力。
```

不需要默认加载：

```text
之前曾讨论 Book Service
为什么提出
反驳了几轮
最终怎样争论
```

历史讨论需要时再查。

---

# 42. 项目规则中记录最终有效约定

一项架构决定已经稳定后，应进入对应项目规则或地图。

不要长期依赖：

> “某次 Chat 里已经讨论过。”

新 Session 应能通过项目本身恢复关键决定。

例如：

```text
project.md

Book API 仍调用 Article Service，
不建立独立 Book Service。
```

这样 Agent 不需要读取历史聊天才能知道当前边界。

---

# 43. 不把临时任务写成永久规则

例如本轮：

```text
暂时不开发删除 API
```

不一定属于全局开发规范。

它应该存在于：

```text
当前 Plan
项目 Roadmap
当前功能契约
```

而不是：

```text
所有项目永远禁止 Delete API。
```

规则只沉淀稳定原则。

任务范围保留在任务上下文。

---

# 44. 更新规则时删除失效内容

不要只追加：

```text
旧规则
新规则
例外
新例外
再补一条例外
```

导致 Agent 同时看到多个版本。

规则变化后应：

```text
修改原规则
删除已经失效的内容
```

历史原因如果仍有价值，单独进入：

```text
decision record
history
```

而不是留在当前执行规则中。

---

# 45. 冲突规则必须显式处理

如果读取到：

```text
rule A：
Worker 不直接写业务表

rule B：
某 Worker 应直接更新 Article
```

不能自行选一条。

先判断：

- 是否一个是通用规则，一个是项目明确例外；
- 是否一个已经过期；
- 是否文档冲突。

无法确认时，明确指出冲突。

不要：

```text
默默选择更方便实现的一条。
```

---

# 46. 项目级例外必须明确标注

如果某个项目确实不遵循通用默认规则，应写成：

```text
例外：
EPUB 完整发布当前仍由 Repository 原子保存完整书籍结构。

原因：
这是已经存在并确认的原子发布行为。

范围：
仅 EPUB 完整发布，不作为新增业务默认模式。
```

这样 Agent 不会把：

> 一个历史例外

复制成：

> 全项目新模式。

---

# 47. 用户当前明确指令不能被 Memory 覆盖

如果 Memory 或历史记录说：

```text
用户以前偏好方案 A
```

而当前用户明确说：

```text
这次采用方案 B
```

必须采用当前指令。

Memory 用于减少重复沟通。

不能用于推翻当前明确决定。

---

# 48. 不根据用户偏好擅自扩大需求

即使历史中知道：

```text
用户喜欢自动化
```

也不能因此在普通需求里自动增加：

```text
Scheduler
Worker
MCP
Plugin
```

历史偏好只能帮助：

> 在多个合理方案中理解用户倾向。

不能代替当前需求证据。

---

# 49. 上下文不足时优先补证据，而不是猜测

如果无法判断：

```text
这个状态由谁修改？
```

应：

```text
查定义
查引用
读 Service
读 Repository
```

而不是根据目录名猜。

如果源码和规则仍不足以判断业务含义，再按照 `plan.md`：

> 推荐方案 + 选择题

向用户确认。

---

# 50. 上下文足够以后停止继续搜索

Agent 应识别：

> 当前已经有足够信息做决定。

不要因为还能继续搜索就不断搜索。

例如已经确认：

- 业务 Owner；
- 调用链；
- 数据结构；
- 相关规则；
- 关键测试；

就应该开始设计或实现。

额外阅读必须有明确目的。

---

# 51. 避免“为了保险多读一点”的无限扩张

这种行为：

```text
这个可能有关
↓
再读一个文件
↓
那个也可能有关
↓
再读整个目录
```

很容易导致上下文污染。

每次准备扩大范围前，先问：

> **当前缺少什么具体信息？**

例如：

```text
缺少事务边界
→ 读 data.md + Service + Repository

缺少 Retry 行为
→ 读 runtime.md + Worker

缺少 API 错误映射
→ 读 api.md + Handler
```

不能只因为“不确定还有没有别的东西”就读取整个项目。

---

# 52. 上下文预算优先留给当前任务

上下文中最重要的应该是：

```text
当前需求
确认后的 Plan
相关规则
相关代码
相关测试
```

而不是：

```text
大量历史讨论
全部项目文档
所有 Migration
所有开源调研内容
重复规则
```

如果必须选择：

> **优先保留能直接影响当前设计和实现正确性的内容。**

---

# 53. 外部研究结果只保留最终结论和证据

例如进行开源项目调研后，不需要长期保留：

```text
搜索过的几十个项目
所有搜索结果
所有尝试路径
```

进入当前任务上下文的应该主要是：

```text
参考了什么
看了哪个实际实现
采用什么
不采用什么
为什么
```

例如：

```text
参考 Miniflux：

采用：
- Feed 负责发现链接；
- Article 流程负责正文处理。

不采用：
- 完整 RSS Reader 数据模型。

原因：
- 当前产品核心是文章学习，不是 Feed 浏览。
```

---

# 54. 新 Session 的默认恢复流程

新 Session 开始一个已有项目任务时，推荐顺序：

```text
1. 读取项目 AGENTS.md

2. 读取当前任务对应规则

3. 使用项目地图定位相关能力

4. 读取相关源码和测试

5. 查看当前 git status / 工作区变化

6. 恢复当前任务或开始 Plan
```

不要默认：

```text
重新 tree 整个仓库
重新读全部 README
重新读全部规则
重新推断整个架构
```

---

# 55. 继续旧任务时先恢复任务状态

如果继续一个已有开发任务，先确定：

```text
Plan 是否已经确认
实现做到哪里
哪些文件已经修改
测试做到哪里
是否有未解决问题
```

再继续开发。

不要因为新 Session：

> 把已经完成的步骤重新做一遍。

尤其不要把：

```text
已经完成的重构
```

再次识别成：

```text
待解决问题。
```

---

# 56. git status 是当前工作区上下文的一部分

开始修改前应了解：

```text
当前有哪些未提交修改
哪些属于当前任务
哪些是用户已有工作
```

不能因为 Agent 只关注源码逻辑，就忽略工作区状态。

已有修改需要：

> 保留。

不要：

```text
reset
checkout
stash
```

用户内容，仅为了得到“干净环境”，除非用户明确授权。

具体 Git 操作遵循 `contributing.md`。

---

# 57. 规则读取本身不要产生业务修改

加载规则、建立上下文、读取地图阶段：

> 默认是只读操作。

不要因为读取到：

```text
项目中存在一个历史不规范实现
```

就立即开始重构。

先完成当前任务判断。

---

# 58. 不把上下文加载过程变成交付内容

Agent 不需要每次向用户完整报告：

```text
我读了 17 个文件
我搜索了 8 个 Symbol
我加载了 4 个规则
```

除非这些信息：

- 影响结论可信度；
- 存在缺失；
- 工具失败；
- 规则冲突；
- 用户要求查看。

正常情况下，直接输出：

> 设计或实现结果。

上下文加载是内部开发过程，不是产品。

---

# 59. 但关键依据应该可追溯

当 Plan 或设计做出重要决定时，应能够指出：

```text
基于哪个现有模块
基于哪个项目规则
基于哪个当前契约
```

例如：

```text
继续使用 Article Service，
因为当前项目已经将书籍正文、导入和阅读进度归属 Article Service。
```

不要求为每一句话附来源。

但重要架构决定不能只是：

> “我觉得这样更合理。”

---

# 60. 上下文加载完成后的自检

在开始 Plan、实现或 Review 前，Agent 至少确认：

## 任务

- 当前真正目标是什么？
- 本轮范围是什么？
- 有没有已经确认的 Plan？

## 规则

- 当前任务需要哪些规则？
- 是否遗漏跨领域规则？
- 是否加载了大量明显无关规则？

## 项目

- 项目地图是否存在？
- 当前业务负责人是谁？
- 真正相关源码在哪里？

## 事实

- 哪些来自规则？
- 哪些来自地图？
- 哪些已经用源码确认？
- 哪些只是历史讨论？

## 工作区

- 当前是否存在用户未提交修改？
- 本次任务允许修改什么？

## 冲突

- 规则与源码是否冲突？
- 当前决定与历史决定是否冲突？
- 是否需要用户确认？

如果这些问题已经明确，就停止继续扩大上下文，进入实际工作。

---

# 61. 最终目标

上下文加载应该形成：

```text
当前任务
↓
AGENTS 入口
↓
按任务加载规则
↓
项目地图定位
↓
读取少量相关源码和测试
↓
确认当前事实
↓
Plan / 实现 / Review
```

而不是：

```text
当前任务
↓
读取所有规则
↓
读取 README
↓
读取全部项目文档
↓
扫描整个仓库
↓
加载历史聊天
↓
搜索所有相关词
↓
上下文已经非常大
↓
才开始思考
```

最终应让 Agent 能够回答：

> 当前任务需要遵守哪些规则？
> 这个能力现在属于哪个模块？
> 需要读取哪些代码才能确认？
> 哪些信息只是历史，哪些是当前事实？
> 是否存在已经确认的决定？
> 当前上下文是否已经足够？
> 有没有读了大量和任务无关的信息？
> 如果开启一个新 Session，能否快速恢复到正确位置？

目标不是：

> **让 Agent 记住整个项目。**

目标是：

> **让 Agent 每次都能快速找到正确的信息，
> 只加载完成当前任务真正需要的上下文，
> 并把更多注意力留给设计和代码本身。**
